## Summary

Reserve from Pool is a composition (a spec that wires two or more atoms — freestanding, self-contained pattern specs — together) that solves a problem none of its constituents solves alone: managing the full life of a reservation against a finite pool so that the pool's free count is always exactly right.

A request takes a provisional hold on one unit of a bounded pool; the hold is confirmed into a firm booking, cancelled, or allowed to time out; and at every instant the pool's `allocated` total equals the number of reservations still live against it.

It wires five constituents: Provisional Commitment (the per-reservation Held → Confirmed | Released | Expired state machine with its confirm-within-window guarantee), Capacity Constraint Enforcement (the bounded pool whose running total never exceeds its declared capacity), Duplicate Prevention (the retry guard that makes every reservation action safely repeatable), Event Log (the durable journal of every state change), and Actor Identity (the attestation that binds every act to a verifiable actor).

The composition's defining emergent guarantee (a property that appears only when atoms are combined — no single atom carries it) is **allocation coherence**: the pool's `allocated` count stays in exact lockstep with the set of reservations in a slot-holding state (Held or Confirmed). Three consequences follow. Confirmed reservations never exceed pool capacity — every [Reserve] gates on `Capacity Constraint.allocate`, which refuses past `capacity`. A cancelled or expired reservation returns its slot to the pool *exactly once* — the terminal transition, the pool `release` and the journal entry are ordered and reconciled against the pool's own count, so no slot is leaked (a cancellation whose unit is never returned) and none is double-released (a unit returned twice, driving the count below the truth). And no reservation is confirmed unless its hold is still live at confirmation time — Provisional Commitment's confirm-within-window guarantee, surfaced at the composition layer, prevents confirming a slot that has already lapsed and been returned.

Beyond coherence, the composition makes every reservation action idempotent under retry (safe to repeat — a retried call returns the first call's outcome instead of acting twice) (the Idempotent Reservation precursor's contract, extended over the pool-aware surface), and records every state change as a durable, attributed Event Log entry. Its most common uses are airline and hospitality booking, event ticketing, hospital bed and resource allocation, and warehouse and supply-chain inventory reservation. Any system that must guarantee, from the pool count alone, that it never oversells and never strands inventory across the reserve/confirm/cancel/expire arc is a candidate for this composition.

## Intent

Every system that reserves a unit of a finite resource faces the same arc, and it is the same whether the resource is an airline seat, a hotel room, a hospital bed, an event ticket, or a unit of warehouse inventory: a request encumbers one unit of a bounded pool provisionally; the encumbrance resolves into a firm booking, a cancellation, or a timed-out lapse; and the pool's free count must reflect, at every instant, exactly how many units are spoken for. Get the binding between the per-reservation lifecycle and the pool arithmetic wrong and the system either oversells (two reservations confirmed against one slot) or strands inventory (a cancelled reservation whose slot is never returned). The arc is constant; the failure modes are constant; and they live precisely at the seam between *the reservation* and *the pool*.

Neither Provisional Commitment nor Capacity Constraint Enforcement, alone, closes that seam. Provisional Commitment owns the per-reservation state machine — Held → Confirmed | Released | Expired, with the confirm-within-window guarantee (Invariant 7) that a hold cannot be confirmed after its window has elapsed — but it holds *one* resource per commitment and, by its own specification, *"does not opine on pool-level rules"*; it has no notion of a bounded pool or a running total. Capacity Constraint Enforcement owns the pool arithmetic — `allocated ≤ capacity` (Invariant 4) enforced by precondition on `allocate`, and `allocated ≥ 0` (Invariant 5) enforced on `release` — but units are *fungible* at its grain: it tracks a running count, not per-allocation identities, and by its own specification *"the composing pattern supplies the per-allocation identity; this atom owns only the pool's arithmetic."* Capacity Constraint even admits `release` against a Closed pool *expressly so that a composing pattern like Provisional Commitment can return slots when its holds reach terminal states* — naming the seam, and naming this composition as the thing that lives there, without filling it. The binding that keeps `allocated` in lockstep with the live-reservation set — allocate-on-hold, hold-the-slot-through-confirm, release-on-terminal — belongs to no single constituent. It belongs to the composition, and this composition is that binding.

This is a composition, not a new primitive. The five constituents are unchanged; the composition is the wiring that makes them coherent as a single reservation surface. It introduces emergent actions — [Reserve], [Confirm Reservation], [Cancel Reservation], [Expire Reservation] — that bind a Provisional Commitment to a Capacity Constraint pool slot, deduplicate retries through Duplicate Prevention, attribute every act through Actor Identity, and journal every state change through Event Log. The [Reserve] action, in particular, wraps a capacity gate (`Capacity Constraint.allocate`), a provisional hold (`Provisional Commitment.place_hold`), a duplicate check, and a journaled, attributed event into one named surface, so that taking a slot is one ordered, recorded act whose pool effect is bound to the reservation — not a `place_hold` whose pool consequences leak into whatever code remembers to decrement the counter.

What the composition is *not*: it is not the resource-availability oracle (whether a *specific* seat or room is bookable belongs to Provisional Commitment's registry, upstream of the pool count); it is not the overbooking-policy engine (a deployment that deliberately oversells by N sets the pool's `capacity` above the physical count — that is a Configuration choice, not a composition behavior); it is not the pricing, waitlist, or fulfillment surface; and it is not the audit-substrate composition (it journals to Event Log and attributes via Actor Identity directly, the lighter pairing, rather than composing the full tamper-evident Audit Trail — a deployment needing seals composes Audit Trail as a peer). Each is named explicitly in Edge cases.

## Composes

- **[Provisional Commitment](../atoms/provisional-commitment.md)** — the per-reservation state machine: Held → Confirmed | Released | Expired, with `place_hold`, `confirm`, `release`, `expire`, the confirm-within-window guarantee (Invariant 7 — a hold cannot be confirmed after `expires_at`), and terminal absorption (Invariant 3). The composition maintains exactly one Provisional Commitment instance and is the sole writer of its state transitions; a reservation *is* a Provisional Commitment, and its `id` is the `reservation_id`. The composition calls `place_hold` (from [Reserve]), `confirm` (from [Confirm Reservation]), `release` (from [Cancel Reservation]), and `expire` (from [Expire Reservation]).
- **[Capacity Constraint Enforcement](../atoms/capacity-constraint-enforcement.md)** — the bounded pool whose `allocated ≤ capacity` (Invariant 4) and `allocated ≥ 0` (Invariant 5) the composition relies on rather than re-implements. The composition maintains one or more Capacity Constraint pools (one per reservable resource class) and is the sole writer of `allocate`/`release` against them for slots it binds. It calls `allocate(pool_id, count=1, ...)` at [Reserve] (the capacity gate), `release(pool_id, count=1, ...)` at [Cancel Reservation] and [Expire Reservation] (the slot return). It also **reads the pool's persisted audit log** — the allocation or release event whose id its call returned, for the `Allocated Before` / `Allocated After` pair the atom writes atomically with the running-total update (its Invariant 14), and the pool's allocation events for the reconciliation's partial-[Reserve] leg. That surface is not `query`: the atom routes its audit log to *"direct inspection of the persisted record by audit pipelines"* and *not* through `query`, so the read is declared here as an instance capability the deployment supplies, `pool_event_read` (Configuration). And the atom's serialization is **per call** — *"Each action's effects (running-total update, audit-log append) are atomic with respect to other concurrent calls"*, while *"Multi-action transactions … belong to a Transaction composition"* — so a section spanning several calls is nothing the pool grants, and every multi-call section on this page is the deployment's `host_exclusion` obligation (Configuration), never the pool's. Capacity Constraint's admission of `release` in every pool state, Closed included (its transition table's any-state `release` row; its Invariant 3 makes Closed absorbing for *new allocations* while leaving releases admissible) is the constituent guarantee that makes slot-return correct even for a pool closed to new reservations while live holds unwind.
- **[Duplicate Prevention](../atoms/duplicate-prevention.md)** — the temporally-bounded retry guard. The composition maintains exactly one Duplicate Prevention instance configured with the idempotency window; every state-changing action carries an `idempotency_token` checked against it, so a retried [Reserve]/`confirm`/`cancel` returns the original outcome rather than acting twice. This is the Idempotent Reservation precursor's mechanism, carried into the pool-aware surface. **The constituent's declared failure modes are inherited as named host obligations at this layer** — mirroring how Invariant 1 inherits the pool's: the recorded-set store must be durable and highly available (the constituent declares its `record` store-write failure a *silent window miss*, under which a retry re-delegates); `check`-unavailability, a fail-open/fail-closed choice the constituent leaves to the deployment, must be handled **fail-closed** here (refusing a retryable reservation is recoverable; double-taking a slot is not); and `token_results` plus the `record` must be durable **before the action's result returns** (the inherited durability ordering — otherwise a crash between the constituent commit and the `record` licenses a re-delegating retry, and the silent miss additionally licenses premature `token_results` eviction through the `check = not-seen` eviction gate). Invariant 5 and Generation-acceptance check 5 are conditioned on these obligations.
- **[Event Log](../atoms/event-log.md)** — the durable, append-only, total-ordered journal. Every state-changing composition action appends **two** Event Log entries — an **intent** entry before any constituent call that commits, and an **outcome** entry after — each recording the action, the invocation's `idempotency_token`, the `attestation_id` binding the act to its actor, the reservation and pool ids, and the timestamp; the outcome entry additionally records the prior and new commitment state and the pool arithmetic (`allocated_before`/`allocated_after` — **copied from the pool's own allocation or release event**, the one whose id `allocate` or `release` returned, read through `pool_event_read`: Capacity Constraint writes that event's `Allocated Before` / `Allocated After` atomically with the running-total update under its Invariant 14, so the pair is the pool's before and after for *this* call, which two `query` reads around the call — a three-call section the atom's per-call serialization does not cover — never were. On [Confirm Reservation], which makes no pool call, the entry carries one `Capacity Constraint.query(pool_id).allocated` read as both values, a witness that the slot stayed counted and not a chain link; the replay chains only entries that cite a pool event id). The pairing is one-to-one only on the paths that commit: an invocation a constituent guard refuses leaves its intent entry unmatched, which is a record of an authenticated attempt rather than a defect (Generation acceptance). Event Log's insertion order is the authoritative ordering of reservation events. **Its durability across a crash is inherited as a host obligation, not assumed from the atom:** Event Log says of itself *"Append is durable on success to the extent the deployment supplies durability"* and *"The atom specifies in-memory semantics. Persistence across process restarts is handled at the deployment layer"* — so every claim on this page that reads the journal after a crash (the rebuild, every sweep leg, Invariants 1, 2 and 6) rests on `journal_durability` (Configuration), the deployment's declared ordering of the journal's durability against the constituent stores it must outlast. Its query shape is likewise the deployment's: Event Log admits a payload predicate as *implementation policy*, and this composition's reads keyed by `idempotency_token`, `reservation_id`, `pool_id` and `action` are declared against `journal_query_shape` (Configuration) rather than attributed to the atom. (The composition uses Event Log directly rather than the full Audit Trail substrate; a deployment requiring tamper-evident seals and attribution-as-one-record composes Audit Trail as a peer — see Edge cases.)
- **[Actor Identity](../atoms/actor-identity.md)** — the attestation surface, and the composition's **only credential-verifying call**. **Two host obligations ride with it, inherited explicitly rather than assumed**, in the same way this composition inherits Duplicate Prevention's and Capacity Constraint's: the **actor registry** whose public material `attest` validates against and `verify` re-checks is a deployment-supplied substrate this composition does not own, and for attestations to stay verifiable across a key rotation that registry **must retain historical material** — Actor Identity states plainly that it does not, and that whether the registry does belongs to the registry; and the **attestation store's durability** is implementation-owned by that atom's own declaration. Generation acceptance check 6 is answerable only where both obligations are met, and the auditor is handed the registry's public material alongside the stores. Every state-changing action calls `attest(action_ref, actor_ref, credential) → attestation_id | rejected(invalid-request | invalid-credential | storage-failure)` **before any constituent call that commits**, so the `actor_ref` and `credential` are bound cryptographically and an unverifiable credential refuses the action with nothing written (Actor Identity's `invalid-credential` is a guard rejection that precedes its own store write). The returned `attestation_id` is **carried on every Event Log entry the action journals**, which is what makes the attribution claim witnessable from the records rather than asserted: an auditor reads the entry, takes its `attestation_id`, and calls `verify` against it. The `action_ref` is composed per-invocation as `"<action>:<idempotency_token>"` — Actor Identity Invariant 2 binds a proof to its recorded action reference, so a bare kind token would bind the proof to a category of act rather than to the act. The composition maintains one Actor Identity instance.

## Composition logic

### Composition state

The composition owns emergent state that wires the five constituents into one queryable reservation surface. None of this state belongs to a single constituent.

- **`reservation_to_pool`** — map from `reservation_id` (the Provisional Commitment `id`) to the `pool_id` whose slot the reservation holds. Populated by [Reserve]; read by [Cancel Reservation] and [Expire Reservation] to know which pool to `release` against. **This is the binding the composition exists to maintain** — it is what makes a reservation's pool slot a recorded fact rather than an implicit consequence. The entry persists for the life of the reservation record (it is the record of which slot the reservation took, retained even after terminal resolution as the audit join from the reservation to its pool). *Cardinality/modality:* exactly one entry per reservation this composition **completed** — one whose `reserve` outcome entry landed (1:1 with those, mandatory, never removed); each entry names exactly one `pool_id` (reservations-to-pools is N:1). **The Provisional Commitment store may hold records the map never names, by design:** a hold placed at [Reserve] step 6 whose outcome entry then failed at step 7 is *compensated*, not completed — driven to Released or Expired, its slot returned, its `reserve_compensated` entry naming the `reservation_id` — and it gets no binding, because it holds no slot and the map is the record of slots held. So the map is 1:1 with completed reservations, not with every Provisional Commitment record, and a Released or Expired record with no binding is that compensation's signature (check 3), never a lost entry. A field `release ∈ {none, pending(invocation), released(release_event_id)}` on the entry records the slot's return: `pending` is written durably **before** the pool `release` is called, carrying the invocation's `idempotency_token` and `attestation_id`, and `released` is written after it returns — so the entry is the composition's own marker of a return that is owed, in flight, or done, and the pool reconciliation leg reads it (Action wiring; *Cross-store consistency under partial failure*). [Slot Released] names the `released(…)` value. No transaction spans the transition, the pool release, and the journal entry — none of the three stores offers one — so the at-most-once return (Invariant 2) is carried by this marker together with the pool reconciliation, not by an atomic commit. **Contract classification: derived index.** Every fact the map carries is journaled: the [Reserve] Event Log entry carries `{reservation_id, pool_id}` and each terminal or compensating entry carries the release fact (`release_event_id`). *Rebuild procedure:* traverse the Event Log (under `journal_durability`, through `journal_query_shape`) for this composition's `reserve` outcome entries and take `{reservation_id → pool_id, release = none}` from each; set `release = released(release_event_id)` where a `cancel_reservation` or `expire_reservation` outcome entry — in-line or `recovery = true` — names the same `reservation_id` (each carries its `release_event_id`). **The outcome takes precedence over any unmatched intent:** only where **no** slot-returning outcome names the reservation at all does an intent entry (`cancel_intended` / `expire_intended`) with no outcome rebuild as `pending`, and only where the Provisional Commitment record's terminal state is the one that intent's action writes — Released for `cancel_intended`, Expired for `expire_intended`. An unmatched intent whose reservation another token returned, or whose terminal state belongs to the other action, is a refused attempt (its step 1's `not-held` / `window-elapsed`) that rebuilds nothing. `pending` is the reconciliation's input, not a stranded slot, and it is keyed per reservation, never per intent. A `reserve_compensated` entry names a `reservation_id` only on the step-7 path, and that reservation has no `reserve` outcome entry and therefore no binding to flag — the rebuild reads compensations for check 3's compensation arm, not for the map. The Contract's three obligations follow: the map sits **outside the actions' atomicity surface** for its *population* (the truth-bearing writes are the constituent transitions and the journal entry; the `release` marker is the one field that is **truth-bearing while it reads `pending`** — the record that a return was begun and not yet journaled, existing in no constituent — held under a durability obligation (Configuration, `index_durability`) and extraction-pending against a durable **Outbox** atom *(forthcoming)*, and a lost `pending` marker is resolved by the pool reconciliation's arithmetic, never by re-running the release; a missing or lost entry otherwise is a **rebuild trigger, not data loss** — reads consult it with rebuild-on-miss semantics, and the recovery discipline consults *the journal via rebuild* and the pool's own count before any release; and the map claims no cross-constituent transactional consistency at all — only the ordered slot-returning pair and the reconciliation the actions themselves declare.

  **The rebuild is bounded by the journal's own retention, and the bound has to be stated because a check now depends on this traversal.** The procedure reads Event Log entry payloads, and where the journal is the Audit Trail substrate its purge cascade destroys a payload in its entirety at the instance's horizon — leaving `event_id` and `sequence_number` and not even the entry type a traversal filters on. Past that point entries here are **not rebuildable**: `pool_id` is the binding this composition exists to maintain and **no constituent holds it** — Provisional Commitment records the reservation, not the pool whose slot it took, which is the whole reason the map exists — so there is no second source to fall back to, and the entries for reservations whose journal entries have been purged are **truth-bearing** under the same `index_durability` obligation, **extraction-pending** against the *Erasure Tombstone* atom *(forthcoming)* the audit substrate names for the same class of fact; the classification splits by retention state, and a rebuild from the live journal repopulates the live half and leaves the purged half standing. Two claims spend this. Generation acceptance **check 1** was anchored in this traversal (methodology debt #19's enumeration-anchoring round) precisely so an index gap could not masquerade as an allocation-coherence violation; past the horizon that anchor is gone and the check degrades to counting whatever the index still holds, which is the state the anchoring removed. And the **recovery discipline** consults the journal via rebuild before any release retry, so past the horizon it consults a shorter journal. The deployment obligation that keeps both sound is Configuration's `journal_retention_ordering`.
- **`token_results`** — the idempotency cache inherited from the Idempotent Reservation precursor: a map from `idempotency_token` to a recorded outcome `(action_type, parameters_digest, result)`. `parameters_digest` is a collision-resistant digest of the **business** call parameters — the ones that determine the outcome (`pool_id`, `resource`, `requester`, `duration` at [Reserve]; `reservation_id` at the terminal actions) — and **explicitly not `actor_ref` or `credential`**, **computed by a pure function or configured digest mechanism at the composition's I/O seam and injected into the transition** — the digest is an explicit input derived from the already-present non-token call parameters, not cryptography improvised inside core logic (see Configuration §`digest_function`; the mechanism-capability pattern per [`execution-contract.md`](../execution-contract.md) §Logic Confinement Principle). Its lifetime is governed by the Duplicate Prevention window (entries are evicted when the token leaves the `recorded` set); a `token_results` entry is never evicted while its token remains in Duplicate Prevention's recorded set — the eviction-ordering constraint inherited from Idempotent Reservation Invariant 7, **enforced through a declared surface**: the evictor may remove `token_results[t]` only after `DuplicatePrevention.check(t)` returns `not-seen` (the token has left the window), so the constituent's own window query is the gate on every eviction, not a second clock this layer keeps. `action_type ∈ {reserve, confirm_reservation, cancel_reservation, expire_reservation}`.

**Classification: extraction-pending.** `token_results` carries non-derivable truth — which result was returned for a given token — that no replay of the constituent stores can reproduce: Duplicate Prevention answers *have I seen this identity?* (membership, no payload) and does not act on the result. Per [`execution-contract.md`](../execution-contract.md) §Composition state, a composition element that carries truth not reconstructible from constituent stores is a not-yet-extracted atom, and until that atom lands the element is declared here as recorded debt riding the extraction's schedule. The proposed atom is an **Idempotency Result Memo** (token → result; write-once; window-governed eviction); the extraction is opened as a roadmap proposal (see [`roadmap.md`](../roadmap.md)).

The Provisional Commitment store (commitment records and their states), the Capacity Constraint stores (pool records and running totals), the Duplicate Prevention store (recorded tokens), the Event Log store (entries), and the Actor Identity store (attestations) are owned by their respective constituent instances. The composition does not duplicate them; it indexes into them via the maps above.

### Configuration

- **`idempotency_window`** — the duration of the Duplicate Prevention window, passed to the Duplicate Prevention instance. Selected to cover the slowest legitimate retry cycle for the most critical action (inherited from Idempotent Reservation Configuration; defaults 60 s for HTTP (Hypertext Transfer Protocol) retry envelopes through 24 h for slow reconciliation rails).
- **`pool_capacity`** — the declared `capacity` of each Capacity Constraint pool, set at pool declaration. A deployment that deliberately overbooks sets `capacity` above the physical unit count (Edge cases — *Overbooking is a capacity choice*); the composition enforces `allocated ≤ capacity` against whatever `capacity` is declared, and does not itself model overbooking policy.
- **`expiry_sweep`** — the deployment's strategy for invoking [Expire Reservation] on holds whose window has elapsed: an eager scheduled sweep (a background job firing [Expire Reservation] at `expires_at`) or a lazy on-observation sweep. The composition holds the binding (`reservation_to_pool`) and exposes [Expire Reservation], but is not the scheduling engine (Edge cases — *Expiry sweeper boundary*, mirroring Customer Onboarding's monitoring-scheduler boundary).
- **`application_actor_ref` and `application_credential`** — the composition's **service identity**, under which the reconciliation sweep acts when the invocation that owed a write is gone: its `Actor Identity.attest` for every journal entry it writes (`action_ref = "recovery:" + <the original idempotency_token>`), the `releasing_actor_ref` it passes to `Capacity Constraint.release`, and the actor on any `Provisional Commitment` transition it completes. The original operator is carried in the recovery entry's data and its `attestation_id` (the intent's proof) alongside; the sweep never attests as the absent operator.
- **`reservation_completion_bound`** — the deployment-declared maximum duration of a state-changing invocation between its intent entry and its outcome entry, read against the seam-injected `now`. It is the **lower edge** of every leg of the reconciliation sweep: an intent younger than it may belong to an invocation still between its writes, and a sweep that compensated or completed it then would release a slot the invocation is about to release, or return one it is about to hold — the double release and the oversell the sweep exists to prevent. The **upper edge** is the journal's retention horizon (`journal_retention_ordering`): past it the intent entry is destroyed and the binding's purged half is truth-bearing, so the sweep reads the index there and repairs nothing it cannot re-derive. *Default:* none.
- **`compensation_window`** — the deployment-declared duration within which an owed compensation or completion — a partial [Reserve], an unreturned slot behind a terminal transition, an unjournaled confirmation — must land, or be escalated as an unresolved finding. Invariant 1's liveness arm and check 3 spend it; no default is prescribed.
- **`reconciliation_cadence`** — the interval at which the reconciliation sweep runs, in addition to its mandatory run at process restart. **The inequality that makes `compensation_window` meetable is `reservation_completion_bound + reconciliation_cadence + recovery_write_latency < compensation_window`, strictly** — an orphan created at `t` is invisible to every leg until `t + reservation_completion_bound`, the next run is at most a cadence later, and the compensating release and its outcome entry land a latency after that; *cadence no longer than the window* is satisfied by a deployment that breaches on every orphan. `recovery_write_latency` is the deployment's disclosed bound on one leg's closure landing — the pool `release` and the recovery outcome entry. The three terms are checked at instance start, and a deployment whose knobs fail the inequality refuses to start rather than starting to breach (§*Liveness is arithmetic*).
- **`outcome_retry_attempts`** — the number of times an invocation re-attempts a transient write **after its act has committed** — the outcome entry, a compensating release, a `reserve_compensated` entry, the late confirm entry — before it returns its `rejected(recording-failure(outcome))` and yields the orphan to the sweep. One injected `now` serves an invocation (*Logic confinement*), so its terminus is counted rather than timed; it is the invocation's half of the one-writer-per-act rule (§*A compensator is exclusive*; *Cross-store consistency under partial failure*). *Default:* none.
- **`journal_durability`** — an **inherited host obligation**: the Event Log instance survives a process crash, ordered **at least as durable as the Provisional Commitment and Capacity Constraint stores** whose commits its intent and outcome entries bracket. Event Log declares in-memory semantics and leaves persistence across restarts to the deployment (Composes), so a journal read after a crash — the rebuild, every sweep leg, check 1's anchor, Invariants 1, 2 and 6 — rests on this entry and on nothing the atom grants. A journal less durable than the stores it brackets would show a committed hold with no intent behind it, which no leg on this page can tell from an unauthenticated act.
- **`journal_query_shape`** — an **instance capability requirement**: the Event Log instance's query admits a payload predicate on `idempotency_token`, `reservation_id`, `pool_id` and `action`, bounded to a sequence-number range where the deployment prefers to filter composition-side. Event Log admits a payload predicate as *implementation policy*; every journal read on this page keyed by one of those fields is declared against this entry. **Membership in a candidate set is not a predicate the instance is asked for:** a read that must find a token among a sweep entry's `intent_candidates`, or a reservation among `release_candidates`, reads `action = reserve_compensated` (and the `recovery = true` outcomes) for the `pool_id` through the declared predicate and filters the candidate set **composition-side** — the declared route, never a filter attributed to the substrate.
- **`pool_event_read`** — an **instance capability requirement**: a consistent read of a Capacity Constraint pool's persisted record — its `allocated` and its audit log, keyed by `pool_id`, with an event addressable by the `allocation_event_id` / `release_event_id` the call returned. Capacity Constraint routes its audit log to *direct inspection of the persisted record*, not to `query` (Composes), so the `allocated_before` / `allocated_after` every outcome entry copies, and the allocation events the reconciliation enumerates, are read here or not at all.
- **`host_exclusion`** — an **instance capability requirement**: the deployment's **three mutual-exclusion sections**, declared because Capacity Constraint serializes each of its calls and nothing more (Composes): **per token**, taken at step 2's `check` and held through the `record`, so a concurrent retry never double-acts before the cache is populated; **per reservation**, taken at the invocation's **first write** — the intent entry — and held through the outcome entry, by the terminal actions, the late writes and every sweep completion; **per pool**, taken by [Reserve] at its first write (the intent entry, step 4) and held through step 8, by the terminal actions from the `pending` marker through the outcome entry, and by the sweep from its consistent `pool_event_read` through its releases and recovery entries. **Semantics, stated:** a section is released on the invocation's return or death; where the host implements it as a lease, the lease is exactly `reservation_completion_bound` long — at least the bound, so a live invocation inside its bound is never pre-empted, and no more, so a stalled-but-alive holder blocks the sweep for at most the bound and the liveness inequality's first term already counts the hold — and **its expiry is the invocation's terminus**: an invocation whose lease expired has yielded, and everything after belongs to the sweep. **Every write after an invocation's first write is made only while the section is held:** an invocation that finds its section lost re-takes it before its pre-check, re-reads the journal for its own act under it, and makes no write it cannot take the section for — a `Capacity Constraint.allocate` or `release`, a marker, an outcome entry — so it can never resume between the sweep's pre-check and the sweep's append. Two runs of a sweep leg — restart and cadence, one node or two — serialize on the same sections. *Default:* none; a deployment that supplies no section has no reconciliation.
- **`recovery_candidates_cap`** — the most ids a recovery entry may name in `release_candidates` or `intent_candidates`. The step-1 sizing of every action bounds the largest record the act can write against `journal_payload_cap` using this cap; a pool whose open set exceeds it is escalated as an unresolved finding rather than compensated in that run (§*An outcome is sized before the intent*). *Default:* none.
- **`journal_payload_cap`** — the Event Log instance's `append` payload cap (its `invalid-payload` arm; 64 kilobytes by the atom's default, per-instance). Every state-changing action sizes its largest possible entry — the sweep's recovery entry for it, with `recovery_candidates_cap` ids and the caller's own `resource` / `requester` strings — against it at step 1 and refuses `invalid-request` before the intent (Action wiring).
- **`journal_retention_ordering`** — the obligation that the Event Log instance's retention (where the journal is the Audit Trail substrate, its purge horizon) outlasts the longest reservation lifetime plus the period over which allocation coherence must be provable from the journal: `reservation_to_pool` rebuilds only from journal payloads, check 1 is anchored in that traversal, and the pool reconciliation reads it. Past the horizon the binding's purged half is the only carrier of `pool_id` (Composition state).
- **`index_durability`** — the durability the deployment owes the `reservation_to_pool` store, as an ordering: **at least as durable as the Provisional Commitment store it keys** — for the `pending` release markers, which exist in no constituent, and for the past-horizon entries, which are the only carrier of the reservation→pool binding once the journal payload is purged. The obligation is the deployment's until the Outbox and Erasure Tombstone atoms land.
- **`token_max_length`** — the byte cap on `idempotency_token` (*Primitive policies*), a deployment constant sized against the journal's payload budget.
- **`digest_function`** — the hash function and serialization convention used to compute `parameters_digest`. The digest is computed by a pure function or configured digest mechanism at the composition's I/O seam (injected as an explicit input into the transition; never computed inside core logic — Logic Confinement Principle). Must be specified and consistent across all instances sharing the `token_results` store; inconsistency across replicas or versions causes legitimate retries to be misclassified as `token-collision`.

### Logic confinement (clock and id)

The clock is an **injected input at the composition's single I/O seam**, never read inside a guard or a transition and never threaded through a caller signature. Per the Logic Confinement Principle ([`execution-contract.md`](../execution-contract.md)), the host reads the clock once per invocation and injects `now` (`clock_t`) at the seam before the orchestration runs; each action is a pure function of its inputs, the constituent records, and that injected `now`. Because the clock enters at the seam rather than as a parameter, the five action signatures below carry **no** `now` argument — the same discipline Provisional Commitment pins for `place_hold` / `confirm` / `release` / `expire`.

At this layer `now` serves exactly one purpose: **stamping the `at` timestamp** on the Event Log entry each state-changing action journals ([Reserve], [Confirm Reservation], [Cancel Reservation], [Expire Reservation]). [Query Reservation] is read-only and stamps nothing.

**The composition adds no clock-bearing guard, and derives no deadline of its own.** The temporal rules of the reservation arc are Provisional Commitment's and are evaluated against the `now` injected at *that* constituent's seam: the hold window `expires_at` is a derived deadline computed once from the injected `now` and `duration` at `place_hold` and stored immutably; the `window-elapsed` guard on `confirm`/`release` and the `window-not-elapsed` guard on `expire` are pure functions of that stored deadline and the injected `now`, writing nothing when they fail. This composition surfaces both rejections unchanged (Invariant 4) and does not re-derive the window arithmetic. **Expiry and sweep semantics are inherited, not restated:** in Provisional Commitment a lapse is a *written* transition rather than a read-time inference — precisely because it has a side effect, returning the resource and, here, the pool slot — fired eagerly or lazily by the deployment's sweeper per the `expiry_sweep` configuration. [Expire Reservation] is the action that sweeper invokes; the composition owns neither the cadence nor the clock that triggers it (Edge cases — *Expiry sweeper boundary*).

**No stored eligibility flag.** The composition stores no derived "expired", "eligible", or "overdue" boolean, so nothing at this layer can lag the clock. The one marker the binding carries, `release ∈ {none, pending(…), released(…)}` — [Slot Released] names its `released(…)` value — is not a clock-derived projection but the record of a *committed fact*: `pending` written before the pool is touched, `released(…)` when the pool `release` returns, and, with the reconciliation, the exactly-once guard behind Invariant 2. Lapsed-ness is never stored here; it is Provisional Commitment's immutable `expires_at` compared against an injected `now`.

**One injected `now` per invocation — for this composition's own stamps.** Within a single state-changing call, one injected reading serves every timestamp this layer writes (the Event Log entry's `at`). It does **not** extend into the constituents: each constituent call is its own pipeline invocation with its own seam, and Provisional Commitment's signatures (`place_hold`, `confirm`, `release`, `expire`) accept no timestamp, so its window guard and transition stamps read the value injected at *its* seam. The journaled `at` and the commitment's own transition stamp are therefore two readings, and under seam-to-seam skew a sweeper can meet `window-not-elapsed` on a hold this layer would judge lapsed — the reason expiry is delegated wholly to the constituent rather than re-derived here, and ordering claims rest on Event Log insertion order rather than on comparing the two stamps. A deployment wanting one reading across all seams in a request must supply it as a host obligation; the spec does not promise it. Ids are likewise allocated at the constituents' own seams: `reservation_id` is the Provisional Commitment `id` (assigned from injected `id_t` at `place_hold`), `pool_id` comes from Capacity Constraint's `declare_pool`, `allocation_event_id` / `release_event_id` from its `allocate` / `release`, and the journal entry id from Event Log's append. This composition mints no id inside a transition and generates no cryptographic material — `parameters_digest` is likewise computed at the seam by the configured `digest_function` and injected as an explicit input (see Composition state and Configuration).

### Primitive policies

- **`idempotency_token`** — non-null, non-empty, within `token_max_length` bytes (`invalid-request`); opaque, byte-exact comparison. Validated at the composition layer before any constituent is consulted (inherited from Idempotent Reservation).
- **`pool_id`** — opaque, system-generated by Capacity Constraint's `declare_pool`. Must reference a known pool that is neither Closed nor Suspended at [Reserve]; otherwise the action surfaces `not-known` (unknown pool) or [Pool Closed] (a Closed *or Suspended* pool — no new reservations; step 3 maps both constituent rejections into this one code, the deliberate collapse the [Pool Closed] card states). Byte-identity equality as a map key.
- **`reservation_id`** — the opaque Provisional Commitment `id`. When supplied to [Confirm Reservation], [Cancel Reservation], or [Expire Reservation], must reference a reservation known to the composition (present in `reservation_to_pool`); otherwise `not-known`.
- **`resource`, `requester`, `duration`** — the Provisional Commitment `place_hold` tuple. Validated by Provisional Commitment's preconditions; the composition propagates its `invalid-request` and `resource-unavailable`.
- **`actor_ref`** — opaque actor identifier; at least one non-whitespace character, else `invalid-request`. Bound cryptographically via Actor Identity through the paired `credential`, and recorded on every Event Log entry.
- **`credential`** — opaque credential material consumed by `Actor Identity.attest`. Boundary well-formedness: non-null and non-empty, else `invalid-request` at step 1 — the shape check this layer makes; the content is never inspected here. **The attestation happens before any constituent call that commits, in every state-changing action** (*Authentication precedes commitment*, Action wiring), so a bad credential is refused *pre-state*: Actor Identity's `invalid-credential` is a guard rejection that fails before even its own store write, and this composition returns it as `rejected(invalid-credential)` with no pool allocation, no hold, no transition, and no journal entry. Its `invalid-request` arm (malformed credential material detected at attestation) surfaces the same way, as a clean `rejected(invalid-request)`. **This composition therefore enforces the seam at its own boundary**; an upstream credential pre-check is defence in depth, not a control it depends on. The compensation paths remain for the transient case — a `storage-failure` at the attestation or the journal — and are the backstop for a committed act's owed record, never, as they once were, the backstop for an unauthenticated caller taking a slot.

No primitive is case-sensitivity-normalized at the composition layer.

### Action wiring

The composition exposes five actions. Four are state-changing — each carries a required `idempotency_token`, attributes via Actor Identity, and journals to Event Log; the fifth, [Query Reservation], is a read-only pass-through. Every state-changing action follows the idempotency shape inherited from Idempotent Reservation: validate the token, consult `DuplicatePrevention.check`, replay the cached result on a matching `seen`, otherwise delegate to the constituents, record the outcome (success *or* rejection — the *cache-the-failure* rule), and `DuplicatePrevention.record`. The wiring below describes the `not-seen` (first-invocation) path; the idempotent-replay path is the shape just stated — Idempotent Reservation's heritage, but fully declared by this spec's own wiring rather than a dependency on the peer — and is not re-stated per action. Every constituent rejection is mapped — propagated, renamed, or surfaced as a new code — at the composition boundary. Event Log's `append` also declares an `invalid-payload` arm, against the instance's payload cap. *Foreclosed by construction* was the wrong argument for it — it was made about the intent, and the outcome is larger, the sweep's recovery entry larger still (§*An outcome is sized before the intent*). Every state-changing action therefore **sizes, at its validation step, the largest record the act can write** — the recovery outcome entry the sweep could land for it, with `recovery_candidates_cap` candidate ids and the caller's own `resource` / `requester` strings — against `journal_payload_cap` (Configuration), and refuses `rejected(invalid-request)` **before the intent** where it would not fit; the candidate sets the sweep writes are bounded by the same cap. A return of `invalid-payload` after that sizing is a composition defect — handled at the journal step exactly as a failed journal write (`recording-failure` at that step's position, with the action's recovery path) while being surfaced to the deployment as a defect, never as a distinct caller rejection. **Every `recording-failure` this composition exports carries its position** — `intent`: nothing committed, the act may be re-run (under the same token where the rejection was not cached, under a fresh one where it was); `outcome`: an act under this token reached, or may have reached, its commit, and it must not be re-run — the caller reads [Query Reservation] where it holds an id, otherwise waits for the sweep, whose resolution the same token then replays (§*A composition's own rejection arm carries the retry bit*).

#### `reserve`

```
reserve(
 pool_id,
 resource,
 requester,
 duration,
 actor_ref,
 credential,
 idempotency_token
) →
  reservation_id
 | rejected(
   invalid-request
  | invalid-credential
  | token-collision
  | not-known
  | pool-closed
  | pool-capacity-exceeded
  | resource-unavailable
  | recording-failure(intent | outcome)
  )
```

Takes one slot of `pool_id` and opens a provisional hold bound to it. The **capacity gate and the hold are bound**: the slot is allocated only if the hold is taken, and the hold is taken only if a slot was available.

Steps (first-invocation path):

1. Validate `idempotency_token`, `actor_ref`, `credential`, and the `place_hold` tuple per Primitive policies, and **size the envelope**: the largest journal entry this invocation can cause — the sweep's recovery entry for it, with `recovery_candidates_cap` ids and these `resource` / `requester` values — against `journal_payload_cap` (Action wiring preamble). Malformed token or args, or an envelope over the cap → `rejected(invalid-request)` (a malformed token is not cached — there is nothing to cache against). Stop.
2. Compute `parameters_digest` from the **business** call parameters — never `actor_ref` or `credential`, so a retry that must present freshly-minted credential material still matches (Composition state) — via the configured `digest_function` — at the seam, injected as an explicit input (Configuration; Composition state). `DuplicatePrevention.check(idempotency_token)`. On `seen`, replay per the inherited idempotency rule (matching `action_type = reserve` and `parameters_digest` → cached result; mismatch → `rejected(token-collision)`). On `not-seen`, **read the journal for this token before delegating** — `not-seen` proves the token was never `record`ed, not that no invocation ran under it: a crash between step 7's outcome landing and step 8's `record` leaves a completed reservation the constituent has never heard of, and a bare delegation would allocate and hold a second time for one token, a first reservation that is fully committed and that no leg compensates (§*Recovery commits under a declared service identity*, the re-entry tell). Query the Event Log through `journal_query_shape` for entries whose payload carries this `idempotency_token`. A **`reserve` outcome entry** naming the token, with the digest recomputed at the seam from its intent entry's business parameters equal to this call's → complete step 8 from it (the binding from `{reservation_id, pool_id}`, the cache from its `reservation_id`, and `record` the token) and return the `reservation_id` as a replay. A **`reserve_compensated` entry** naming the token — in its own `idempotency_token` for an in-line compensation, or among the `intent_candidates` of a sweep-written one, the membership read being `action = reserve_compensated` for this `pool_id` filtered composition-side (`journal_query_shape`) — → cache and `record` the rejection it records and return it, **populating no binding**: a compensated hold holds no slot and the map is the record of slots held (Composition state). The recorded rejection is the entry's own `reason` for an in-line compensation, and `rejected(recording-failure(outcome))` for a sweep-written one — the result the sweep records for every candidate token, since which candidate's act the compensated allocation was is not decidable and none of them holds a slot. A differing digest, or a token whose entries belong to another action → `rejected(token-collision)`. An **intent entry with no outcome and no compensation** beside it → `rejected(recording-failure(outcome))`, cached and recorded: an earlier invocation under this token may hold a slot, this one cannot tell and must not take a second, and the sweep is the one writer that resolves it (*Cross-store consistency under partial failure*, leg *(c)*) — the caller reserves afresh under a fresh token once the sweep has landed, and the same token replays the rejection. No trace → continue.
3. **Attest — the credential check, and the act's binding proof.** `Actor Identity.attest(action_ref = "reserve:" + idempotency_token, actor_ref, credential)` → `attestation_id` (or map: `invalid-credential` → `rejected(invalid-credential)`; `invalid-request` → `rejected(invalid-request)`; `storage-failure` → `rejected(recording-failure(intent))` — not cached and not recorded: the token stays `not-seen` and the same token retries the whole action). **Nothing has committed when this runs**, and Actor Identity's `invalid-credential` is a guard rejection that fails before any store write of its own, so an unverifiable credential refuses the reservation with nothing written anywhere — no attestation, no pool allocation, no hold (*Authentication precedes commitment*; Invariant 7). The `action_ref` is **per-invocation, not a bare kind token**: Actor Identity Invariant 2 binds a proof to the recorded action reference, so a token reused across every reservation would make all attestations of that kind mutually substitutable and bind the proof to a *category* rather than to an act. `idempotency_token` is required, per-invocation and byte-exact, so composing it costs no new id — this composition still mints none inside a transition (*Logic confinement*).
4. **Journal the intent:** append an Event Log entry `{action: reserve_intended, idempotency_token, pool_id, resource, requester, duration, attestation_id, actor_ref, at: now}` (or map `storage-failure` → `rejected(recording-failure(intent))`; nothing has committed and nothing is cached or recorded, so the caller retries the whole action under the same token — Event Log declares its `storage-failure` definitive, *the event does not land*; a deployment whose journal lands the append and still returns the failure has produced the bare intent step 2's read finds on that same-token retry, and step 2's deferral arm, not this one, is what the retry then lands, so the two arms compose rather than conflict). **The pool's and the reservation's `host_exclusion` sections are taken here, at the invocation's first write, and held through step 8** (Configuration): an invocation that stalls between this entry and step 5 and wakes after the sweep has resolved its intent must not allocate on a token the sweep has already cached and recorded, and the section is what stops it — step 5 runs only while the sections are held, and an invocation that finds them lost re-takes them and re-reads the journal for its token under them, adopting a `reserve_compensated` or recovery entry that names it (return the recorded rejection, allocate nothing) before it touches the pool. This entry is the marker-before-act: an intent entry with no matching outcome entry names an invocation that committed nothing, or committed and failed to journal, or died between — which is what the *Cross-store consistency under partial failure* recovery reads, and what previously had to be inferred from constituent state alone.
5. **Capacity gate — under the sections, pre-checked:** holding the token's, the pool's and the reservation's `host_exclusion` sections (re-taken if lost, the journal re-read for this token under them — *proceed as landed*: an entry already resolving the token means the sweep has been here, and the invocation returns that result and allocates nothing), `Capacity Constraint.allocate(pool_id, count=1, allocating_actor_ref=actor_ref)` → `allocation_event_id` (or map: `not-known` → `rejected(not-known)`; `over-capacity` → [Pool Capacity Exceeded]; `suspended`/`closed` → [Pool Closed]; `invalid-request` → `rejected(invalid-request)`; `storage-failure` → `rejected(recording-failure(intent))` — Capacity Constraint Invariant 14 promises no partial record under a `storage-failure` return, so nothing is held. On any rejection, cache it against the token, `record` the token, and stop — no hold is placed, no slot is held, and the intent entry left behind names an attempt that took nothing: it stands behind no allocation event and explains no slot of divergence (Invariant 1; check 1), and a later retry under this token replays the cached rejection rather than re-reading the journal).
6. **Place the hold:** `Provisional Commitment.place_hold(resource, requester, duration)` → `reservation_id` (or map: `invalid-request` → `rejected(invalid-request)`; `resource-unavailable` → `rejected(resource-unavailable)`; `storage-failure` → `rejected(recording-failure(intent))` — the position is `intent` because the compensation that follows leaves nothing standing. **On any rejection here, compensate the step-5 allocation:** `Capacity Constraint.release(pool_id, count=1, releasing_actor_ref=actor_ref)` — the slot was allocated but no hold took it, so it must be returned or it leaks — **and journal the compensation**: append a `reserve_compensated` Event Log entry `{action: reserve_compensated, idempotency_token, pool_id, reservation_id?, hold_resolution: none | released | expired, allocation_event_id, release_event_id, reason: <the rejection>, attestation_id, actor_ref, at: now}` — `reservation_id` absent and `hold_resolution = none` on this path, where no hold was placed; present, with the terminal transition taken, on the step-7 path —, appended **after** the compensating release returns (the release is a committed write on the pool's own append-only audit log and the journal entry an append — neither can be withdrawn, so nothing spans them; a crash between the two is the pool reconciliation leg's case, resolved by arithmetic, *Cross-store consistency under partial failure*), so the compensation is never an invisible act — it is what makes a failed [Reserve] distinguishable, in the journal, from a leak (Generation acceptance check 3's compensation arm; the forensics procedure reads it). Then cache the rejection and stop. The compensating release is the only path where the composition releases a slot without a terminal commitment transition, and it exists precisely to preserve allocation coherence across a partial [Reserve]).
7. **Attribute and journal:** record an Event Log entry `{action: reserve, idempotency_token, reservation_id, pool_id, prior_state: none, new_state: Held, allocated_before, allocated_after, allocation_event_id, attestation_id, actor_ref, at: now}` — `allocated_before` / `allocated_after` copied from the allocation event `allocation_event_id` names, read through `pool_event_read` (Composes — Event Log) — `at` stamped from the **seam-injected `now`** for this invocation, a reading of this layer's own seam and distinct from the one the step-6 `place_hold` delegation consumed at *its* seam (per-seam readings are never shared or compared — *Logic confinement*) — attributed via `Actor Identity` under `credential`. If the journal write fails after steps 5–6 succeeded → `rejected(recording-failure(outcome))` — the position telling the caller a slot and a hold **exist** under this token and the act must not be re-run under a fresh one until the journal shows the compensation (§*A composition's own rejection arm carries the retry bit*); the rejection is cached and the token recorded, so the same token replays it; **`reservation_to_pool` is not populated** until the event lands (audit-first discipline), so a reservation never becomes resolvable without its [Reserve] event journaled. **The orphan is recoverable, and the recovery is prescribed:** the allocated slot and Held commitment with no journaled event and no binding cannot be resolved by any caller action (all three resolution actions would return `not-known`), so the implementation must **compensate, not complete** — and the hold-side compensation **branches on the window**: `Provisional Commitment.release(reservation_id)` while the hold's window is still open, `Provisional Commitment.expire(reservation_id)` once it has lapsed (the constituent refuses `release` on a lapsed hold with `window-elapsed` — a rejection that can never clear, so a release-only retry loop would spin forever; both transitions are terminal and both free the resource). Then return the slot (`Capacity Constraint.release(pool_id, count=1, ...)`) and journal a `reserve_compensated` entry (as in step 6, appended after the pool release — here carrying the `reservation_id` and `hold_resolution: released | expired`, so the compensated hold is named in the journal and check 3 can tell it from a leak) once the journal recovers — the caller's cached `recording-failure` result then stays truthful (their retry replays the rejection; the reservation never becomes live), and the reservation id, never having been returned, dangles nowhere. Until the compensation lands, the orphan is surfaced as a high-priority finding per the *Cross-store consistency under partial failure* edge case. **The compensation's own arms are partitioned, not looped, and every retry has a terminus:** each transient retry below runs at most `outcome_retry_attempts` times (Configuration) inside the invocation, under the reservation's and the pool's `host_exclusion` sections, after which the invocation returns its cached `rejected(recording-failure(outcome))` and yields the orphan to the sweep — the invocation and the sweep are never both writers for one act (§*A compensator is exclusive*). `Provisional Commitment.release` / `expire` — `storage-failure` → retry (transient); `window-elapsed` on `release` → take the `expire` branch; `window-not-elapsed` on `expire` → take the `release` branch; `not-held` → the hold is already terminal (a concurrent path resolved it) — proceed to the pool release; `not-known` → an internal-consistency finding, escalated, nothing further run. `Capacity Constraint.release` — `storage-failure` → retry; `over-release` → the slot was already returned (a double compensation the reconciliation's arithmetic would have refused) — a finding, never retried; `not-known` / `invalid-request` → findings. The journal append — `storage-failure` → retry. Where the invocation is gone or has spent its attempts, the sweep performs the compensation under the service identity behind a `recovery_intended` entry (Configuration), re-reading under the same sections whether the compensation already landed before it writes.
8. Populate state only after the event lands: `reservation_to_pool[reservation_id] = {pool_id, release: none}`; cache `token_results[idempotency_token] = (reserve, digest, reservation_id)`; `DuplicatePrevention.record(idempotency_token)`. A crash before the `record` lands is the seam step 2's journal read closes on the retry, and the sweep closes for a token nobody retries.
9. Return `reservation_id`.

#### `confirm_reservation`

```
confirm_reservation(reservation_id, actor_ref, credential, idempotency_token) →
  ok
 | rejected(invalid-request | invalid-credential | token-collision | not-known | not-held | window-elapsed | recording-failure(intent | outcome))
```

Confirms a held reservation into a firm booking. **The slot is not released** — a Confirmed reservation keeps its pool unit (the binding allocation persists), so `allocated` is unchanged. This is the action whose `window-elapsed` rejection is the composition's *no-confirm-without-active-hold* guarantee.

Steps (first-invocation path): validate; `check`; on `not-seen`: **read the journal for this token as at [Reserve] step 2** (a `confirm_reservation` outcome naming the token, digest matching → cache, `record`, replay `ok`; a bare `confirm_intended` → `rejected(recording-failure(outcome))`, cached and recorded, the sweep's leg *(d)* resolving it; no trace → continue); resolve `reservation_id` in `reservation_to_pool` (absent → `rejected(not-known)`); **attest** — `Actor Identity.attest(action_ref = "confirm_reservation:" + idempotency_token, actor_ref, credential)` → `attestation_id`, mapping its arms as at [Reserve] step 3, with nothing committed on any of them (*Authentication precedes commitment*); journal the intent entry `{action: confirm_intended, idempotency_token, reservation_id, pool_id, attestation_id, actor_ref, at: now}` (a `storage-failure` → `rejected(recording-failure(intent))`, uncached, as at [Reserve] step 4); then `Provisional Commitment.confirm(reservation_id)` → `ok` (or map: `not-known` → `rejected(recording-failure(intent))` — internal-consistency anomaly, the composition knows the id but Provisional Commitment does not; `not-held` → `rejected(not-held)`; `window-elapsed` → `rejected(window-elapsed)` — the hold lapsed before confirmation, and the slot it held is the expiry sweeper's to return, not this action's; `storage-failure` → `rejected(recording-failure(intent))`, nothing transitioned, uncached); journal `{action: confirm_reservation, idempotency_token, reservation_id, pool_id, prior_state: Held, new_state: Confirmed, allocated_before, allocated_after, attestation_id, actor_ref, at: now}` — `allocated_before = allocated_after`, one read of `Capacity Constraint.query(pool_id).allocated` — a single constituent call, atomic under the pool's own per-call serialization — carried on the same schema every outcome entry uses as a witness that the slot stayed counted, not as a chain link: the replay chains only entries that cite a pool event id (Composes — Event Log) — `at` stamped from the **seam-injected `now`** for this invocation, a reading of this layer's own seam and distinct from the one the `confirm` delegation's window guard consumed at the constituent's seam (per-seam readings are never shared or compared — *Logic confinement*) — attributed via Actor Identity; cache and `record`. Return `ok`. (The slot stays allocated; no `Capacity Constraint` call is made — Confirmed consumes the unit in the binding allocation.)

**The confirm pair — transition plus outcome entry — and what happens when it splits.** `confirm` is irreversible (Confirmed is absorbing), so a `storage-failure` on the outcome append after the transition committed cannot be compensated the way a partial [Reserve] is: the reservation *is* Confirmed, and until the entry lands the journal's last word on it says Held. The arm is landed as follows. Return `rejected(recording-failure(outcome))`, carrying `stage: post-commit` in the rejection data so the caller knows the confirmation stands and confirms it through [Query Reservation]; **cache the rejection and `record` the token** — the cache-the-failure rule applies, and recording is what keeps a retry from re-delegating into `confirm`'s `not-held` on the caller's own committed act. The implementation then owes the **late outcome write**: it retries the append at most `outcome_retry_attempts` times inside the invocation (the transient arm only — the retry partition at [Reserve] step 7), then yields the write to the sweep's leg *(d)* — one writer per entry, the sweep taking the reservation's `host_exclusion` section and re-reading for an existing outcome under it (§*A compensator is exclusive*) — the late entry carrying the intent entry's `attestation_id` (the invocation's binding proof, already made; no second attestation is taken) and `recovery = true`, so an auditor distinguishes it from an entry written in-line. Detection is durable and needs no process memory: a `confirm_intended` entry with no `confirm_reservation` outcome beside it, against a Provisional Commitment record in Confirmed, is the owed write (the residual sweep's leg *(d)*, *Cross-store consistency under partial failure*), and every late write is preceded, **under the reservation's `host_exclusion` section**, by a traversal for an existing outcome naming the same `idempotency_token` — the look-then-append is re-read under the section, never before it. The pair is completed by the late write like the slot-returning pair, and the reason is the same in both: a store answers the question directly — here the Provisional Commitment record, there the pool's own count — so no transaction is needed and none is claimed.

#### `cancel_reservation`

```
cancel_reservation(reservation_id, actor_ref, credential, idempotency_token) →
  ok
 | rejected(invalid-request | invalid-credential | token-collision | not-known | not-held | window-elapsed | recording-failure(intent | outcome))
```

Cancels a held reservation and **returns its slot to the pool, in order, exactly once**.

Steps (first-invocation path): validate; `check`; on `not-seen`: **read the journal for this token as at [Reserve] step 2** (a `cancel_reservation` outcome — in-line or `recovery = true` — naming the token, digest matching → cache, `record`, replay `ok`; a bare `cancel_intended` → `rejected(recording-failure(outcome))`, cached and recorded, the sweep's leg *(a)* resolving it; no trace → continue); resolve `reservation_id` in `reservation_to_pool` (absent → `rejected(not-known)`); resolve `pool_id`; **attest** — `Actor Identity.attest(action_ref = "cancel_reservation:" + idempotency_token, actor_ref, credential)` → `attestation_id`, arms as at [Reserve] step 3, nothing committed on any of them (*Authentication precedes commitment*); journal the intent entry `{action: cancel_intended, idempotency_token, reservation_id, pool_id, attestation_id, actor_ref, at: now}` (a `storage-failure` → `rejected(recording-failure(intent))`, uncached, as at [Reserve] step 4). **The attestation and its intent entry stand before the terminal steps** — the intent is the credential gate and the recovery marker. Then, **in this order, none of it inside a transaction** — the terminal transition is absorbing, the pool release is an append on the pool's own audit log, and the journal entry is an append, so no store offers a rollback and none is claimed (*Cross-store consistency under partial failure*):

1. `Provisional Commitment.release(reservation_id)` → `ok` (or map: `not-known` → `rejected(recording-failure(intent))`; `not-held` → `rejected(not-held)` — the reservation is already terminal: Confirmed, Released, or Expired; a cancel of a Confirmed reservation is out of scope here — un-booking a firm reservation is handled by a Reversal pattern, Edge cases; `window-elapsed` → `rejected(window-elapsed)` — the hold lapsed before the cancel arrived, the constituent refuses `release` on a lapsed hold, and the resolution belongs to [Expire Reservation] (the sweeper's action returns the slot; the caller has nothing further to do); `storage-failure` → `rejected(recording-failure(intent))`, nothing transitioned, uncached, the same token retries). On any rejection nothing further runs; the guard rejections are cached against the token, and the intent stands as the record of the attempt — **and of nothing more**: the reconciliation admits a `cancel_intended` as an unjournaled return only where no slot-returning outcome names the reservation at all and the record's terminal state is Released, the state this action's transition writes, so a cancel refused `not-held` because another token already returned the slot, or `window-elapsed` because the sweeper's expiry owns it, is never compensated as a return that was begun (*Cross-store consistency under partial failure*, leg *(a)*).
2. **Mark the return owed:** durably set `reservation_to_pool[reservation_id].release = pending(idempotency_token, attestation_id)` — the composition's own marker that a slot return is in flight, written before the pool is touched (Composition state) — and take the pool's `host_exclusion` section here, the reservation's having been taken at the intent entry; both are held through step 4. A store refusal here → `rejected(recording-failure(outcome))`, cached and recorded: the reservation is terminal, its slot not yet returned, and the reconciliation leg owes the return (the intent entry and the terminal record are the evidence; the marker is what would have made it cheaper to find).
3. **Pre-check under the sections, then release.** An invocation that stalled between step 2 and this step and lost its lease has yielded: it re-takes the reservation's and the pool's sections before anything else and re-reads, under them, the marker and the journal for a slot-returning outcome — in-line or `recovery = true` — naming this reservation. One found means the sweep's leg *(a)* already returned the slot: **proceed as landed** — set the marker `released(…)` from it if it still reads `pending`, release nothing, skip step 4, cache `ok` and `record` the token. None found: `Capacity Constraint.release(pool_id, count=1, releasing_actor_ref=actor_ref)` → `release_event_id` (or map: `not-known` → `rejected(recording-failure(outcome))`; `over-release` → `rejected(recording-failure(outcome))` — an internal-consistency anomaly meaning the pool as a whole would over-drain, which the reconciliation's arithmetic forecloses per reservation; `invalid-request`/`storage-failure` → `rejected(recording-failure(outcome))` — on `storage-failure` the release **may or may not have committed**, the token gives no way to tell, and the reconciliation leg is what decides, by the pool's own count, never by a blind retry; every arm here is cached and recorded, the reservation being terminal). Then durably set `release = released(release_event_id)` and take `allocated_before` / `allocated_after` from the release event that id names (`pool_event_read`).
4. Journal `{action: cancel_reservation, idempotency_token, reservation_id, pool_id, prior_state: Held, new_state: Released, allocated_before, allocated_after, release_event_id, attestation_id, actor_ref, at: now}` — `at` stamped from the **seam-injected `now`** for this invocation, a reading of this layer's own seam and distinct from the one the step-1 `release` delegation consumed at the constituent's seam (per-seam readings are never shared or compared — *Logic confinement*) — attributed via Actor Identity. A `storage-failure` here leaves the slot returned and the marker `released(…)`, the outcome owed: the append is retried at most `outcome_retry_attempts` times inside the invocation, then `rejected(recording-failure(outcome))` carrying `stage: post-release`, cached and recorded, and the reconciliation leg lands the late outcome entry from the marker (`recovery = true`, the intent's `attestation_id`) under the reservation's `host_exclusion` section — never both.

Cache and `record`. Return `ok`. **What makes the return exactly-once is not a transaction — it is the marker plus the pool reconciliation** (*Cross-store consistency under partial failure*): a crash anywhere in steps 1–4 leaves a terminal record, possibly a `pending` marker, possibly a pool release event, and no outcome entry, and the reconciliation leg resolves *whether* the release landed from the pool's own `allocated` against the journaled live set under the pool's `host_exclusion` section — the count is the second source the earlier "one atomic commit" requirement was standing in for, and unlike that requirement it is one the stores can actually supply.

#### `expire_reservation`

```
expire_reservation(reservation_id, actor_ref, credential, idempotency_token) →
  ok
 | rejected(invalid-request | invalid-credential | token-collision | not-known | not-held | window-not-elapsed | recording-failure(intent | outcome))
```

The action an expiry sweeper invokes on a held reservation whose window has elapsed: it drives the Provisional Commitment `expire` transition and **returns the slot to the pool, in order, exactly once**, exactly as [Cancel Reservation] does, differing only in the constituent transition (`expire` rather than `release`) and the `window-not-elapsed` guard.

Steps (first-invocation path): validate; `check`; on `not-seen`: read the journal for this token as at [Reserve] step 2 (an `expire_reservation` outcome naming the token → replay `ok`; a bare `expire_intended` → `rejected(recording-failure(outcome))`, cached and recorded; no trace → continue); resolve `reservation_id` and `pool_id`; **attest** — `Actor Identity.attest(action_ref = "expire_reservation:" + idempotency_token, actor_ref, credential)` → `attestation_id`, arms as at [Reserve] step 3, nothing committed on any of them; journal the intent entry `{action: expire_intended, idempotency_token, reservation_id, pool_id, attestation_id, actor_ref, at: now}`. **The attestation and its intent entry stand before the terminal steps.** Then, in [Cancel Reservation]'s order and with its arms — the transition, the `pending` marker, the pool release, the `released(…)` marker, the outcome entry, none of it inside a transaction: durably set `release = pending(idempotency_token, attestation_id)` and take the pool's section; under the sections, pre-check as at [Cancel Reservation] step 3 (a slot-returning outcome already naming the reservation → proceed as landed, release nothing); otherwise `Capacity Constraint.release(pool_id, count=1, ...)` → `release_event_id`, set `release = released(release_event_id)`, the entry's `allocated_before` / `allocated_after` copied from that release event (`pool_event_read`); journal `{action: expire_reservation, idempotency_token, reservation_id, pool_id, prior_state: Held, new_state: Expired, allocated_before, allocated_after, release_event_id, attestation_id, actor_ref, at: now}` — `at` stamped from the **seam-injected `now`** for this invocation, a reading of this layer's own seam and distinct from the one the `expire` delegation's `window-not-elapsed` guard consumed at Provisional Commitment's seam (per-seam readings are never shared or compared — *Logic confinement*) — attributed via Actor Identity. Cache and `record`. Return `ok`.

#### `query_reservation`

```
query_reservation(reservation_id) →
  {state, pool_id, slot_held} | rejected(not-known)
```

Read-only. **No Event Log entry is produced** — a read changes no state. Resolves `reservation_id` in `reservation_to_pool` (absent → `rejected(not-known)`), reads the commitment's current state from Provisional Commitment, and reports `{state, pool_id, slot_held = (state ∈ {Held, Confirmed} and release = none)}`. The second conjunct is redundant in steady state — Invariant 2 keeps a Held/Confirmed reservation's slot unreleased — and is kept deliberately as a conservative read guard across the recovery windows this spec names, where the belt-and-braces conjunction answers `false` rather than overstating a slot. Callers consume this to learn whether a reservation is live and holds a slot.

### The load-bearing wiring decision — allocation coherence

The composition's structural reason to exist: **the pool's `allocated` total equals the number of reservations in a slot-holding state (Held or Confirmed) bound to that pool, at every instant of quiescence — so the pool never oversells and never strands a slot.**

**Two senses of "terminal", named so that every test on this page can say which it means.** Provisional Commitment's terminal states are *constituent-terminal*: Confirmed, Released and Expired are all absorbing (its Invariant 3), and a reservation in any of them never transitions again. Only two of them are *slot-returning*: Released and Expired give the pool slot back; **Confirmed keeps it** — a confirmed reservation is a firm booking that consumes the unit for as long as it stands. Every stranded-slot test on this page — Invariant 2, Generation acceptance check 3, the residual detection sweep, the inventory-leak forensics — is scoped to the **slot-returning terminals**, Released and Expired: a reservation there whose return is unjournaled past the completion bound and unreleased by the pool's count is a stranded slot; a Confirmed reservation with `release = none` is the correct steady state, not a finding. Where the page says "terminal transition" of an action it means the slot-returning one [Cancel Reservation] and [Expire Reservation] drive; where it cites Provisional Commitment's absorption it means the constituent sense.

*Principle.* A reservation system must, from the pool count alone, never confirm more reservations than capacity and never lose a freed slot. Structurally that means the pool's running total and the live-reservation set must move together: a reservation enters the live set exactly when it takes a slot, and leaves it exactly when its slot is returned, with the counter tracking that membership.

*Likely objection.* Capacity Constraint already guarantees `allocated ≤ capacity` (Invariant 4), and Provisional Commitment already owns the reservation state machine. Why not let the caller `allocate` on `place_hold` and `release` on the terminal transition itself — why does the binding need to be the composition's job?

*Mechanism that resolves it.* Because neither constituent knows about the other, and the seam between them is exactly where coherence breaks. Capacity Constraint tracks a fungible count with *no per-allocation identity* — it cannot, by itself, know that *this* `release` corresponds to *that* expired hold, or prevent a slot being released twice for one reservation; its own spec defers per-allocation identity to the composing pattern. Provisional Commitment owns per-reservation identity and the Held → terminal transitions but has *no notion of a pool* — its `release`/`expire` decrement nothing. A caller wiring the two by hand re-implements the binding per call site, and the first site that releases a slot for a reservation that already lapsed (double-release → count below truth), or transitions a hold terminal without releasing the slot (leak → count above truth), or confirms a hold whose slot was already returned by an expiry sweep (oversell), breaks coherence silently. The composition closes this by owning the `reservation_to_pool` binding with its tri-state `release` marker ([Slot Released] its `released(…)` value): [Reserve] allocates, then holds, with a compensating release if the hold fails (Action wiring step 6); [Confirm Reservation] keeps the slot (Confirmed consumes the unit); [Cancel Reservation] and [Expire Reservation] release the commitment and then the pool slot, in order, with the `release` marker and the pool reconciliation guaranteeing the pool `release` happens exactly once — **an earlier revision required the transition, the pool release and the journal entry to commit as one atomic trio, and no constituent could honor that:** the transition is absorbing, the pool release is an append on the pool's own audit log, and the journal entry is an append, so a rollback of any of them was an undeclared capability, and a journal entry rolled back after it had landed was a false record; and the confirm-within-window guarantee (Provisional Commitment Invariant 7, surfaced as `window-elapsed`) forecloses confirming a slot an expiry already returned. The binding is what makes `allocated` a faithful image of the live-reservation set.

*Result.* Allocation coherence is structural. An auditor (or the pool's own `query`) can read `allocated` and trust it equals the count of live reservations against the pool; the system cannot oversell (every [Reserve] gated on `allocate`), cannot strand a slot (every slot-returning transition — Released or Expired — releases, exactly once, and Confirmed keeps its slot by design), and cannot confirm a lapsed hold (the window guard). The three failure modes that define reservation bugs — oversell, leak, double-release — are each foreclosed by a named mechanism, not avoided by convention.

## Composition-level invariants

These invariants emerge from the composition. None belongs to a single constituent; each requires two or more working together to hold.

- **Invariant 1 — Allocation coherence (load-bearing; safety + liveness).** *Safety — at quiescence:* for every pool, `Capacity Constraint.query(pool_id).allocated` equals the number of reservations bound to that pool (in `reservation_to_pool`) whose Provisional Commitment state is Held or Confirmed, whenever no [Reserve] against the pool is in flight and no compensation is owed. *Liveness — every divergence is a named window that closes:* the equality is knowingly false inside exactly three windows, each declared by the wiring and each converging — (i) between step 5's `allocate` and step 6's `place_hold`, where the slot is counted and no reservation yet exists; (ii) between step 6's hold and step 7's outcome entry, where the reservation is Held but unbound and unjournaled, so the count exceeds the bound live set by one; and (iii) while a compensation is owed after either seam failed. Windows (i) and (ii) close when the outcome entry lands or the compensation does; (iii) closes when the compensation lands — *Diverged(pool) ↝ Coherent(pool)* under the compensation obligation of Edge cases (b), which is the eventuality's carrier. **Every window is keyed on an allocation event of the pool's own audit log, never on an intent alone:** an unmatched `reserve_intended` behind which no allocation event stands — refused at step 5, or dead before the gate — holds zero slots and explains none, and a window keyed on it would excuse one slot of divergence for as long as the intent survives, which is forever. A divergence not accounted for by an allocation event that neither a `reserve` outcome nor a `reserve_compensated` entry names, nor by a return the reconciliation still owes, is the violation. *Defended in-line:* [Reserve] increments the pool (`allocate`) exactly when it places a hold (and compensates with a `release` if the hold fails, step 6); [Confirm Reservation] leaves both the live-set membership and the counter unchanged (Held → Confirmed is still slot-holding); [Cancel Reservation] and [Expire Reservation] remove the reservation from the live set (Held → terminal) and then decrement the counter (`release`), in that order, the reconciliation closing any crash between the two. No other action touches the pool. *Rests on:* Capacity Constraint Invariants 4–5 (the counter arithmetic) **under that atom's own named host obligations, all of which this composition inherits as deployment obligations rather than re-deriving** — serializable per-pool execution of each call (surfaced in Edge cases — *Concurrency*), overflow-safe integer arithmetic, and crash-atomic multi-record writes — with system-wide id uniqueness cited where it lives, Capacity Constraint Invariant 13 — the pool's persisted audit log read through `pool_event_read`, and the multi-call sections and the journal's survival across a crash as this composition's own declared host obligations (`host_exclusion`, `journal_durability`, Configuration), Provisional Commitment Invariants 1, 3 (state exclusivity and terminal absorption), and the ordered terminal steps with their `release` marker and the **pool reconciliation leg** (Edge cases — *Cross-store consistency*), which resolves every crash between the terminal transition and the outcome entry from the pool's own count under the per-pool `host_exclusion` section — the second source that replaces the transaction an earlier revision required and no store could provide. This is the invariant the formal model checks (the Ledger's `formal:` line).

- **Invariant 2 — Slot returned at most once.** For every reservation, the pool `release` that returns its slot is committed at most once across its lifetime. *Defended in-line:* the `release` marker on `reservation_to_pool[reservation_id]` is set `pending(…)` before the terminal `release` against the pool is called and `released(release_event_id)` — [Slot Released] — when it returns, and [Cancel Reservation]/[Expire Reservation] only release for a reservation transitioning *out of* Held — Provisional Commitment's single-resolution guarantee (its Invariant 2: exactly one terminal transition commits, even under race) means a reservation reaches a terminal state once, and its terminal absorption (Invariant 3) means it never leaves, so the slot-returning transition fires once. *Rests on:* Provisional Commitment Invariants 2 and 3, the `release` marker ([Slot Released] is its `released(…)` value — read as a precondition by the reconciliation leg, which never releases for a reservation the marker or the journal shows returned), and the pool reconciliation's arithmetic, which releases exactly the pool's unlanded returns and never more, with **one writer per return** — the invocation until `outcome_retry_attempts` is spent, the sweep thereafter, both under the reservation's `host_exclusion` section — over a journal that survives the crash under `journal_durability` (Edge cases, *Cross-store consistency*). A double-release (count driven below the live-set size) is foreclosed structurally; the constituent's `over-release` rejection fires only when the *whole pool* would over-drain, so it is a pool-level sanity arm, not a per-reservation guard — the marker and the reconciliation, not that rejection, are what carry this invariant.

- **Invariant 3 — Confirmed reservations never exceed capacity.** The count of Confirmed reservations against a pool never exceeds the pool's `capacity`. *Rests on:* Invariant 1 (allocation coherence — Confirmed reservations are in the slot-holding set counted by `allocated`) plus Capacity Constraint Invariant 4 (`allocated ≤ capacity`). Because every Confirmed reservation holds a slot counted in `allocated`, and `allocated ≤ capacity`, the Confirmed count is bounded by capacity. This is the *no-oversell* guarantee in the form a booking operator states it.

- **Invariant 4 — No confirmation of a lapsed hold.** A reservation is confirmed only while its hold window is open; a hold whose window has elapsed cannot be confirmed and is resolvable only by [Expire Reservation]. *Defended in-line:* [Confirm Reservation] maps Provisional Commitment's `window-elapsed` rejection straight through. *Rests on:* Provisional Commitment Invariant 7 (confirmation within the window). This is what prevents confirming a slot that an expiry sweep has already returned to the pool — the coherence guard at the confirm/expire race.

- **Invariant 5 — Idempotent reservation actions.** For any `idempotency_token` within the Duplicate Prevention window, repeated [Reserve]/[Confirm Reservation]/[Cancel Reservation]/[Expire Reservation] calls with matching `parameters_digest` return the same response and invoke the constituents at most once; reuse of a token across a different `action_type` or parameters is `token-collision`. *Rests on:* **this composition's own wiring and its wired constituent** — the per-action idempotency shape (validate → `check` → replay-or-delegate → cache → `record`), the `token_results` element caching every outcome (the cache-the-failure rule), Duplicate Prevention's membership and single-recording invariants (a token is recorded once; re-recording does not extend the window), and the per-token serialization obligation (Edge cases — *Concurrency*) — **all under Duplicate Prevention's inherited host obligations (Composes), exactly as Invariant 1 is conditioned on the pool's**: a durable, highly-available recorded-set store, fail-closed `check` handling, and cache-then-record durability before the result returns; a window miss traceable to a violated obligation is a deployment finding against the obligation, not a disproof of this invariant. The Idempotent Reservation precursor is the *heritage* of this shape — its Invariants 1–4 and 8 are the same claims over the narrower surface — cited as provenance, not as a load-bearing dependency on a non-wired peer: everything Invariant 5 needs is declared by this spec and its own constituents. Idempotency is what makes the coherence guarantees hold *under retry*: a retried [Reserve] does not take a second slot.

- **Invariant 6 — Every state change is attributed and journaled.** Every **committed** state change produces, **at quiescence**, exactly one **outcome** Event Log entry naming the reservation, the pool, the prior and new state, the pool arithmetic, the acting actor, and — the field that makes this claim checkable rather than asserted — the **`attestation_id`** returned by that invocation's `Actor Identity.attest` call, plus one **intent** entry preceding it carrying the same `attestation_id`; an invocation a constituent guard refused leaves its intent entry unmatched, which is the record of an attempt and not a gap (Composes), and read-only queries produce neither. An auditor reads an entry, takes its `attestation_id`, and calls `Actor Identity.verify` against it: the attribution is *witnessed*, not narrated. An outcome entry whose `attestation_id` names no attestation, or whose attestation does not verify against the entry's own composed `action_ref`, is a conformance failure. *Rests on:* Event Log's append-only total order under the deployment's `journal_durability` obligation (the atom's own durability is *to the extent the deployment supplies* it) and Actor Identity's `attest` and `verify`; the audit-first ordering in [Reserve] (the binding is not populated until the event lands), the ordered terminal steps in the two slot-returning actions, and the late-outcome-write obligation on the confirm pair and on the slot-returning pair — the windows in which a committed change is journaled after the fact, surfaced meanwhile and closed by a `recovery = true` entry carrying the invocation's own `attestation_id`, paired to its intent by the `idempotency_token` and `attestation_id` both entries carry (the per-invocation key: the attestation is minted once per acting invocation, and a replay mints none). The reservation lifecycle is reconstructable from the Event Log alone at quiescence.

- **Invariant 7 — Constituent invariants preserved.** All invariants of Provisional Commitment (10), Capacity Constraint Enforcement (14), Duplicate Prevention, Event Log, and Actor Identity hold over their respective instances. The composition never bypasses a constituent precondition; constituent rejections flow through, mapped, and are cached against the idempotency token.

- **Invariant 8 — Authentication precedes commitment.** No constituent call that commits is reached on any path before this composition's caller has presented a credential that validates against the actor registry's public material for the supplied `actor_ref`. The mechanism is the `Actor Identity.attest` call that opens every state-changing action — before `Capacity Constraint.allocate` and `Provisional Commitment.place_hold` at [Reserve], before `Provisional Commitment.confirm` at [Confirm Reservation], and before the terminal steps at [Cancel Reservation] and [Expire Reservation]. A slot is therefore never taken, confirmed, released, or expired on an unverified actor's asserted authority; `invalid-credential` is a pre-state refusal with nothing written, since Actor Identity's own guard fails before even its store write.

  **The `action_ref` binds the proof to the act, not to a category.** It is composed per-invocation as `"<action>:<idempotency_token>"`, because Actor Identity Invariant 2 verifies a proof against its recorded action reference: a bare kind token shared by every reservation would make all attestations of that kind mutually substitutable, and the attribution claim would remain unearned even with the call wired. The token is required, per-invocation and byte-exact, so nothing new is minted and this composition still mints no id inside a transition.

  **What this does and does not establish:** a successful attestation establishes that material matching the actor's registered verifier was presented at that instant, and leaves a proof an auditor can re-verify. It does *not* establish that the presenter *is* that actor (a stolen credential validates), that the presentation is bound to a channel or session, or that it cannot be replayed — and it establishes nothing about *authorization*: whether this actor was entitled to take or release a slot is not gated here, and this composition composes no Permissions instance. *Rests on:* Actor Identity's `attest` guard ordering (its `invalid-credential` precedes any store write) and Event Log's append-only order. *Defended in-line:* the ordering is visible in every action's wiring, and Generation acceptance check 6 tests it from the records alone.

Allocation coherence (Invariant 1) with slot-returned-at-most-once (Invariant 2) gives the *no-leak/no-double-release* property — the pool count is a faithful image of the live set. Never-exceed-capacity (Invariant 3) with no-confirmation-of-a-lapsed-hold (Invariant 4) gives the *no-oversell* property across the confirm/expire race. Idempotency (Invariant 5) makes both hold under retry; attribution-and-journaling (Invariant 6) makes the whole arc records-reconstructable; preserved constituent invariants (Invariant 7) are the floor the emergent guarantees stand on.

## Examples

### Walkthrough — event ticketing against a bounded pool

A venue sells a 2-seat VIP (very important person — premium) tier as a Capacity Constraint pool `pool_vip` with `capacity = 2`. The composition runs with a 5-minute idempotency window and an eager expiry sweep.

1. **Reserve (buyer A).** `reserve(pool_vip, resource="vip-tier", requester="buyer_a", duration=10m, actor_ref="checkout_svc", credential=<checkout_svc>, idempotency_token=tok_a1) → reservation_id = rsv_001`. Internally: `Capacity Constraint.allocate(pool_vip, 1, ...)` → `allocated: 0 → 1`; `Provisional Commitment.place_hold("vip-tier", "buyer_a", 10m)` → `rsv_001` (Held); Event Log records [Reserve]; `reservation_to_pool[rsv_001] = {pool_vip, release: none}`. `query(pool_vip).allocated = 1`.
2. **Reserve (buyer B).** `reserve(pool_vip, ..., requester="buyer_b", ..., idempotency_token=tok_b1) → rsv_002`. `allocated: 1 → 2`. The pool is now full.
3. **Reserve (buyer C) — capacity gate fires.** `reserve(pool_vip, ..., requester="buyer_c", ..., idempotency_token=tok_c1)` → `Capacity Constraint.allocate(pool_vip, 1, ...)` → `over-capacity` → `rejected(pool-capacity-exceeded)`. No hold is placed; `allocated` stays 2. Buyer C is not oversold. (Invariant 3.)
4. **Retry buyer A's reserve (network drop).** `reserve(pool_vip, ..., idempotency_token=tok_a1)` → `DuplicatePrevention.check(tok_a1) → seen`; cached `(reserve, digest_a, rsv_001)` replayed → returns `rsv_001`. No second `allocate`; `allocated` stays 2. (Invariant 5.)
5. **Confirm (buyer A).** `confirm_reservation(rsv_001, actor_ref="checkout_svc", credential=<…>, idempotency_token=tok_a2) → ok`. `Provisional Commitment.confirm(rsv_001)` → Confirmed (within window); the slot is *kept* — no pool `release`. `allocated` stays 2. (Confirmed consumes the unit.)
6. **Expiry (buyer B lets the hold lapse).** Ten minutes pass; the sweep fires `expire_reservation(rsv_002, actor_ref="sweeper", credential=<sweeper>, idempotency_token=tok_sweep_b) → ok`. `Provisional Commitment.expire(rsv_002)` → Expired; `Capacity Constraint.release(pool_vip, 1, ...)` → `allocated: 2 → 1`; `release = released(…)`; Event Log records [Expire Reservation]. The slot is returned exactly once. (Invariants 1, 2.)
7. **Reserve (buyer C, retry with a fresh token).** Now `reserve(pool_vip, ..., requester="buyer_c", idempotency_token=tok_c2)` → `allocate` → `allocated: 1 → 2` → `rsv_003` Held. Buyer C gets the slot buyer B let lapse. The pool count tracked the truth throughout.

### Cancellation returns the slot

Buyer A cancels before confirming (in a variant where rsv_001 is still Held): `cancel_reservation(rsv_001, ..., idempotency_token=tok_cancel_a) → ok`. `Provisional Commitment.release(rsv_001)` → Released; `Capacity Constraint.release(pool_vip, 1, ...)` → `allocated` decrements; `release = released(…)`. The slot returns to the pool in order with the cancellation. (Invariants 1, 2.)

### Partial-reserve compensation

A [Reserve] allocates a slot (`allocated: 1 → 2`) but `Provisional Commitment.place_hold` then returns `resource-unavailable` (the specific resource was taken between the capacity gate and the hold). The composition compensates: `Capacity Constraint.release(pool_vip, 1, ...)` → `allocated: 2 → 1`, returning the slot the unsuccessful reserve took, and returns `rejected(resource-unavailable)` to the caller (cached against the token). Coherence is preserved across the failed reserve — the slot is not leaked. (Action wiring step 6.)

### Rejection path — confirming a lapsed hold

A buyer's checkout stalls; by the time `confirm_reservation(rsv_002, ...)` arrives, `rsv_002`'s 10-minute window has elapsed. `Provisional Commitment.confirm(rsv_002)` → `window-elapsed` → `rejected(window-elapsed)`. The reservation is not confirmed; its slot is the expiry sweeper's to return. The buyer must reserve afresh. (Invariant 4 — no confirmation of a lapsed hold; this is the confirm/expire race resolved in the pool's favor.)

### Regulated adversarial scenarios

**Regulator/operator audit — "prove you never oversold the pool."** An auditor reads the pool's `query(pool_id).allocated` and the Event Log and confirms that at no point did the count of Confirmed reservations exceed `capacity` (Invariant 3), and that `allocated` at every event equals the live-reservation set reconstructed from the Event Log (Invariant 1). The `allocated_before`/`allocated_after` fields on every reservation event — copied from the pool's own events, whose ids the entries cite — make the arithmetic chain replayable against the pool's audit log; a state in which Confirmed reservations outnumber `capacity`, or `allocated` diverges from the live set, is a conformance failure. The auditor consults no source code — the pool count and the journal are sufficient.

**Disputed double-booking — two customers claim the same unit.** An investigator inspects the Event Log for the pool: every [Reserve] carries the `allocation_event_id` and the `allocated_before`/`allocated_after`; every terminal action carries the `release_event_id`. If two Confirmed reservations exist against a 1-capacity pool, either `capacity` was raised by an `adjust_capacity` (an overbooking choice the pool's audit log records) or coherence was violated — and the Event Log shows which. Idempotency (Invariant 5) forecloses the retry-induced double-reserve; the dispute resolves to a recorded `adjust_capacity`, a client token-discipline failure, or a genuine finding, each distinguishable from the records.

**Inventory-leak forensics — "free count is wrong; find the stranded slot."** An operator observes `allocated` higher than the visible live reservations. The investigator replays the Event Log: every [Reserve] (slot taken) must have either a matching terminal [Cancel Reservation]/[Expire Reservation] (slot returned, `release = released(…)`) or a live Held/Confirmed reservation — and every pool allocation with no [Reserve] entry at all must have its `reserve_compensated` entry (the journaled compensation of a partial reserve; an allocation with neither is the finding). A reservation in a **slot-returning** terminal state (Released or Expired — not Confirmed, which keeps its slot) whose return is unjournaled and whose pool count shows the slot still held is the stranded slot — a leak whose precise reservation and pool the records name; a Released or Expired record with no binding entry at all is a compensated step-7 reserve, named by its `reserve_compensated` entry, and holds nothing. Invariant 2 (slot returned at most once) and Invariant 6 (every change journaled) are what make the leak locatable rather than a mystery in an aggregate counter.

## Generation acceptance

A derived implementation of this composition is *acceptable* — in the regulator-acceptance sense — when an external auditor, given the composition's `reservation_to_pool` and `token_results` stores plus the Provisional Commitment, Capacity Constraint, Duplicate Prevention, Event Log, and Actor Identity instances, can do all of the following without recourse to source code, runbooks, or developer narration.

### Record-clearable checks

1. **Allocation coherence.** For every pool, `query(pool_id).allocated` equals the number of that pool's reservations whose Provisional Commitment state is Held or Confirmed (Invariant 1). **Count them from the journal, reconciled against `reservation_to_pool` — not by counting entries in the index.** `reservation_to_pool` is a **derived index**, and counting its entries is not a keyed lookup, so rebuild-on-miss — which repairs a gap precisely because a lookup that finds nothing is observable — cannot fire. A lost entry would make the count come up short and this check would report `allocated` as exceeding the reservations that justify it: **an allocation-coherence violation that is not there**, and the one remediation it invites (reconciling `allocated` down to the counted reservations) would release genuinely-held slots and over-allocate the pool. A check that misdiagnoses an index gap as a substantive violation is worse than one that stays silent, because it recruits the auditor into the corruption — the trap [Audit Trail](./audit-trail.md) names from the other side. So: traverse the Event Log for this composition's `reserve` entries for the pool — the declared rebuild traversal (Composition state) — resolve each `reservation_id` through `reservation_to_pool` as a **keyed** lookup with rebuild-on-miss, read the Provisional Commitment state, and only then compare. **A divergence that survives the rebuild is a conformance failure only when it survives the in-flight exemption too:** Invariant 1 holds at quiescence, and its declared windows are **keyed on the pool's allocation events**, read through `pool_event_read`: an allocation event that neither a `reserve` outcome nor a `reserve_compensated` entry names (check 3's compensation arm) accounts for exactly one slot of divergence while it stands, as does a slot-returning terminal whose return the reconciliation has not yet resolved. A `reserve_intended` entry with no outcome and no allocation event behind it accounts for **zero** — a refused or pre-gate attempt took nothing, and were it admitted as a window it would excuse one slot forever, since a refused intent never receives an outcome. A divergence the windows explain is an open recovery obligation, reported as such; one they do not is the coherence finding. One that the rebuild closes is an index gap the rebuild has just closed, reported as that rather than as a coherence finding. The traversal reads journal entry payloads and so inherits the retention-horizon bound on any payload-sourced rebuild (the `Q-rebuild-bound` class, open on this pattern): past that horizon the reconciliation degrades to whatever the index still holds, which is a bound to state rather than a reason to count the index instead.
2. **No oversell.** For every pool, the count of Confirmed reservations never exceeds `capacity` across the Event Log replay (Invariant 3).
3. **Slot returned at most once, and compensations are visible.** For every reservation in a **slot-returning** terminal state — Released or Expired, the two senses of "terminal" being distinguished under *The load-bearing wiring decision* — **at most one slot-returning outcome entry — in-line or `recovery = true` — names it in the journal** (the pool keeps no per-allocation identity, so the count is of the journal's entries, never of the pool's release events), and the binding's `release` reads `released(the release_event_id that entry carries)` once it has landed; a Released or Expired reservation whose `release` reads `none` or `pending` **older than `reservation_completion_bound`** is an open return the reconciliation leg owes — a finding only where no `recovery_intended` entry names it within `compensation_window`, and a stranded-slot conformance failure only where the pool's count shows the slot still held after that window (Invariant 2). Younger ones are in flight and inconclusive. A **Confirmed** reservation is constituent-terminal but holds its slot: `release = none` there is the correct state, and a check written over the constituent's terminal set would convict every confirmed booking. A Released or Expired record that appears in **no** binding at all is the step-7 compensation's signature, not a leak — its `reserve_compensated` entry names the `reservation_id` (Composition state, cardinality). **Compensation arm:** every Capacity Constraint allocation event with no corresponding [Reserve] **outcome** journal entry (`action: reserve` — an unmatched `reserve_intended` entry is exactly the signature being looked for, not a match) has a `reserve_compensated` entry naming its `allocation_event_id` and `release_event_id` — an allocation with neither is an unresolved partial [Reserve], a conformance failure until its compensation lands.
4. **No lapsed confirmation.** For every Confirmed reservation, the constituent's own store shows the `confirm` was admitted while the window was open — Provisional Commitment Invariant 7 enforces this at the transition, so the check is a structural read of the commitment record (state Confirmed with its stored `expires_at`), not a claim this composition's journal must prove. The journal corroborates: the [Confirm Reservation] entry's `at ≤ expires_at` is expected as best-effort wall-time agreement (timestamps are advisory; a small skew between the journal's seam and the constituent's is a clock artifact, not a finding — the constituent's admission is the guarantee) (Invariant 4).
5. **Idempotency.** Every `idempotency_token` within the window binds to one outcome; no two distinct reservations share a token; retries within the window produce no second constituent invocation (Invariant 5, inherited from Idempotent Reservation) — checked **under the named Duplicate Prevention host obligations** (durable/highly-available recorded-set store; fail-closed `check`; cache-then-record durability ordering): a miss traceable to a violated obligation is a deployment finding against that obligation, recorded as such, not a pass.
6. **Attribution is witnessed, and authentication preceded the act.** For every state-changing outcome entry in the Event Log, take its `attestation_id` and call `Actor Identity.verify` against it, and recompose the expected action reference from the entry's own `action` and `idempotency_token` fields — both of which every entry carries for exactly this purpose. `verified` **and** a recorded `action_ref` equal to that composition is the passing result. The other outcomes are not all failures, and conflating them would make this check unrunnable in practice: `failed-verification(proof-invalid)` against a *matching* action reference is a genuine finding; `failed-verification(actor-unknown-in-registry)` and `failed-verification(registry-unavailable)` are **registry conditions, not composition conformance failures** — the first is what a key rotation looks like where the registry keeps no historical material, the second is a transient outage, and both are re-run rather than recorded against this composition; `not-known` means the id names no attestation at all, which *is* a finding. An attestation that verifies against a **different** action reference is the sharpest finding of all, because it is what a category-scoped `action_ref` would produce. An entry whose `attestation_id` is absent, names no attestation, or whose attestation verifies against a different action reference is a conformance failure — this is what makes Invariant 6's attribution claim checkable from the records rather than narrated. Then confirm an **intent** entry carrying the same `attestation_id` precedes the outcome entry in Event Log order: because the attestation is the composition's only credential-verifying call and its id rides the intent entry, the records establish that a valid credential was presented **for this exact invocation** — the `action_ref` carries the token, so the proof binds to this act and no other. **State the limit precisely:** the records order the attestation against the *journal entries*, not against the *constituent commits*, which live in the Provisional Commitment and Capacity Constraint stores with no order shared with the Event Log — and *Clock semantics* forbids the cross-seam stamp comparison that would supply one. An implementation that allocated, then attested, then wrote both entries would produce byte-identical records. What this check witnesses is the per-invocation credential presentation, which is real and is the half an auditor can have; Invariant 8's ordering claim rests on the declared wiring and is defended in-line by the step lists, not claimed as records-derivable.

  **An intent entry with no outcome entry is not a failure.** It names an invocation that committed nothing (a constituent guard refused it), or committed and failed to journal, or died between; resolve which against the constituent stores, and only the middle case owes the compensation the *Cross-store consistency under partial failure* edge case prescribes. Before the intent entry existed, that determination had to be inferred from constituent state with no record of what was attempted.

7. **Constituent Generation acceptance bars.** Verify each constituent's own bar over its store: Provisional Commitment's, Capacity Constraint's, Duplicate Prevention's, Event Log's, Actor Identity's.

### Externally-clearable checks

- **Whether the declared `capacity` reflects the physical unit count or a deliberate overbooking margin.** The composition enforces `allocated ≤ capacity`; whether `capacity` was set above the physical count (overbooking) is a deployment policy read from the pool declaration and `adjust_capacity` history, not a composition behavior.
- **Whether the resource-availability oracle behind `place_hold` was correct.** The composition records `resource-unavailable`; whether the underlying registry's availability determination was accurate belongs to the registry.
- **The composing-instance configurations** — idempotency window, digest function, expiry-sweep strategy, and the liveness inequality `reservation_completion_bound + reconciliation_cadence + recovery_write_latency < compensation_window`, confirmed over all three terms and never over the cadence alone (§*Liveness is arithmetic*) — read from deployment configuration, not from the stores.

## Edge cases and explicit non-goals

- **Cross-store consistency under partial failure.** The state-changing actions write to two or three stores in sequence; a failure between writes leaves partial state — and the failure classes are **not symmetric in their recoverability**, so the obligations split. *(a) The slot-returning pair is ordered and reconciled by the pool's own count — not made atomic, because it cannot be.* An earlier revision required [Cancel Reservation]'s and [Expire Reservation]'s terminal transition, pool release, flag and journal entry to commit within one host transaction, arguing that without it a lost pool release could not be told from a lost *record* of one. The argument was right about the ambiguity and wrong about the remedy: the transition is absorbing (Provisional Commitment Invariant 3), the pool release is an append on Capacity Constraint's own append-only audit log, and the journal entry is an Event Log append — none can be withdrawn, no store declares enlistment, and a journal entry "rolled back" after it had landed was a sealed record of a release that did not happen. The remedy is the **second source the stores actually supply**: the pool's `allocated` is authoritative for how many slots are held, and the journal is authoritative for how many should be. The steps are therefore ordered — transition, `pending` marker, pool release, `released(…)` marker, outcome entry — and every crash between them is resolved by the **pool reconciliation leg**: under the pool's `host_exclusion` section (Configuration — the deployment's obligation, not the pool's: Capacity Constraint serializes each call and sends a section spanning several to a Transaction composition; while the sweep holds it, no invocation is between its pool call and its outcome entry), take one consistent read of the pool's persisted record through `pool_event_read` — its audit log and its `allocated` — beside a journal read under `journal_durability`, and compute `expected = |reservations bound to the pool in Held or Confirmed| + |allocation events of the pool that neither a reserve outcome nor a reserve_compensated entry names — the open [Reserve] partials, of any age| + |slot-returning terminals whose return has not been journaled|`, comparing it with the pool's `allocated`. **The unjournaled-return set is keyed per reservation, never per intent, and a reservation is counted only under its own section:** the leg takes the reservation's `host_exclusion` section *before* counting it — a reservation whose section a live invocation holds is inside its bound and is that invocation's to return, so the leg neither counts it nor releases for it this run — and a Released or Expired record enters the set only where **no** slot-returning outcome entry — in-line or `recovery = true` — names the reservation at all, and only through a `pending` marker or an intent whose action matches the record's terminal state (`cancel_intended` ↔ Released, `expire_intended` ↔ Expired). A `cancel_intended` or `expire_intended` with no outcome against a reservation another token returned, or against the other action's terminal, was refused at its step 1 (`not-held` / `window-elapsed`) and is not a return — admitting it would land a recovery outcome for a return never begun, on a reservation whose real return is already journaled. Each member is a slot that *may* have been released. The count of **unlanded returns**, `allocated − (expected − those)`, is exactly the number of those returns that **did not** land; the leg releases exactly that many slots (the pool is fungible — Capacity Constraint keeps no per-allocation identity), attributes the releases to the unjournaled reservations, and lands **exactly one** outcome entry per reservation (`recovery = true`, the pairing intent's `attestation_id`, `recovered_by = application_actor_ref`; where several open intents of the matching action name one reservation — reachable only through a crashed token and a retry under another — the earliest by Event Log insertion order is the pairing and the rest are named as `intent_candidates`) — **naming the whole unjournaled set as `release_candidates` on every such entry where more than one was open at once**, since which of several concurrent returns landed is not decidable from a fungible counter and the record says so. Both candidate sets are bounded by `recovery_candidates_cap` (Configuration): a pool whose open set exceeds it is escalated as an unresolved finding and not compensated in that run, so every recovery entry stays inside the envelope each action sized at its step 1 (§*An outcome is sized before the intent*). Zero unlanded returns means every return landed and only the entries are owed. A *negative* count — the pool holds fewer than the records justify — is a double release, a conformance failure that is reported and never "repaired" by allocating. Every write the leg makes is preceded by a `recovery_intended` journal entry naming the pool, the reservations, and the count it is about to release, attested under the service identity (Configuration). *(b) The [Reserve] seams are compensable, and their compensations are journaled; the confirm pair is completed, not compensated.* The allocate→hold seam (step 6: slot allocated, hold refused) and the hold→journal seam (step 7: allocate + hold committed, journal failed) are each resolved by **compensating release** — return the slot (and, for the step-7 orphan, drive the hold terminal first: `release` while its window is open, `expire` once it has lapsed — step 7's branch), journal a `reserve_compensated` entry appended after the release, cache the rejection so the caller's retry replays it. A compensation that itself fails is retried inside the invocation at most `outcome_retry_attempts` times under high-priority surfacing, then yielded to the sweep — one writer per act, never both; until it lands, the partial [Reserve] is a surfaced finding, never a quiet inconsistency. *The confirm pair* — `Provisional Commitment.confirm` plus its outcome entry ([Confirm Reservation]) — splits differently: the transition is irreversible and no pool call is involved, so the seam is resolved by the **late outcome write** the action prescribes, never by compensation and never by a transaction, and the split is surfaced as an Invariant 6 gap until the entry lands. *(c) The residual detection sweep, between two edges.* Every leg examines only intents older than `reservation_completion_bound` (a younger one may belong to an invocation still between its writes — compensating a live [Reserve] returns a slot it is about to hold, and completing a live cancel releases twice) and inside the journal's retention horizon (past it the intent is destroyed and the binding's purged half is truth-bearing — read, never repaired). Any reservation in a **slot-returning** terminal state — Released or Expired, never Confirmed, which keeps its slot (*The load-bearing wiring decision*, the two senses of "terminal") — whose return is unjournaled (per the journal-backed rebuild and the `release` marker) is the pool reconciliation leg's input (*(a)*), a stranded slot only where that leg's arithmetic shows it unreleased; any Confirmed reservation whose `confirm_intended` entry has no `confirm_reservation` outcome entry is an unjournaled confirmation owing its late outcome write (*(d)* below); any Capacity Constraint allocation event with no corresponding [Reserve] **outcome** journal entry (`action: reserve` — an unmatched `reserve_intended` entry is exactly the signature being looked for, not a match) and no `reserve_compensated` entry is the partial-[Reserve] signature — found through `pool_event_read`, since an intent alone names no allocation. The same leg closes the seam [Reserve] step 2 defers to it: it completes step 8 for any `reserve` outcome entry older than the bound whose token `DuplicatePrevention.check` still reports `not-seen` (the crash between the outcome landing and the `record`), and, once the pool's open partials are compensated, resolves every `reserve_intended` older than the bound with no outcome and no compensation naming its token, whose token `check` still reports `not-seen`, by caching `rejected(recording-failure(outcome))` against the token and recording it — the sweep's `reserve_compensated` entry names the open intents of the pool as `intent_candidates`, and without this step a deferred retry would defer forever. *(d) The confirm-pair leg.* Any `confirm_intended` entry with no `confirm_reservation` outcome entry beside it whose reservation the Provisional Commitment store shows as Confirmed is an unjournaled confirmation: the late outcome write is owed, carrying the intent's `attestation_id` and `recovery = true`, preceded — under the reservation's `host_exclusion` section — by a traversal for an outcome naming the same token; an invocation still retrying holds that section until it has spent `outcome_retry_attempts`, so the two never both write. Every leg runs at process restart and on `reconciliation_cadence`, under the per-pool and per-reservation `host_exclusion` sections — two runs of a leg, restart and cadence, on one node or two, serialize on the same sections, a run that cannot take a pool's section skips the pool until its next run, and every look-then-write pre-check is re-read under the section, so no act ever has two compensators (§*A compensator is exclusive*) — as the service identity behind a `recovery_intended` entry, over a journal the deployment keeps across the crash (`journal_durability`); a partial not resolved within `compensation_window` escalates as an unresolved finding rather than remaining an open retry. This mirrors Idempotent Reservation's *idempotency under partial composition failure*. The `token_results` cache must be durable before `DuplicatePrevention.record` reports success (the inherited durability-ordering requirement) or a retry re-delegates and the coherence guarantees weaken.
- **Expiry sweeper boundary.** The composition holds the binding and exposes [Expire Reservation], but it is not the scheduling engine. An external sweeper reads holds whose `expires_at` has passed (eager: a timer at `expires_at`; lazy: on next observation) and calls [Expire Reservation]; the composition does not set timers or own the cadence. Until the sweeper fires, an elapsed hold is still Held and its slot is still allocated — so `allocated` may transiently count a lapsed-but-not-yet-expired hold; this is the documented eager-vs-lazy gap inherited from Provisional Commitment, and [Confirm Reservation]'s `window-elapsed` guard ensures the lapsed hold cannot be confirmed in the interim. A deployment requiring tight free-count accuracy runs an eager sweep.
- **Overbooking is a capacity choice, not a composition behavior.** A deployment that deliberately oversells (airlines selling 110 seats against 100) sets the pool's `capacity` above the physical count; the composition enforces `allocated ≤ capacity` against whatever `capacity` is declared and never itself permits `allocated > capacity`. Overbooking *policy* (how much to oversell, how to handle the overflow at fulfillment) is upstream; the composition's guarantee is coherence against the declared bound.
- **Cancelling a Confirmed reservation (un-booking) is out of scope.** [Cancel Reservation] operates on a Held reservation; a Confirmed reservation is a firm booking, and reversing it (refund, re-open the slot) is handled by a Reversal pattern (compose a Reversal atom that produces a compensating action and, where the slot should re-open, a pool `release`). This composition's terminal transitions out of Held are cancel and expire; un-booking a Confirmed reservation is a separate, deliberately-excluded lifecycle.
- **Multi-unit reservations.** This composition binds one slot per reservation (`count = 1`). A reservation for N units of a pool (a group booking) is a composing extension that allocates `count = N` and tracks N in the binding; the single-unit case is the primitive, and the multi-unit case is named here as the obvious generalization a deployment wires when it needs it.
- **Resource-availability oracle.** Whether a *specific* resource (seat 14C, room 307) is bookable belongs to Provisional Commitment's registry (`resource-unavailable`), upstream of and distinct from the pool's *count*. A pool with free capacity can still reject a [Reserve] for a specific unavailable resource; the two gates are independent (pool count via `allocate`, specific resource via `place_hold`).
- **No tamper-evident seal at this layer.** This composition journals to Event Log and attributes via Actor Identity — durable and attributed, but not cryptographically sealed. A deployment whose reservation events are litigation-exposed composes Audit Trail (Event Log + Actor Identity + Retention Window + Tamper Evidence) as a peer in place of the bare Event Log + Actor Identity pairing; the action wiring is identical, with `record_action` replacing the direct Event Log append. This composition uses the lighter pairing by default because reservation systems are high-throughput and most do not require per-event seals.
- **Rejected attempts are invisible in this layer's journal — a declared boundary.** The Event Log entries record successful and compensated state changes **plus one intent entry per authenticated invocation**, so the older claim that a rejected action appends nothing here no longer holds and should not be relied on: since the intent entry is written before the guards that reject, a capacity refusal or a `window-elapsed` now leaves a durable, never-deletable intent entry with no outcome entry beside it. That is deliberate — it is what makes an authenticated attempt distinguishable from no attempt at all, and it is what Generation acceptance check 6's unmatched-intent residue reads — but it has two consequences worth stating rather than discovering. A retrying caller against a full pool writes one permanent entry per attempt into an append-only log this composition composes with no Retention Window, which is a volume consideration for the high-throughput deployments this pattern serves. And attempt-level visibility is now *partial* rather than absent: refusals that occur **before** the attestation — a malformed argument, a token collision, an idempotent replay — still append nothing, though its outcome is cached against the idempotency token for replay. This is the same deliberate records-witness-successful-changes boundary Capacity Constraint declares at its own layer, inherited rather than contradicted. Deployments whose regulators require attempt-level visibility ("how many over-capacity rejections did this pool emit during the window?") compose Event Log around the call surface at deployment grain, exactly as the constituent's rejection-visibility note prescribes; this composition names its rejection vocabulary precisely so that journal has a stable vocabulary to record against.
- **Concurrency.** Concurrent state-changing actions on the same `reservation_id` (a [Cancel Reservation] racing an [Expire Reservation], or a [Confirm Reservation] racing an expiry sweep) resolve under the host's serialization guarantees and Provisional Commitment's single-resolution guarantee (its Invariant 2 — exactly one terminal transition commits under race; terminal absorption, its Invariant 3, then holds the loser out) — the first terminal transition wins, the second observes `not-held` and is rejected, and only one pool `release` fires — the loser transitions nothing and so reaches neither the `pending` marker nor the pool call, and a return the sweep has already landed is adopted at step 3's pre-check, never repeated. Concurrent `allocate` calls against the same pool are serialized **per call** by Capacity Constraint's own concurrency obligation (its Invariant 4 host obligation — serializable execution per `pool_id`); the composition relies on it for the call and does not re-implement the pool's serialization. What the pool does not grant is a section spanning several calls — its own edge case sends *"multi-action transactions"* to a Transaction composition — so the three sections this page needs are declared as the deployment's `host_exclusion` obligation (Configuration): per token (a concurrent retry never double-acts before the cache is populated — the Idempotent Reservation requirement, owned here), per reservation (the terminal steps, the late writes and the sweep's completions), and per pool (an invocation from its pool call through its outcome entry, the sweep from its consistent read through its releases and entries). **The reconciliation sweep takes the per-pool section for its arithmetic and the per-reservation section for each completion**, so a sweep and a live invocation never act on one pool's count or one reservation's return at once, and two sweep runs never act on one pool.
- **Clock semantics.** `now` — the `at` stamp on every journaled reservation event — is the injected `clock_t` supplied at the composition's single I/O seam (see *Logic confinement*): read once per invocation by the host for this layer's own stamps — each constituent delegation is its own pipeline invocation with its own seam reading, never shared with or compared against this one — and never read inside a guard or a transition; no signature carries a `now` parameter. The hold window is not this composition's to keep: `expires_at`, the `window-elapsed` / `window-not-elapsed` guards, and eager-vs-lazy sweep timing are **inherited from Provisional Commitment's clock treatment** — evaluated against the `now` injected at that constituent's seam, with the lapse a written transition rather than a read-time inference because it returns a resource and a pool slot — and are not restated here as a competing rule. What remains a deployment matter is clock *quality*: the honesty of the injected reading, its monotonicity, and skew between this composition's seam and the constituents' own. That skew is why ordering never rests on comparing stamps — Event Log insertion order is the authoritative ordering of reservation events (Composes — Event Log). Where reservation timestamps have legal or settlement force, a Trusted Timestamping composition supplies the verifiable anchor and binds Event Log insertion order to wall-time; absent it, insertion order is authoritative. The residual risk under seam injection is a deployment that injects a dishonest `now`, not an internal race.

#### Reserve

The composition's core action: it takes one slot of a pool and opens a provisional hold bound to it — the capacity gate (`Capacity Constraint.allocate`) and the hold (`Provisional Commitment.place_hold`) are bound so the slot is allocated only if the hold is taken, with a compensating `release` if the hold fails (preserving allocation coherence). Returns the `reservation_id`, or [Pool Closed] / [Pool Capacity Exceeded] / an inherited rejection. Idempotent under retry.

Kind: Operation

#### Confirm Reservation

The composition action that confirms a held reservation into a firm booking. **The slot is not released** — a Confirmed reservation keeps its pool unit, so `allocated` is unchanged. Rejects `window-elapsed` (Provisional Commitment's confirm-within-window guarantee, surfaced here) — the *no-confirm-without-active-hold* guarantee (Invariant 4).

Kind: Operation

#### Cancel Reservation

The composition action that cancels a held reservation and **returns its slot to the pool, in order, exactly once** — the Provisional Commitment `release`, then the `pending` marker, then the pool `release`, then [Slot Released] and the journal entry, with the pool reconciliation resolving any crash between them by the pool's own count (Invariants 1–2).

Kind: Operation

#### Expire Reservation

The action an expiry sweeper invokes on a held reservation whose window has elapsed: it drives the Provisional Commitment `expire` transition and returns the slot to the pool in the same order and under the same exactly-once discipline as [Cancel Reservation] — differing only in the constituent transition and the `window-not-elapsed` guard.

Kind: Operation

#### Query Reservation

The read-only query returning `{state, pool_id, slot_held}` for a reservation — reads the commitment's current state and the binding. Produces no Event Log entry.

Kind: Operation

#### Slot Released

The `released(release_event_id)` value of each `reservation_to_pool` binding entry's `release` marker, written when the pool `release` returns — preceded by `pending(…)`, written before the pool is touched. Together with the pool reconciliation's arithmetic it is what makes a slot return to the pool **at most once** (Invariant 2) — the reconciliation never releases for a reservation the marker or the journal shows returned, and releases exactly the pool's unlanded returns otherwise.

Kind:      Field
Field of:  the reservation-to-pool binding entry
Role:      the slot-return-once guard
Projects:  release

#### Pool Closed

The composition's own rejection from [Reserve] — returned when the target pool is Closed or Suspended to new reservations. Maps Capacity Constraint's `closed` / `suspended` allocate rejections to one pool-specific code — a deliberate collapse that discards the retryable-once-resumed signal `suspended` carries; a caller who needs the distinction reads the pool's own `query`, while this boundary reports only that no new reservation is admitted now.

Kind:      Member
Member of: the reserve rejection
Role:      Rejection
Projects:  pool-closed

#### Pool Capacity Exceeded

The composition's own rejection from [Reserve] — returned when the pool is full: Capacity Constraint's `allocate` refuses past `capacity` (Invariant 4). The observable form of the *no-oversell* guarantee (Invariant 3) at the capacity gate.

Kind:      Member
Member of: the reserve rejection
Role:      Rejection
Projects:  pool-capacity-exceeded
