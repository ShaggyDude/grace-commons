## Summary

Login wires together the full lifecycle of logging in: checking the presented credential, issuing a time-limited session on success, logging out, and — crucially — cancelling every session that came from a credential when that credential is revoked. It combines three patterns: one that verifies credentials (Credential), one that issues and tracks time-limited sessions (Session), and the tamper-evident audit record that spans all of it (Audit Trail).

Its central guarantee is that a session can never be issued without a successful credential check first — the wiring makes it structurally impossible, and an auditor can confirm it from the records because every issued session is named by a login-family audit event: `login_succeeded` on the clean path, or `login_map_write_failure` on the map-degradation arm, each recorded before the call returns or retried until it lands — and a session that outran every record (a crash inside the issuing call) is found by the issuance-reconciliation sweep and revoked with a record, unusable anyway since the dying call returned its token to no one. Its second guarantee is cascade completeness: when a credential is revoked, every still-active session derived from it is cancelled before the operation returns, leaving none behind.

Every login attempt (success or failure), every logout, and every cascaded revocation is recorded, so an investigator can answer from the records alone which credentials established which sessions, whether a session rested on a valid credential, and when and by whom sessions were revoked. The cascade is the load-bearing guarantee that appears only when the three patterns are combined — it belongs to none of them alone — and it is what lets higher-level patterns reliably cut off access the moment a credential is pulled.

## Intent

Every system that authenticates principals eventually faces the same composability problem: credential verification is a momentary check, session management is a bounded persistence concept, and audit recording is a regulated obligation — and none of the three atoms can see the other two. Credential answers *"does this material match what was registered?"* and returns immediately. Session issues a time-bounded token but makes no authentication judgment — it issues a session for whatever principal it is given, trusting entirely that the caller verified authentication first. Audit Trail records events but knows nothing about the semantics of the events it records. The question of *what should happen at the boundary where these three concepts meet* — how the transition from credential verification to session issuance should be wired, what should be recorded and when, and especially what should happen to open sessions when a credential is revoked — belongs to no single atom. It belongs to the composition.

Login is that composition. It provides three services: the `login` action wires `Credential.verify → Session.issue` in the correct order, with every login attempt (successful or failed) recorded in the Audit Trail before returning. The `logout` action wires `Session.revoke` with attribution and Audit Trail recording. And [Revoke Sessions For Credential] provides the cascade: when a Credential is revoked — whether by the credential owner, an administrator, or an automated compromise-response process — every Session derived from that Credential is revoked in the same operation, and the full cascade is recorded.

The cascade is load-bearing for downstream compositions. Privileged Access Provisioning's `exercise_access` action depends on Session validity as its first guard: a session invalidated by credential revocation will block all subsequent `exercise_access` calls for any Capability issued to that principal's sessions. The cascade path is: `Credential.revoke` (outside this composition's surface) → caller invokes [Revoke Sessions For Credential] → Login walks `credential_to_sessions[credential_id]` → `Session.revoke` for each Active session → Audit Trail records each revocation → Privileged Access Provisioning's session check thereafter returns `rejected(session-invalid)`. The Login composition is the mechanism that makes this arc visible and traceable from records alone.

This composition does not implement multi-factor authentication (MFA — requiring two or more independent proofs of identity), account lockout, rate limiting, or session renewal. It implements the minimal correct wiring of three atoms for the common authenticated-session case — the pattern that every other authentication-adjacent composition either calls or depends on.

## Composes

- **[Credential](../atoms/credential.md)** — the verification surface. The composition calls `Credential.verify(principal_ref, credential_type, presented_material)` as the first action of `login`. A `verified` result is the gate; any `failed-verification(reason)` terminates the `login` call with `rejected(credential-invalid)` and records a failed-login event in the Audit Trail without issuing a session. The composition also queries the credential store directly (read-only) to retrieve the `credential_id` of the active credential after a successful `verify`, for population of `credential_to_sessions`. The composition does not call `Credential.register`, `rotate`, or `revoke` — those belong to the identity-management surface. [Revoke Sessions For Credential] is called externally by whatever revokes the credential; this composition provides only the downstream cascade, not the credential revocation itself.

- **[Session](../atoms/session.md)** — the time-bounded session record. The composition calls `Session.issue(principal_ref, issued_by_ref, session_duration)` inside `login`, after credential verification succeeds. The composition calls `Session.revoke(session_token, revoked_by_ref, reason)` inside `logout` and inside each step of [Revoke Sessions For Credential]. The composition calls `Session.validate(session_token)` inside [Revoke Sessions For Credential] to read each session's status before deciding whether to revoke: a lapsed session reads `invalid(expired)` by the atom's **derived-expiry projection** — there is no `Session.expire` action, no expiry write, and no stored Expired state anywhere — and the cascade skips it, not to avoid an error (a revoke over a lapsed stored-Active record would in fact commit) but because a session already dead by derivation needs no revocation write. Callers needing to validate sessions on subsequent requests call `Session.validate` directly; `validate` is not re-exposed on this composition's surface.

- **[Audit Trail](./audit-trail.md)** — the regulated-audit substrate. One Audit Trail instance is maintained for all three of Login's actions, consuming its declared contract exactly: `record_action(action_ref, actor_ref, credential, data) → event_id | rejected(invalid-credential | invalid-request | recording-failure(step))`. The full event roster: `login` writes `login_succeeded`, `login_failed(...)`, or `login_map_write_failure`; `logout` writes `logout_succeeded`; [Revoke Sessions For Credential] writes one `credential_revocation_cascade_initiated` event, one `session_revoked_by_cascade` event per revoked session, and `session_revoke_failure_during_cascade` / `session_not_found_during_cascade` on its failure arms; the issuance-reconciliation sweep writes `orphan_session_revoked` on its revoke-and-record closure and re-emits the actions' own event types otherwise (*The recovery discipline*). **Every Login event is emitted by the composition actor** (`actor_ref = application_actor_ref`, `credential = application_credential` — Configuration), with the human parties as `data` fields: Login's callers are end principals whose presented material is the very thing under test (a failed login's principal has no attestable credential at all), not registered audit actors, so the composition's own registered identity is the only honest attestation surface for every event it writes. **Consumed read capability, declared:** beyond `record_action`, the composition consumes the substrate's declared pass-through list read — a query by sequence-number range (here always with an **open upper bound**) passes through the substrate to its Event Log's `read` unchanged, per the substrate's own list-query split — with every event selection performed **in composition code** over the returned sequence: filtering to the login-family `action_ref`s and to a `credential_id` inside `data` is the enumerate-and-filter move the substrate itself uses for its own rebuilds, never a payload-predicate *query* (that lookup shape is the forthcoming **Reverse Index** pattern's, which a deployment may compose over the trail as an instance optimization without changing this contract). The cascade's event-derived set, both rebuild procedures in Composition state, Invariant 2a's coverage reads, Invariant 5's sequence-order check, and Generation acceptance's event queries name this capability and no other. Event Log, Actor Identity, Retention Window, and Tamper Evidence are reached transitively through Audit Trail; the composition does not maintain separate instances of those atoms.

## Composition logic

### Composition state

The composition owns emergent state that is not representable inside any single constituent atom. Every element carries its Contract classification per [`execution-contract.md`](../execution-contract.md) §Composition state — *derived index*, with a named rebuild procedure that regenerates it from constituent stores, or the honest boundary where derivability is conditional:

- **`credential_to_sessions`** — map from `credential_id → Set<session_token>`. Populated atomically with each `Session.issue` call inside `login`: the `credential_id` of the verified credential maps to the newly issued `session_token`. Entries are never deleted from the set — the set includes all sessions ever issued for the credential, including expired and revoked ones. The cascade action ([Revoke Sessions For Credential]) iterates the full set and skips non-Active sessions; it does not modify the set. `credential_id` is the key because credentials are the upstream identity anchor: two different credentials for the same principal (different types, or a rotation successor) are tracked as separate cascade roots, each with their own derived-session set. **Contract classification: derived index** — the pairing fact lives in the Audit Trail, a constituent: `login` step 7 writes `{principal_ref, credential_type, credential_id, session_token, attempted_at}` into the `login_succeeded` event data, and step 5's failure arm writes the same pair into a `login_map_write_failure` event, so every issued session's `(credential_id, session_token)` pair is immutable audit content. *Rebuild procedure:* enumerate the substrate through the declared enumerate-and-filter read (*Composes*), select the `login_succeeded` events, and group each data's `session_token` by its `credential_id`; a `login_map_write_failure` event names a pair the live map lacks — the rebuild reconstructs exactly the backfill Invariant 2a's remediation prescribes, so rebuild-on-miss *is* the remediation path.

  **The rebuild is bounded by the audit instance's horizon, and — unusually for this corpus — the bound is comfortably longer than anything that reads it, which is the finding rather than a reason to skip stating it.** The traversal reads `login_succeeded` payloads, which the substrate destroys in their entirety at the horizon, `action_ref` included; past it the traversal cannot recognize the events at all. What matters is **which pairs the readers actually need**. The cascade ([Revoke Sessions For Credential]) iterates the set and **skips every non-Active session**, so the only pairs whose recovery can change an outcome are those whose sessions are still Active — and an Active session is by construction within its own TTL. **The rebuild therefore has to remain valid for one session lifetime, not for the life of the credential or the audit trail**, and a session TTL is measured in hours or days against an audit horizon measured in years. The comparison passes by orders of magnitude.

  That comparison is the thing to state, and stating it is not ceremony: it is what distinguishes this map from the ones elsewhere in the corpus where the same shape is a live defect. Where a claim can outlive the evidence it reads, the spec owes a declared ordering and a check. **Here the claim cannot** — the reader discards exactly the entries whose evidence would have expired — so the bound is recorded and nothing further is owed. A deployment that configured an audit horizon shorter than its own session TTL would invert this, which is a configuration no regulated deployment reaches by accident and which the ordering above makes visible if it ever did. The Contract's three obligations follow: the map sits **outside the action's atomicity surface** (the session's validity never depends on the map write — step 5's failure arm returns the session anyway); a missing or lost entry is a **rebuild trigger, not data loss** — and because the cascade reads this map as *gate input for revocation completeness*, that read carries **rebuild-backed semantics** ([Revoke Sessions For Credential] step 2): the authoritative set is the one the audit events carry, and a lost map entry can never silently shrink a cascade; and the map claims no cross-constituent transactional consistency. *Rebuild boundary, named:* a step-7 `login_succeeded` write that fails after the step-5 map write committed leaves the map ahead of the audit record until the retried write lands (the step-7 failure arm below); during that window the rebuild under-reads by exactly the entries the retry will restore.

- **`session_to_credential`** — reverse map from `session_token → credential_id`. Maintained as the strict inverse of `credential_to_sessions`: every atomic write that adds a `session_token` to a `credential_id`'s set also writes the corresponding entry to `session_to_credential` in the same transaction. Used for per-session traceability — given a `session_token`, an auditor can recover the `credential_id` that produced it without a full scan. Entries are immutable once written and never deleted. **Contract classification: derived index** — the same rebuild as `credential_to_sessions`, keyed in the reverse direction; the two maps are projections of one relation (Invariant 6's inverse-consistency claim), so a divergence between them is an index defect resolved by rebuild from the events, never a fact of its own.

- **`login_event_log`** — append-only record of every `login` call, whether successful or failed. Each entry carries: `event_id` (opaque, system-generated), `principal_ref`, `credential_type`, [Outcome] (one of: `success` | `success-with-map-failure` | `failed-verification(reason)` | `failed-storage-failure(stage)`), `credential_id` (null on credential-verification failure), `session_token` (null on failure; present on `success` and `success-with-map-failure`), `attempted_at`. [Success With Map Failure] means `Session.issue` succeeded and the session was returned to the caller, but the cascade-map write (step 5) failed; [Failed Storage Failure] means the call failed at the named stage (`credential-id-lookup`, `credential-id-confirm`, or `session-issue`) before any session was issued. This log is the composition's own state; the Audit Trail is the regulated-audit record of the same events. The two are redundant by design: the `login_event_log` is the composition-layer fast query surface; the Audit Trail is the tamper-evident external-auditor surface. **Contract classification: conditional derived index — with a declared truth-bearing window:** an entry whose mirrored audit event has not yet landed (the step-7 retry window, or the step-5 failure arm's pending record) is the **durable intent** for that record — truth-bearing for exactly that window, under a durability obligation, because its payload is what the sweep's re-emission is constructed from (*The recovery discipline*); once the event lands the entry is a pure cache again. With `failed_login_audit_trail` enabled (the default and the regulated posture), every entry mirrors an Audit Trail event — `login_succeeded`, `login_map_write_failure`, or a `login_failed(...)` — so the log is a derived index over the substrate's login-family events (*rebuild procedure:* the declared enumerate-and-filter read (*Composes*) selected to those action types, projecting each event's `data` into the entry shape — total, because every login-family event carries `attempted_at` in its data, the payload-provenance copy of the seam reading the entry was stamped with), a composition-layer query cache with rebuild-on-miss semantics and no consistency claim. With the knob **disabled**, the failed-attempt entries carry truth no constituent store holds; per the Contract's record-coordination rule (a composition that must record that its own calls occurred does so by composing Event Log, never by growing a bespoke store), a deployment disabling the knob either backs the failure entries with a composed Event Log instance or accepts them as out-of-band operational observability rather than spec state — the choice is the deployment's, and the spec's own invariants (Invariant 4 included) are honest either way because the success-path entries remain audit-mirrored.

### Logic confinement (clock and id)

The clock is an **injected input at the composition's single I/O seam**, never read inside a guard or a transition and never threaded through a caller signature. Per the Logic Confinement Principle ([`execution-contract.md`](../execution-contract.md)), the host reads the clock once per invocation and injects `now` (`clock_t`) at the seam before the orchestration runs; the `login` signature carries **no** `now` argument. At this layer the reading serves exactly one purpose: stamping `attempted_at` on the `login_event_log` entry — one reading per `login` invocation, whichever outcome arm writes the entry. **No guard at this layer is time-gated**: input validation, the `Credential.verify` gate, and the cascade's Active-check are state- and outcome-valued; session expiry is Session's own temporal rule, evaluated against the reading injected at *that* constituent's seam (`Session.issue`/`validate` accept no timestamp from this composition, so their stamps and expiry arithmetic are the constituent's, taken at its own seam — two seams, two readings, never claimed equal). Ids are allocated by the constituents at their own seams: `credential_id` by Credential, `session_token` by Session, `event_id`s by the stores that write them. This composition mints no id inside a transition and generates no cryptographic material.

### Configuration

- **`default_session_duration`** — the `session_duration` passed to `Session.issue` when the caller does not supply one. Deployment-configurable. Must be a positive duration; absent default returns `invalid-request`.

- **`audit_trail_retention_policy`** — the retention policy the Audit Trail **instance is configured with** at deployment: `record_action(action_ref, actor_ref, credential, data)` takes no per-call retention argument, so every audit write this composition makes inherits the instance's configured policy and no call site passes one. Typically `hipaa_6_year` (HIPAA — the US Health Insurance Portability and Accountability Act), `sox_7_year` (SOX — the Sarbanes-Oxley Act), or `pci_dss_1_year` (PCI DSS — the Payment Card Industry Data Security Standard) depending on the regulated domain. Deployment-configurable.

- **`application_actor_ref` and `application_credential`** — the composition's service identity, a first-class registered actor in the substrate's Actor Identity registry, and the attested emitter of **every** Audit Trail event this composition writes (the distinguishing rule stated in *Composes*: the human parties — the logging-in principal, the logout caller, the cascade's `revoked_by_ref` — appear in each event's `data`, never as the attested `actor_ref`, because none of them presents a registry credential at this surface). The same service-identity discipline as documented in Multi-Party Approval's Configuration section: the deployment provisions and rotates this credential; its compromise surface and forgery defense follow the same reasoning as documented there. An `invalid-credential` from any of this composition's `record_action` calls is therefore a **deployment fault** (the composition credential is bad), never a caller outcome: it takes the same landing as the site's recording failure, with a hard operational alert naming the true cause.

- **`issuer_refs`** — the set of `issued_by_ref` values the deployment's calling layers pass into `login` (and hence into `Session.issue`). Deployment-declared, non-empty. This is the scope of the issuance-reconciliation sweep's Session-store comparisons (*The recovery discipline*): sessions issued outside the declared set are another surface's business and are neither adopted nor revoked by this composition's sweep.

- **`failed_login_audit_trail`** — whether failed `login` attempts are recorded in the Audit Trail (in addition to the `login_event_log`). Defaults to `true`. Regulated deployments should leave this enabled; turning it off reduces the Audit Trail's forensic completeness for breach investigations. Disabling does not affect the `login_event_log`, which records all attempts regardless.

### Action wiring

**`login(principal_ref, credential_type, presented_material, issued_by_ref, session_duration?) → session_token | rejected(invalid-request | credential-invalid | storage-failure)`**

1. Validate: `principal_ref`, `credential_type`, `presented_material`, `issued_by_ref` must be non-null, non-empty, and **non-whitespace**, and each string input must satisfy the consuming constituents' declared string policies and length caps (Session's input rules for what `issue` receives; the wired Audit Trail instance's payload budget for what the event details carry) — adopted at this boundary so the constituents' `invalid-request` arms are foreclosed for validated inputs; `session_duration` must be positive if supplied. Any violation: `invalid-request`, nothing written.
2. Call `Credential.verify(principal_ref, credential_type, presented_material)`.
   - If `failed-verification(reason)`: append to `login_event_log`: `{principal_ref, credential_type, outcome: failed-verification(reason), credential_id: null, session_token: null, attempted_at: now}`. If `failed_login_audit_trail` is enabled, call `Audit Trail.record_action(action_ref=login_failed, actor_ref=application_actor_ref, credential=application_credential, data={principal_ref, credential_type, reason, attempted_at})` — composition-attributed with the principal in `data` (*Composes*; the failing principal's material just failed and cannot attest anything). Its arms: `recording-failure(step)` → the entry stands in `login_event_log`, the event is retried by the implementation as a hard alerting condition; `invalid-credential` → the deployment fault of Configuration, same landing; `invalid-request` → unreachable per step 1. Return [Credential Invalid].
3. Query the credential store (the atom's declared queryable administrative surface) for the **effective-Active** credential of `(principal_ref, credential_type)` → `credential_id`, then **confirm the read against the verify outcome**: call `Credential.verify(principal_ref, credential_type, presented_material)` a second time — the verify–read–verify sandwich. A second `verified` proves the presented material matches the pair's effective-Active credential *on both sides of the read*, so the `credential_id` just read roots a record the material verifies against (the atom's effective-Active uniqueness gives at most one per pair). A second `failed-verification`, or a read finding **no** effective-Active record, means a rotation, revocation, or lapse committed inside the window — the **named verify→read race**, not a storage inconsistency — and the composition retries once from step 2 with the same inputs; if the retry's verify fails, the credential has genuinely turned and the step-2 failure arm applies. **The retry's other failure is landed, not looped:** if the retry's verify succeeds but its sandwich fails again — a second rotation racing the window, or a second empty read — the single retry budget is spent and the composition returns `rejected(storage-failure)`, appending `{principal_ref, credential_type, outcome: failed-storage-failure(credential-id-confirm), credential_id: null, session_token: null, attempted_at: now}` to `login_event_log` (and, if `failed_login_audit_trail` is enabled, recording `login_failed(credential-id-confirm-failure)`, composition-attributed, arms as at step 2): contention at the credential surface, honestly surfaced as retry-later rather than spun on, and a named [Outcome] so Invariant 4's vocabulary stays total. A genuine store error on the read (the query itself fails): append to `login_event_log`: `{principal_ref, credential_type, outcome: failed-storage-failure(credential-id-lookup), credential_id: null, session_token: null, attempted_at: now}`; if `failed_login_audit_trail` is enabled, record `login_failed(credential-id-lookup-failure)` (composition-attributed, arms as at step 2); return `rejected(storage-failure)`.
4. Call `Session.issue(principal_ref, issued_by_ref, session_duration ?? default_session_duration)`.
   - If `rejected(storage-failure)`: append to `login_event_log`: `{principal_ref, credential_type, outcome: failed-storage-failure(session-issue), credential_id, session_token: null, attempted_at: now}`; if `failed_login_audit_trail` is enabled, record `login_failed(session-issue-failure)` (composition-attributed, arms as at step 2); return `rejected(storage-failure)`.
   - If `rejected(invalid-request)`: unreachable once step 1 adopted the constituent's string policy — observing it means this layer's validation and the atom's disagree, a conformance fault to fix; it takes the `failed-storage-failure(session-issue)` landing with a deployment alert naming the true cause.
   - On success: `session_token` is the returned token.
5. Atomically: add `session_token` to `credential_to_sessions[credential_id]`; write `session_to_credential[session_token] = credential_id`.
   - If this write **succeeds**: proceed to step 6.
   - If this write **fails**: the session has been issued (step 4 committed). Append to `login_event_log`: `{principal_ref, credential_type, outcome: success-with-map-failure, credential_id, session_token, attempted_at: now}`. Call `Audit Trail.record_action(action_ref=login_map_write_failure, actor_ref=application_actor_ref, credential=application_credential, data={principal_ref, credential_type, session_token, credential_id, attempted_at})`. Its arms matter here more than anywhere: this event is the surface that keeps the session cascade-coverable (Invariant 2a — the cascade set is event-derived), so on `recording-failure(step)` or the deployment-fault `invalid-credential` the implementation **retries the write until it lands, as a hard alerting condition** — until it does, the session sits in neither the map nor the events, the one named uncovered window. Return `session_token` to the caller — the session is valid even if the cascade map is incomplete; the map write failure is a finding to investigate and remediate separately, not a reason to deny the authenticated session to the principal. Steps 6–8 are not reached.
6. Append to `login_event_log`: `{principal_ref, credential_type, outcome: success, credential_id, session_token, attempted_at: now}`.
7. Call `Audit Trail.record_action(action_ref=login_succeeded, actor_ref=application_actor_ref, credential=application_credential, data={principal_ref, credential_type, credential_id, session_token, attempted_at})` — composition-attributed with the principal in `data` (*Composes*); `attempted_at` in the payload is what makes the `login_event_log` rebuild total. If this call fails (`recording-failure(step)`, or the deployment-fault `invalid-credential`), the session is still returned (step 4 committed; the authenticated principal is not denied over an audit-write fault) — the missing `login_succeeded` event is an audit-coverage orphan the implementation retries until it lands, surfaced meanwhile as a hard alerting condition; until it lands, the cascade maps are ahead of the audit record (the rebuild boundary named in Composition state). `invalid-request` is unreachable per step 1.
8. Return `session_token`.

**`logout(session_token, actor_ref, reason?) → logged-out | rejected(invalid-request | not-known | already-terminal | storage-failure)`**

1. Validate: `session_token` and `actor_ref` must be non-null, non-empty, and non-whitespace; if `reason` is not supplied, default to `"user-initiated-logout"`; the resolved `reason` and both refs must satisfy the consuming constituents' string policies and caps — Session's `revoke` input rules, and the wired Audit Trail instance's payload budget for the `logout_succeeded` event data. Any violation: `invalid-request`, nothing written. (This is the policy step 3's unreachability claim rests on.)
2. Call `Session.revoke(session_token, revoked_by_ref: actor_ref, reason)`.
   - If `rejected(not-known)`: return `rejected(not-known)`.
   - If `rejected(already-terminal)`: return `rejected(already-terminal)`.
   - If `rejected(invalid-request)`: return `rejected(invalid-request)`.
   - If `rejected(storage-failure)`: return `rejected(storage-failure)`.
3. Call `Audit Trail.record_action(action_ref=logout_succeeded, actor_ref=application_actor_ref, credential=application_credential, data={requested_by: actor_ref, session_token, reason})` — composition-attributed with the requesting actor in `data` (*Composes*). Arms: `recording-failure(step)` or the deployment-fault `invalid-credential` → the revocation committed at step 2 and stands; return `logged-out` with the missing record retried by the implementation as a hard alerting condition (the Session store's `Revoked` status is the authoritative terminal record meanwhile); `invalid-request` → unreachable per step 1's adopted policy; a post-validation `invalid-request` is a validation disagreement — a conformance fault taking the recording-failure landing with an alert naming the true cause.
4. Return `logged-out`.

*Note: `logout` does not modify `credential_to_sessions` or `session_to_credential`. The `session_token` remains in both maps as a durable history entry. The session's `status = Revoked` in the Session store is the authoritative terminal-state record; the cascade action skips sessions whose `Session.validate` returns non-`valid`.*

**[Revoke Sessions For Credential]** — (Projected contract: `revoke_sessions_for_credential(credential_id, revoked_by_ref, reason) → {revoked: N, skipped: M, not_found: K} | rejected(invalid-request | storage-failure)`)

*This action is called by whatever external process revokes a credential — typically the identity-management surface or a compromise-response process — to cascade that revocation to all derived Sessions.*

1. Validate: `credential_id`, `revoked_by_ref`, `reason` must be non-null, non-empty, and non-whitespace, and `reason` must be short enough that the step-5 concatenation (`"credential-revocation-cascade: " + reason`, prefix included) satisfies Session's `revoke` reason policy and the audit-payload budget — adopted here so the constituents' `invalid-request` arms are foreclosed for validated inputs. Any violation: `invalid-request`.
2. Compute `sessions` as the **union** of the live map entry `credential_to_sessions.get(credential_id)` and the **event-derived set** — the `(credential_id → session_token)` pairs carried by the substrate's `login_succeeded` **and** `login_map_write_failure` events for this `credential_id`, read through the declared enumerate-and-filter capability (*Composes*). The union is unconditional, not "where integrity is in doubt": the events cover sessions whose map write failed, the live map covers sessions whose step-7 event is still in its retry window (the rebuild boundary), and every session `login` ever returned is in at least one of the two surfaces outside the step-5-failure-event retry window (the one named uncovered window, closed by that write's retry-until-lands discipline). Mechanically, any `login_map_write_failure` event for this credential without a completed remediation *forces* the event-side read — the cheapest conforming implementation reads the events every time. If the union is empty (no sessions were ever issued for this credential through this Login composition): proceed — the action is a no-op, and returning `{revoked: 0, skipped: 0, not_found: 0}` is the correct outcome. The caller can inspect the credential record directly to determine whether the credential exists; the composition does not perform that check.
3. Call `Audit Trail.record_action(action_ref=credential_revocation_cascade_initiated, actor_ref=application_actor_ref, credential=application_credential, data={credential_id, revoked_by_ref, session_count: sessions.size})` — composition-attributed with the requesting actor in `data`. Arms: `recording-failure(step)` → return `rejected(storage-failure)` (nothing has been revoked; the caller retries the whole action safely); the deployment-fault `invalid-credential` → the same return with the alert naming the true cause; `invalid-request` → unreachable once step 1 caps `reason` (below). Do not proceed to step 4 on any failure — cascading without an initiation record produces orphaned `session_revoked_by_cascade` events that cannot satisfy the Generation-acceptance (GA) check-3 reconciliation, making the cascade non-auditable.
4. Initialize counters: `revoked = 0`, `skipped = 0`, `not_found = 0`. **These are the cascade's only record of its skips**, and step 5c writes no per-session event — deliberately, since a session that is already terminal needed nothing done to it and an event per non-act would bury the events that matter. That is why step 6 exists: without it the counters die with the invocation and the reconciliation below has no way to tell a skipped session from a missed one.
5. For each `session_token` in `sessions`:
   a. Call `Session.validate(session_token)`.
   b. If `valid(...)`: call `Session.revoke(session_token, revoked_by_ref, reason: "credential-revocation-cascade: " + reason)`. If `revoke` succeeds: increment `revoked`; call `Audit Trail.record_action(action_ref=session_revoked_by_cascade, actor_ref=application_actor_ref, credential=application_credential, data={session_token, credential_id, revoked_by_ref})`. If `revoke` returns `storage-failure` — or the foreclosed `invalid-request`, observed only as a validation disagreement, a conformance fault carried on the same arm — call `Audit Trail.record_action(action_ref=session_revoke_failure_during_cascade, actor_ref=application_actor_ref, credential=application_credential, data={session_token, credential_id, revoked_by_ref, error: <the arm>})`; continue to next session (do not abort the cascade — partial revocation is better than no revocation; the failure is an open finding that must be remediated). If `revoke` returns `already-terminal`: another process **revoked** the session between the `Session.validate` call and the `Session.revoke` call — a normal TOCTOU (time-of-check-to-time-of-use) race; only a prior revoke *write* produces `already-terminal`, since lapse is derived and would have surfaced as `invalid(expired)` at 5a. Increment `skipped` and continue. No Audit Trail event needed; the terminal transition is already recorded in the Session store. Each per-session `record_action`'s own failure arms take the retry-until-lands discipline (the cascade proceeds; the missing record is a hard alerting condition until it lands).
   c. If `invalid(expired)` or `invalid(revoked)`: increment `skipped`. The session is already terminal; no `Session.revoke` call is needed, and **no per-session event is written** — the skip is carried in the counter and reported by step 6's completion event.
   d. If `invalid(not-known)`: increment [Not Found]; call `Audit Trail.record_action(action_ref=session_not_found_during_cascade, actor_ref=application_actor_ref, credential=application_credential, data={session_token, credential_id, revoked_by_ref})`. This indicates a `session_token` is present in `credential_to_sessions` but absent from the Session store — a data integrity gap that is distinct from a normal terminal-state skip and should surface for investigation.

6. **Record the cascade's completion, closing the initiation event step 3 opened.** `Audit Trail.record_action(action_ref=credential_revocation_cascade_completed, actor_ref=application_actor_ref, credential=application_credential, data={credential_id, initiation_event_id, revoked, skipped, not_found, failures})` — composition-attributed, with the four counters the loop accumulated. **This is what makes cascade completeness checkable at all.** Steps 5b–5d write one event per session that was *acted on*, and step 5c writes none, so the per-session events sum to `session_count − skipped` rather than to `session_count` — a shortfall that is entirely conformant and that a reconciliation over the per-session events alone must read as a missed session. The completion event carries the missing term. Arms: `recording-failure(step)` → the cascade's revocations stand (they committed) and the completion record is **retried until it lands**, with the initiation event left open and surfaced meanwhile — an initiation with no completion is the cascade's own orphan, and it is a finding rather than a failure of the action, which returns its result either way.
7. Return `{revoked: N, skipped: M, not_found: K}`.

### The recovery discipline (the issuance-reconciliation sweep)

The retry-until-lands obligations the actions above declare are not in-process promises — they survive process failure because a restart **sweep re-derives every owed record from durable state**, runs at restart and thereafter until every discrepancy closes, and treats each open discrepancy as a hard alerting condition. Three comparisons, each with its closure:

- **Entry vs. events.** Every `login_event_log` entry whose mirrored audit event is absent is an owed record: the entry is the **durable intent** — truth-bearing for exactly that window (Composition state names the bounded exception), carrying the full payload (`principal_ref`, `credential_type`, `credential_id`, `session_token`, `attempted_at`) the record needs — and the sweep re-emits the event from it (all Login events are composition-attributed, so the re-emission is the same `record_action` the invocation would have made).
- **Sessions vs. records.** Every Session-store session issued under the deployment's declared `issuer_refs` (Configuration) that no login-family event *or* `login_event_log` entry names is the crash window before any intent landed. Nothing is owed to any caller — the dying invocation returned its token to no one, so the orphan is unusable — and nothing can honestly attribute it after the fact, so the sweep **revokes and records it**: `Session.revoke(session_token, revoked_by_ref = application_actor_ref, reason = "unattributed-issuance-recovery")`, then one `orphan_session_revoked` event (composition-attributed, `data = {session_token, principal_ref}` from the Session record's own fields). The conservative arm is deliberate: a session no record names is killed, never adopted.
- **Revocations vs. events.** Every `Revoked` session (under the declared `issuer_refs`) with no revocation-family event is an owed record reconstructible from the Session record itself — `revoked_by_ref` and `reason` are the atom's own stored fields — and the stored reason's `"credential-revocation-cascade: "` prefix decides which record is owed: prefixed → `session_revoked_by_cascade`; otherwise → `logout_succeeded` with `requested_by` from `revoked_by_ref`. The sweep re-emits accordingly, closing the `logout` step-3 and cascade step-5b retry windows across crashes.

The sweep writes no second store: every comparison reads state already durable (the log, the Session store, the trail), and every closure is an ordinary composition-attributed `record_action`.

### Composition-level invariants

**Invariant 1 — Credential gates issuance.** A `session_token` appears in `session_to_credential` only if `Credential.verify(principal_ref, credential_type, presented_material)` returned `verified` during the `login` call that produced it, and that `verify` was the immediately preceding call in the same `login` invocation. There is no path through the composition's action wiring that calls `Session.issue` without first receiving `verified` from `Credential.verify`.

**Invariant 2 — Cascade completeness (snapshot-scoped).** After `revoke_sessions_for_credential(credential_id, ...)` returns, every session that was in the step-2 union *at the time it was read* and was `Active` at the time its cascade step executed is in a terminal state in the Session store — except in the case of a `Session.revoke` `storage-failure` during step 5 (which is recorded in the Audit Trail as `session_revoke_failure_during_cascade` and is an implementation finding, not a conformant terminal state). The cascade guarantee is scoped to the snapshot: sessions landing after the step-2 read are not covered by this invocation and require a subsequent [Revoke Sessions For Credential] call to close. **Single-cascade sufficiency is scoped honestly, and the in-flight window is named:** callers executing a cascade as part of a breach response should confirm that `Credential.revoke` has committed before calling [Revoke Sessions For Credential] — once the credential is terminal, every *subsequent* `Credential.verify` fails, so no login whose verify runs after the revocation can establish a session. What that does **not** cover is a login already in flight: one whose `verify` (and sandwich re-verify) committed *before* the revocation landed can still issue its session and land it in the map and events *after* this cascade's step-2 read — a live session derived from the revoked credential that this cascade never saw. Closure is procedural and records-alone checkable: after in-flight quiescence (a bound the deployment knows — its maximum `login` invocation duration), run a second [Revoke Sessions For Credential]; the second cascade's snapshot includes every straggler, and a post-quiescence read of the event-derived set with every member terminal is the completeness evidence (GA check 3's reconciliation over both cascades).

**Invariant 2a — Cascade coverage (union-defined).** The cascade set for a credential — what [Revoke Sessions For Credential] step 2 reads — is the **union** of the live map entry and the event-derived set (`login_succeeded` ∪ `login_map_write_failure` pairs, via the declared enumerate-and-filter read — *Composes*), and that union contains every `session_token` ever returned by a `login` call that verified against `credential_id`: sessions whose step-5 map write failed are carried by their `login_map_write_failure` events (cascade-covered through the event side, not exiled), and sessions whose step-7 event is still in its retry window are carried by the live map. The one uncovered window is a step-5-failure whose *own* event write is still in its retry — retried as a hard alerting condition until it lands, and durable across crashes: the `success-with-map-failure` entry is the intent the sweep re-emits from (*The recovery discipline*), and a session that predates even the entry is closed by the sweep's revoke-and-record arm. A `login_map_write_failure` event is therefore the canonical signal of **map degradation to remediate** (backfill the map entry so the fast path serves it), not of a cascade-coverage gap; remediation restores the index, never the coverage, which the events already provide.

**Invariant 3 — Session-credential traceability (pinned to the confirmed read).** For every `session_token` in `session_to_credential`, the value `credential_id` is the effective-Active credential for `(principal_ref, credential_type)` **at `login` step 3's read, sandwich-confirmed**: the second `verify` proves the presented material matched that record's verifier on both sides of the read, so a rotation racing the login either forces the step-3 retry or fails the login — no session is ever rooted on a credential id its material never verified against. The mapping is immutable once written. An auditor traces any session to its originating credential through the composition's state or, records-alone, through the `login_succeeded` / `login_map_write_failure` event that carries the same pair.

**Invariant 4 — Login event log completeness.** Every `login` call — regardless of outcome — produces exactly one entry in `login_event_log`. The `outcome` vocabulary is: `success` (session issued, map written), `success-with-map-failure` (session issued but map write failed), `failed-verification(reason)` (credential check failed), `failed-storage-failure(credential-id-lookup)` (step 3 store failure), `failed-storage-failure(credential-id-confirm)` (step 3's exhausted sandwich retry), `failed-storage-failure(session-issue)` (step 4 store failure). An entry with outcome `success` or `success-with-map-failure` has non-null `session_token`; all failure outcomes have null `session_token`. An entry with any outcome other than `failed-verification(reason)` has a non-null `credential_id` (because the credential was verified successfully before the failure point), except for `failed-storage-failure(credential-id-lookup)` and `failed-storage-failure(credential-id-confirm)` entries, which have null `credential_id` (the id could not be retrieved, or could not be confirmed against the presented material).

**Invariant 5 — Audit Trail completeness.** Every `login_succeeded` event in the Audit Trail has a corresponding `session_token` that appears in `session_to_credential`. Every `session_revoked_by_cascade` event in the Audit Trail has a corresponding `session_token` that was in `Active` status in the Session store immediately before the cascade step that produced the event. No Audit Trail event of type `session_revoked_by_cascade` exists without a corresponding `credential_revocation_cascade_initiated` event bearing the same `credential_id` earlier in the substrate's Event Log sequence — the authoritative order; timestamps are advisory.

**Invariant 6 — Map inverse consistency.** `credential_to_sessions` and `session_to_credential` are strict inverses. For every `(credential_id, session_token)` pair in `credential_to_sessions`, the entry `session_to_credential[session_token] = credential_id` exists. For every `(session_token, credential_id)` pair in `session_to_credential`, `session_token` appears in `credential_to_sessions[credential_id]`. A discrepancy between the two maps is evidence of a non-atomic implementation of `login` step 5 — the two writes are one transaction by contract, so a half-committed pair cannot come from a conforming run.

## Examples

### Successful login and session use

A user enters their password in a financial system. The host system calls `login(principal_ref: user_u91, credential_type: "password", presented_material: <raw-password>, issued_by_ref: login_svc_l01)`.

Step 2: `Credential.verify(user_u91, "password", <raw-password>) → verified`. Step 3: credential store query returns `credential_id: cred_c01`. Step 4: `Session.issue(user_u91, login_svc_l01, 3600) → session_token: tok_abc123`. Step 5: `credential_to_sessions[cred_c01]` = `{tok_abc123}`; `session_to_credential[tok_abc123]` = `cred_c01`. Steps 6–7: `login_event_log` entry and Audit Trail `login_succeeded` event recorded. Return: `tok_abc123`.

The host system sets a session cookie. On the next request, the host system (or Privileged Access Provisioning) calls `Session.validate(tok_abc123) → valid(principal_ref: user_u91, expires_at: 2026-09-01T11:00:00Z)`.

### Failed login — wrong password

The user enters an incorrect password. `login(user_u91, "password", <wrong-password>, login_svc_l01)`. Step 2: `Credential.verify → failed-verification(material-mismatch)`. Step 2 path: `login_event_log` entry with `outcome: failed-verification(material-mismatch)`; Audit Trail `login_failed` event. Return: `rejected(credential-invalid)`. No session is issued; no entry appears in `credential_to_sessions` or `session_to_credential`.

### Logout

The user clicks "Log out." The host system calls `logout(session_token: tok_abc123, actor_ref: user_u91, reason: "user-initiated-logout")`. Step 2: `Session.revoke(tok_abc123, user_u91, "user-initiated-logout") → revoked`. Step 3: Audit Trail `logout_succeeded` (composition-attributed; `requested_by: user_u91` in the data). Return: `logged-out`. Subsequent `Session.validate(tok_abc123) → invalid(revoked)`.

### Cascading revocation — compromise response

An incident-response team determines that `cred_c01` (user_u91's password credential) was likely compromised. The identity-management surface calls `Credential.revoke(cred_c01, revoked_by_ref: security_team_s01, reason: "suspected-compromise-2026-09-12")`. The response team then calls `revoke_sessions_for_credential(credential_id: cred_c01, revoked_by_ref: security_team_s01, reason: "suspected-compromise-2026-09-12")`.

Step 2: `credential_to_sessions[cred_c01]` = `{tok_abc123, tok_def456}` (two sessions were issued over the credential's lifetime). Step 3: Audit Trail `credential_revocation_cascade_initiated` event for `cred_c01`, `session_count: 2`. Step 5a — `tok_abc123`: `Session.validate → valid(...)` → `Session.revoke(tok_abc123, security_team_s01, "credential-revocation-cascade: suspected-compromise-2026-09-12") → revoked`; Audit Trail `session_revoked_by_cascade`. Step 5b — `tok_def456`: `Session.validate → invalid(expired)` → skipped (dead by derivation; no revocation write needed). Return: `{revoked: 1, skipped: 1, not_found: 0}`.

Any subsequent Privileged Access Provisioning `exercise_access` call under `tok_abc123` will return `rejected(session-invalid)` at step 1, before the Capability is presented.

### Regulated adversarial scenarios

Three scenarios the composition must survive in regulated contexts:

**Regulator audit.** A SOX (Sarbanes-Oxley Act) auditor asks *"was the session used to exercise access to financial control Final Critique 789 at 09:14 on 2026-10-15 established under a valid, non-revoked credential?"* The auditor reads the Privileged Access Provisioning `session_access_log` to find `session_token: tok_abc123` was used at that time. The auditor queries `session_to_credential[tok_abc123]` → `credential_id: cred_c01`. The auditor reads the Credential store: `cred_c01` was `Active` at `09:14` (it was revoked at `11:40` on the same day, after the access). The Audit Trail's `login_succeeded` event for `tok_abc123` shows `attempted_at: 2026-10-15T08:52:00Z`, `credential_id: cred_c01`, `principal_ref: user_u91` in its data. Invariant 1 (credential gates issuance) is the structural guarantee that the session could not exist without a prior verified credential. The auditor has their answer from the records alone.

**Disputed login event.** A user claims *"I did not log in from that location at 03:00 AM on 2026-11-20."* The investigator queries the `login_event_log` for `principal_ref: user_u91` on that date. The entry shows `attempted_at: 2026-11-20T03:00:12Z`, `outcome: success`, `credential_id: cred_c01`, `session_token: tok_xyz789`. The Audit Trail's `login_succeeded` event corroborates the timestamp and credential used. Credential's Invariant 3 (sole-holder verification) means the presented material matched the verifier registered for user_u91's password credential — the login succeeded because someone presented the correct password. Whether that was the legitimate user or an attacker with the compromised password is a separate investigation; Login's records bound the forensic window: the session was issued at `03:00:12Z` after a successful credential check.

**Breach investigation — cascade completeness.** A security team is investigating a credential compromise. They ask *"how many active sessions were revoked when we cascaded the revocation of cred_c01, and is there any evidence that any session slipped through?"* The Audit Trail shows: `credential_revocation_cascade_initiated` at `2026-12-03T14:22:00Z` for `cred_c01`, `session_count: 5`. Five subsequent `session_revoked_by_cascade` events appear, each naming a distinct `session_token`. There are no `login_map_write_failure` events for `cred_c01`. Invariant 2 (cascade completeness) is the structural guarantee: all 5 sessions are accounted for. The investigator can confirm by querying `credential_to_sessions[cred_c01]` directly — 5 entries, each with `Session.validate → invalid(...)`. Cascade is confirmed complete.

## Edge cases and explicit non-goals

What this composition does not cover:

- **Multi-factor authentication.** This composition verifies one credential of one type per `login` call. Requiring a principal to satisfy two or more credential checks before a session is issued — password then TOTP (Time-based One-Time Password), hardware key then PIN — is handled at the composing-pattern layer, beyond Login's scope. A multi-factor login composition would call `Credential.verify` twice (for different `credential_type` values) before calling `Session.issue`, and would carry its own cascade map across both credential types.
- **Credential registration, rotation, and revocation.** Login does not call `Credential.register`, `rotate`, or `revoke`. Those are the identity-management surface's actions. [Revoke Sessions For Credential] handles the downstream cascade after an external revocation; it does not initiate the credential revocation.
- **Failed-attempt tracking and account lockout.** Login records every failed attempt in `login_event_log` and (if configured) in the Audit Trail, but it does not count failed attempts, implement exponential backoff, or lock credentials after N failures. Those are handled at the deployment layer. A deployment that wants lockout must add a rate-limiting or lockout layer above this composition that inspects `login_event_log` and decides when to reject further `login` calls for a given `principal_ref`.
- **Session renewal and sliding-window expiry.** Login issues a session with a fixed `expires_at`. Sliding-window renewal — where the session's effective expiry extends on each active request — requires the composing layer to call `login` again (producing a new session) and revoke the old one, delivering the new token to the caller. Login provides the primitives; the renewal policy belongs to the composing layer.
- **Session validation on incoming requests.** Callers needing to validate a session on each request call `Session.validate(session_token)` directly. Login does not re-expose a `validate_session` action. Compositions that gate actions on session validity (Privileged Access Provisioning, Session-Gated Authorization) call `Session.validate` directly, not through Login.
- **Credential recovery and account recovery.** Reset-by-email, backup codes, recovery keys — these flows produce new `credential_material` that is then rotated in via `Credential.rotate`. Login sees only the normal `login` call after recovery is complete; it is not involved in the recovery flow itself.
- **Concurrent session limits.** Login imposes no limit on how many Active sessions a given `principal_ref` may have simultaneously. A principal who logs in from five devices has five active sessions. Enforcing a per-principal session limit requires the composing layer to query `credential_to_sessions` or the Session store and revoke excess sessions before issuing new ones.
- **Credential-revocation initiation.** [Revoke Sessions For Credential] is the cascade action; it does not call `Credential.revoke`. The caller is responsible for revoking the credential through Credential's own surface before calling the cascade action. A deployment that calls [Revoke Sessions For Credential] without first revoking the credential has revoked the sessions but left the credential Active — the principal can still log in and get a new session. The correct sequence is always `Credential.revoke` then [Revoke Sessions For Credential].
- **In-flight logins racing a credential revocation.** `Credential.revoke` forecloses *future* verifies, not a `login` already past its verify: a call whose sandwich-confirmed verify committed before the revocation landed can issue its session after the breach team's cascade has taken its snapshot (Invariant 2's named in-flight window). The procedural closure is part of the breach runbook, not the wiring: revoke the credential, cascade once, wait out the deployment's maximum login duration, cascade again — the second snapshot contains every straggler, and the GA check-3 reconciliation over both cascades plus a post-quiescence all-terminal read of the event-derived set is the records-alone completeness evidence.

- **Device binding and session fixation protection.** Whether a session token is bound to a device fingerprint, IP address, or browser context is handled at the composing-pattern layer. Login stores no device information. Session fixation defense (ensuring a pre-authentication session token is not re-used post-authentication) requires the composing deployment to generate a fresh `session_token` after authentication, which is the default: `Session.issue` always generates a fresh `session_token`.
- **Authorization to perform logout.** Login does not verify that `actor_ref` has the right to terminate `session_token`. It accepts any non-null, non-empty `actor_ref` supplied by the caller and passes it to `Session.revoke` as the revocation actor. Whether `actor_ref` must be the session's own `principal_ref`, an administrator, or any authenticated caller is a Permissions decision the composing layer must enforce before calling `logout`. A deployment that exposes `logout` without an upstream authorization check allows any caller with a valid `actor_ref` to terminate any session they know the token for. The Audit Trail records who called `logout` (`actor_ref`) and which session was terminated, providing the forensic record regardless of whether the revocation was authorized by the principal or by an administrator.
- **Credential rotation and session cascade.** [Revoke Sessions For Credential] works identically whether the named `credential_id` is in `Revoked` or `Rotated` status — the composition does not check the credential's current status before cascading. Callers who rotate a credential (via `Credential.rotate`) may choose to cascade sessions established under the old credential or preserve them briefly for graceful handoff. The correct sequence for rotation-with-cascade is: call `Credential.rotate` (old credential goes to `Rotated`), then call `revoke_sessions_for_credential(old_credential_id, ...)`. New sessions will be established under the new `credential_id`, which has a separate cascade map entry.
- **OpenID Connect and federated identity.** External identity providers (IdPs) present a different authentication model: the credential verification happens at the IdP, and the composing system receives a signed assertion rather than raw credential material. Wiring an OIDC authorization-code flow into this composition's `login` action requires treating the IdP's signed assertion as the `presented_material` and registering a verifier-derivation function that validates OIDC ID tokens. The atom and composition mechanics are the same; the derivation function is the deployment-configured extension point.

#### Revoke Sessions For Credential

The composition's load-bearing emergent action: given a `credential_id`, it walks `credential_to_sessions[credential_id]` and revokes every still-`Active` derived session through `Session.revoke`, recording an initiation event and one cascade event per session in the Audit Trail. Returns `{revoked, skipped, not_found}` (the snapshot accounting), or an inherited rejection. Called *after* an external `Credential.revoke`; it never revokes the credential itself. Neither constituent carries this cascade.

Kind: Operation

#### Credential Invalid

The composition's own `login` rejection — returned when `Credential.verify` fails (`failed-verification(reason)`): the credential check did not pass, so no session is issued and a failed-login event is recorded. The observable form of the credential-gates-issuance boundary (Invariant 1).

Kind:      Member
Member of: the login rejection
Role:      Rejection
Projects:  credential-invalid

#### Outcome

The `login_event_log` entry's classification of a `login` call: one of `success`, [Success With Map Failure], `failed-verification(reason)`, or [Failed Storage Failure]. Every `login` call appends exactly one entry (Invariant 4), giving the composition a records-alone query surface alongside the tamper-evident Audit Trail.

Kind:      Field
Field of:  the login-event-log entry
Role:      the login-attempt classification
Projects:  outcome

#### Success With Map Failure

The [Outcome] for the load-bearing step-5 asymmetry: `Session.issue` succeeded and the session was returned to the caller, but the cascade-map write failed. The session is valid but not covered by cascade revocation (Invariant 2a); a `login_map_write_failure` Audit Trail event is the canonical remediation signal.

Kind:      Member
Member of: the login outcome
Role:      Outcome

## Standards references

- **NIST (National Institute of Standards and Technology — US federal standards body) SP 800-63B §7 (Session Management)** — the primary standard for session lifecycle in authenticated systems. The composition's `login → Session.issue` wiring implements the session binding requirement; `logout → Session.revoke` implements the session termination requirement. The [Revoke Sessions For Credential] cascade implements the reauthentication-on-credential-change requirement: when a credential is revoked, all dependent sessions must be terminated.
- **NIST SP 800-53 AC-12 (Session Termination)** — requires that sessions terminate after a defined condition. The composition's `logout` and [Revoke Sessions For Credential] actions are the two termination surfaces; the `expires_at` immutability of Session is the time-bounded termination mechanism.
- **OWASP ASVS V3.1 (Authentication) and V3.3 (Session Termination)** — the OWASP (Open Worldwide Application Security Project) Application Security Verification Standard; the `login` action's sequencing (verify then issue, with failed attempts recorded) and `logout`'s full revocation (not just cookie deletion) correspond to ASVS requirements for authentication event logging and session invalidation on logout.
- **GDPR (EU General Data Protection Regulation — the European Union's data-privacy law) Article 32 (Security of Processing)** — the `login_event_log` and Audit Trail recording of all authentication events, including failures, contribute to the "appropriate technical measures" Article 32 requires. The [Revoke Sessions For Credential] cascade is a breach-response mechanism that reduces the blast radius of a compromised credential.
- **HIPAA (US Health Insurance Portability and Accountability Act) §164.312(d) (Person or Entity Authentication)** — the composition's `Credential.verify → Session.issue` wiring is the structural implementation of this requirement: a session is issued only after the principal's identity is confirmed. The Audit Trail records the authentication event for post-incident investigation.
- **PCI DSS (Payment Card Industry Data Security Standard — the card networks' mandatory security rules for cardholder data) Requirement 8.2 (User Identification and Authentication)** and **Requirement 8.6 (Session Management)** — authentication event logging (all login attempts, successful and failed), session termination on logout, and revocation on credential change correspond to PCI DSS structural requirements. The `login_event_log` is the composition-layer record; the Audit Trail is the tamper-evident external-auditor record.
- **SOX §302 / §404 (Internal Controls)** — the `credential_to_sessions` map and its cascade action are the structural mechanism for ensuring that a compromised credential's access window can be closed completely and auditedly. - **OpenID Connect Core 1.0** — the composition is the Grace Commons expression of the OIDC (OpenID Connect — an identity layer built on OAuth 2.0) login flow: authorization code exchange (credential verification), session establishment (session issuance), and session revocation on logout or token revocation. ## Generation acceptance

A derived implementation of Login is *acceptable* — in the regulator-acceptance sense — when an external auditor, given the composition's state (`credential_to_sessions`, `session_to_credential`, `login_event_log`) and the constituent atoms' stores (Session records, Audit Trail events), can do all of the following without recourse to source code, runbooks, or developer narration — every Audit Trail query below reading the substrate through the declared enumerate-and-filter capability (*Composes*), with no payload-index surface assumed:

- **Verify that every session in `session_to_credential` has a corresponding `login_succeeded` Audit Trail event.** For every `(session_token, credential_id)` pair in `session_to_credential`, confirm that the Audit Trail contains a `login_succeeded` event with matching `session_token` and `credential_id`. A session in `session_to_credential` without a corresponding `login_succeeded` event is evidence of a bypass of the credential-gates-issuance invariant (Invariant 1) — outside the step-7 retry window (the rebuild boundary: the entry's event lands with the retried write, and the standing alert is the interim signal; the gap is a finding once that retry has quiesced).
- **Verify map inverse consistency.** For every `(credential_id, session_token)` pair in `credential_to_sessions`, confirm that `session_to_credential[session_token] = credential_id`. For every `(session_token, credential_id)` pair in `session_to_credential`, confirm that `session_token` appears in `credential_to_sessions[credential_id]`. Any discrepancy is a map write failure (step 5 of `login`) and is a finding.
- **Verify cascade completeness for any credential revocation event.** For any `credential_revocation_cascade_initiated` Audit Trail event with `credential_id = C` and `session_count = N`, resolve its `credential_revocation_cascade_completed` event (matching `initiation_event_id`) and reconcile **per cascade, in two equations**. First, the per-session events account for the acts: the sum of subsequent `session_revoked_by_cascade`, `session_revoke_failure_during_cascade`, and `session_not_found_during_cascade` events carrying that `initiation_event_id` equals `revoked + failures + not_found` from the completion event's counters. Second, the snapshot is accounted for in full: `session_count = revoked + skipped + failures + not_found`. **Reconciling the per-session events directly against `N` is wrong and was the earlier form of this check** — step 5c writes no event for an already-terminal session, so that sum equals `N − skipped` on every conformant cascade, and it fails maximally on exactly the case the runbook prescribes (a second cascade after in-flight quiescence, which is mostly skips by design). The `skipped` term has no per-session event by construction; the completion event is the only place it exists. An initiation event with **no** completion event is a distinct finding — the cascade did not finish recording — and must not be read as a coverage failure of the sessions themselves. Confirm that all `session_token` values from `session_revoked_by_cascade` events are in a terminal status in the Session store (`Revoked`). `session_revoke_failure_during_cascade` and `session_not_found_during_cascade` events are findings requiring remediation; their presence does not satisfy cascade completeness. An Active session in `credential_to_sessions[C]` after a cascade that has no corresponding `session_revoke_failure_during_cascade` event is evidence of a cascade implementation defect (missed session) or a post-cascade concurrent login (requires a second cascade call per Invariant 2's snapshot-scoped guarantee).
- **Verify login event log and Audit Trail consistency.** For every `login_event_log` entry with `outcome = success`, confirm that the Audit Trail contains a `login_succeeded` event with matching `session_token` and `credential_id`. For every entry with `outcome = success-with-map-failure`, confirm that the Audit Trail contains a `login_map_write_failure` event with matching `session_token` and `credential_id`. A success entry without a corresponding Audit Trail event is evidence of an Audit Trail write failure during `login` step 7; a `success-with-map-failure` entry without a corresponding Audit Trail event is evidence of an Audit Trail write failure during the step-5 failure branch. Either is a finding once its retry-until-lands discipline has quiesced; while the retry stands, the hard alert is the surfaced interim state.
- **Reconstruct the session history for any principal.** Given a `principal_ref`, query `login_event_log` for all entries with that `principal_ref`. For each entry with `outcome = success` or `outcome = success-with-map-failure`, follow `session_token` to the Session store to determine the session's current status and `expires_at`. The result is a complete timeline of: when the principal authenticated, with which credential, which session was issued, whether the session was revoked (and by what mechanism), and whether the session expired naturally. No external data source is required.
- **Confirm all `login_map_write_failure` events are resolved.** Enumerate the substrate (the declared read) and select the `login_map_write_failure` events. For each, confirm one of: (a) the named `session_token` has been manually reconciled into `credential_to_sessions` and `session_to_credential` via a remediation process, or (b) the session is dead — stored `Revoked`, or lapsed, its `Session.validate` reading `invalid(expired)` by the atom's derived-expiry projection (there is no stored Expired state). An unresolved `login_map_write_failure` event with an Active session in the Session store represents map degradation to remediate — the session stays cascade-covered through the event side (Invariant 2a's union), but the fast-path map under-serves it until the backfill lands; the unremediated event is the open finding.
- **Verify the store-to-records direction.** Enumerate the Session store's sessions issued under the deployment's declared `issuer_refs`: every one is named by a login-family event or a `login_event_log` entry, or by an `orphan_session_revoked` recovery event (the sweep's revoke-and-record closure); every `Revoked` session has its revocation-family event (`logout_succeeded` or `session_revoked_by_cascade`, per the stored reason's cascade prefix). A session none of those name — outside the sweep's open retry windows, which stand as hard alerts — is a finding: an issuance or revocation the records cannot account for. This is the direction the record-to-store checks above cannot see, and the sweep's own comparisons are exactly this check run from inside.

This is the generator's contract: any implementation derived from this composition must produce state that passes all six checks above. The bar is the regulator's question — *"can you prove that every session in this system was established under a verified credential, and that every session derived from a revoked credential was terminated?"* — not the developer's intuition.

## Decisions

Directional changes only — the turns a future reader must know the pattern took, and why. Everything smaller lives in the commit that made it: `git log -- compositions/login.md`.

- **2026-08-26 — Every Login event is composition-attributed.** *Chose:* attest under `application_actor_ref` / `application_credential`, with the human parties in `data`. *Over:* attesting under the principal's own credential. *Because:* Login's callers are end principals whose material is the thing under test, not registry actors — and a failed login has no valid credential to attest with. This governs every audit write the pattern makes.
- **2026-08-26 — Invariant 2 promises less than it did.** *Chose:* cascade completeness is claimed only for verifies that committed after the revocation, with the in-flight window named and a second cascade prescribed after quiescence. *Over:* single-cascade sufficiency. *Because:* a login whose verify committed before the revocation can land its session after the cascade's snapshot, and no single cascade can see it. The headline guarantee is narrower and true.
