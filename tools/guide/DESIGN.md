# Guided Decomposition Tool — Design

> **Design doc, not built.** It specifies the tool before any code — the discipline the tool teaches (the spec is canonical; code is derived). It carries no Status line or Lineage because it is a tool-design doc, not a library pattern. It has been pressure-tested three times: a correctness Super-Torvalds pass (8 foundational findings → v2), a **UX Super-Torvalds pass** (→ v3), and a **fresh-reader adversarial pass** (4 foundational + 22 further findings → v4); **v5** then reorganizes the arc into **four explicit phases — Authoring, Review, Formalise, Submit** — separating review, formalisation, and submission so each is resumable and separately automatable, under an explicit **one-way navigation model** (a linear super-wizard with rewind-to-flag and fractal sub-wizards) (no load-bearing machinery dropped; the settled decisions below unchanged). Three decisions are now settled and shape everything below: **(1)** the tool has a deterministic core *and* an **opt-in AI challenger** — a live reviewer that interrogates the user's answers but never supplies them; **(2)** v1 serves the **outsider** audience for real, not just contributors; **(3)** the tool's product is **authoring plus a submission candidate** — grounding is a library function, and the outsider's path to it is submission. All are recorded under *Design review*. The acceptance bar is the closing line, now joined by a user-facing one: a newcomer must be able to *finish* — verified before code (see *the user-success bar*).

---

## Purpose

The library's bottleneck asset is the **decomposition discipline** — give every concept one home, name what each piece is, attack each piece before trusting it. It is a skill, which is what makes it both scarce and a bottleneck. (Not a *moat* — [`the-spec-layer.md`](../../the-spec-layer.md) assigns that word to proprietary domain patterns; the commons is deliberately the commodity layer.) This tool transfers it.

The honest mechanism, learned from the UX review: a tool that only *asks* and records is a blank form with anxiety — it ships the hard part back to the person who came for help. The skill does not live in the first question ("does this have its own state machine?"); it lives in the **second** one ("you said no — then what owns the `approved` → `revoked` transition you just wrote?"). So the tool is two things at once: a **deterministic core** that asks the right questions in the right order, retrieves, lints, and scaffolds — and an **opt-in AI challenger** that asks the second question, the way a fresh-reader does in Pass 3. The core guarantees completeness and ordering; the challenger raises the floor of the answers. Together they transfer the discipline; neither alone does.

**Who it is for — the outsider.** The tool is designed to the *hardest* reader's bar: someone applying the method to their own domain with no library vocabulary. Contributors are not a second design target and need no separate mode. A fluent contributor either **works raw** — hand-authoring with the full manual discipline, the way the library's own authors do (decompose in their head, draft directly, run councils) — or uses this same tool, where the tiered output lets them skim at speed. Designing for the outsider covers the contributor for free; the reverse is not true, and the v2 design's quiet failure was building for the contributor and *calling* it the outsider's tool. There is one tool, aimed at the demanding case.

---

## What the tool is — and the two things it never does

**The deterministic core.** Elicits the candidate list, retrieves catalog matches, walks the required sections, runs mechanical lint, records answers, scaffolds the draft. Zero npm dependencies (Node built-ins only), fully functional **offline**. This is the spine; everything works without a network.

**The AI challenger (opt-in).** A live reviewer that reads what the user wrote and **interrogates** it — plays the Pass-3 postures against their own prose, flags likely over-absorption, asks the sharper follow-up, makes them defend a cut. It runs through Node's built-in `fetch` against a configured AI endpoint (the user's own key, or, for in-tree runs, the repo's local config — see *Form and fit*), so it adds no package dependency; absent a configured endpoint — or one that fails mid-run (timeout, error, malformed output) — the tool degrades cleanly to the deterministic core, from that point on if need be, and the closing report says so; the challenger can never block a run. The challenger is the project's *own* discipline made live: the methodology requires an AI fresh-reader at the close (the Final Critique is AI-conducted and required for grounding) because authors rationalize past their own gaps. The challenger pulls that scrutiny forward into the authoring sitting, in non-binding form — strictly additive to the author-led Round 1 the methodology already expects, and the only fresh reader an outsider gets before submission.

**The two hard nevers** — the guardrails that keep the challenger a *guide*, not an oracle:

1. **It never mints `grounded`.** Status ceiling is `partially resolved`. (Below.)
2. **It never *answers*.** It does not propose spec content, does not decide atom-vs-composition, does not classify a finding's severity, does not close a finding, and does not block progress. Its challenges land in the draft's Lineage notes as *open questions the user chose to carry or resolve* — and the never is structural, not prompt-deep: challenger output is parsed as question items and rendered only into Lineage's open questions; no code path inserts challenger text into a section body. This is the bright line against the answer-giver tool (branch b), which would let a novice rubber-stamp a confident-wrong spec with nice headings and dissolve the discipline. The one exception is **catalog retrieval** — surfacing candidate existing atoms and compositions by search — which is information, not judgment, and ships even in the no-AI core.

The split between *"never answers"* (a principle) and *"never asks a responsive follow-up"* (a UX cop-out) is deliberate: the tool asks and challenges; it does not answer or adjudicate.

## The bar the tool must never cross

A single interactive sitting is **one author-led round**, even with the challenger raising its quality — not the 3×3 baseline plus an independent fresh-reader Final Critique plus (for vote-yes) a verified model that grounding requires. So the tool's output is honestly partial: a **`partially resolved`** draft, with the independent review and the formal layer deferred and queued. Grounding is never the tool's to grant — it is the outcome of the batch lane. The challenger improves the draft and gives an outsider a *real* fresh-reader pass they otherwise could not get; it does not substitute for the canonical, independent Final Critique that grounding still demands.

---

## Two lanes

**Lane A — interactive, fast (this tool).** Decompose → author → one author-led round (with the opt-in challenger) → cast the formal-layer vote. Output: a `partially resolved` draft, findings in its Lineage notes, and queue entries.

**Lane B — batch, asynchronous.** Drains the queues: the **review queue** (the independent Final Critique grounding requires) and the **formal queue** (the model — council-authored, verified through [`tools/harness/`](../harness/)). Grounding happens here. **Failure branch:** a deferred model that finds a counterexample is conflict-protocol case 1 — fix the English, re-verify, take a touch-triggered re-pass, and, where the fix is a breaking change, cascade-downgrade the compositions naming the pattern per the constituent-change cascade (additive fixes do not cascade). Deferring the model does not defer the consequences of it failing.

**For the outsider, Lane B must be reachable, not an institution they lack.** A contributor's queues are drained by the council and harness. An outsider has neither — so the tool gives them two exits, both honest. **Private use:** the review-queue entry is emitted as a **human-runnable critique brief** — a self-contained prompt they can paste, with their draft and the constituent specs it names, into any capable AI for an independent fresh-reader critique, plus plain instructions for reading the findings back. It is the same challenger run once more at the end in a fresh context — a real independent review, *not* the canonical Final Critique: `grounded` is a library status, minted only by the library's own machinery, and a private pattern simply never claims it. **Submission:** for a pattern aimed at the commons, the run's bundle — draft, decomposition map, Lineage, queue entries — *is* a submission candidate, entering the contribution lifecycle at Draft with Round 1 evidenced ([`contributing.md`](../../contributing.md) §How to contribute); the queue entries travel with it as work orders, so the library's council and harness drain them on admission exactly as for in-tree runs — which is how a vote-yes outsider's model obligation reaches the harness it needs. Submission is not admission: the quality bar and any admission mechanics belong to the library ([`governance.md`](../../governance.md) holds the draft proposal); the tool's job is to make the candidate strong. Either way, the outsider's deferred payoff is addressed to an action they can take.

## The arc — four explicit phases

The tool is organized as four explicit phases. Each answers a distinct question, emits specific artifacts, and can be resumed independently. The separation exists for three reasons: to make the outsider journey understandable; to keep responsibilities distinct; and to let future implementation and automation decisions be made phase-by-phase rather than against one monolithic workflow. The tool's purpose is not to produce grounded patterns — it is to help an author produce a **submission candidate** and the supporting artifacts the library's review and formal processes require.

### Phase 1 — Authoring

**Question: what are we building?** **Goal:** transform domain knowledge into a structured decomposition and a first-draft specification. The phase is author-led and understands the domain before writing the pattern; it is a **loop, not a line** (add, edit, merge, split, re-triage), because triaging candidate five routinely reveals that candidate two was two candidate concepts.

**1a — Elicit the pieces (the first mile, now designed).** The hardest step is getting the candidate list *out* of the user, and it cannot be assumed. The tool runs **domain-walking probes** — *What records exist in this domain? Who acts on them, and how? What must never be allowed to happen? What would an auditor or regulator ask you to prove?* — each answer emitting **candidate concepts** (a stage, not a kind: pre-triage items destined to be promoted or rejected) into a **visible, editable list** before any triage begins.

**1b — Retrieve, don't assign homework.** For each candidate, the tool **surfaces** the closest existing patterns — keyword-matching the candidate statement against atom *and composition* summary blockquotes and showing the top few with one-line descriptions — and asks *reuse / extend / new / reject* (reject = not a concept at all — a quality attribute, implementation residue, or noise; rejected candidates are recorded in the decomposition map, so elicitation lineage stays complete even when the answer is "this isn't a concept"). A newcomer cannot be expected to know their "history of who approved what" is **Event Log**; the tool shows them the candidate rather than sending them to read the catalog. This is retrieval, not judgment — the user still decides — and it is what stops a novice re-minting Event Log, Actor Identity, and Audit Trail under new names.

**1c — Triage, with worked examples.** For a genuinely new candidate, the directory-placement test (*does the specification name another pattern?* → composition vs atom, quoted per [`contributing.md`](../../contributing.md) §Workflow) and the EOS (Essence of Software — the methodology's conceptual-independence lens) extraction questions (own state machine? recurs across domains? host specifiable without it? would another concept that needs it reinvent it?). **Every judgment question ships one concrete yes-instance and one no-instance** drawn from the library's worked examples (Personal Todo, Duplicate Prevention) — because defining "state machine" does not tell a user whether *theirs* has one; a matched pair of examples does. Composition matches from the retrieval step trigger the composition-layer extraction gate's *consideration* only — the gate decides by its own conjunction (invariant-level recurrence, never the surface similarity a keyword match constitutes; `pressure-testing.md` §The composition-layer extraction gate).

**Phase 1 is a loop over a mutable list** — add, edit, **merge, split, re-triage** — because triaging candidate five routinely reveals that candidate two was actually two concepts. A wizard with no back button fossilizes first guesses; this phase has one. **Exit invariant: Phase 1 is complete when the candidate list is empty** — every candidate promoted into the decomposition map or rejected into it. The stage cannot outlive the phase, because the pipeline consumes the object: no post-triage surface has anything left to call a candidate — the same design move as routing challenger output only into Lineage's open questions (make drift structurally impossible; don't ask authors to remember).

**Emits so far:** `<domain>.decomposition.md` (see *Artifacts*).

**1d — Draft the spec.** Walk the required sections in order for the chosen pattern's shape, per [`spec-format.md`](../../spec-format.md), each prompt carrying its governing convention inline. **Prose sections open in `$EDITOR`** (a temp file seeded with the prompt and conventions as comments) rather than fighting a single-line prompt; short answers stay inline. A run may **resume**: re-ingesting a partial scaffold and skipping filled sections, so the multi-hour arc is not a mandatory single sitting. At pattern choice the tool emits a **session plan** — *"this composition needs atoms A and B first; that's roughly three sittings, in this order"* — turning the atoms-before-compositions ordering constraint from an ambush into a roadmap. The Summary (Tier 1) is written at grounding, not draft time, and is skipped here.

**The structural-relation sub-flow (compositions).** When authoring a composition's invariants, the deterministic core watches for relational language — *owns, contains, belongs to, member of, parent/child of* — and, on a hit, **forces a structural-relation declaration** rather than letting the relation stay loose: pick its **cardinality** (one-to-one / one-to-many / many-to-many) and the **modality** of each side (mandatory / optional). From those two answers the core auto-inserts the required invariants in the canonical phrasing owned by [`spec-format.md`](../../spec-format.md) §Cross-cutting authoring conventions (referential integrity; orphan-freedom *only where a side is mandatory*, in its conditional at-quiescence form — safety plus liveness, modulo declared compensation and the retention horizon, never a static "always both sides"; inverse consistency), seeds the relation's **composition-state classification** at *derived index* (the default — the inverse is rebuilt from the forward references, not a second stored map), seeds the **Alloy multiplicity** for the formal-queue entry, and queues an auto-generated **orphan / dangling-reference / inverse-inconsistency buggy-twin** scenario. This makes executable the **Pass 3 *Relations* checklist line** (`pressure-testing.md`) — vocabulary that is precise and universally legible (data-modeling cardinality, not new jargon), with *maintenance* deferred to the composition-state rule so the tool never nudges an author toward a stored dual-write. (The rule landed as a single Pass 3 bullet rather than a standalone convention — smallest machinery that closes the gap; the tool enforces that one line.) The **challenger** then interrogates the relation a deterministic check cannot: *"you declared one-to-many, parent mandatory — show me the action that could leave a child with no parent; if none can, what structurally prevents it?"* and *"is the inverse derived or stored? if stored, justify the second map against the composition-state rule."*

**Emits:** the decomposition map; `<name>.md` (canonical section order, answers filled, thin sections marked `not-yet-drafted`, a seeded `## Lineage notes`); initial Lineage notes; and a **session plan** when the pattern's dependency set needs more than one sitting.

The deterministic core owns the flow. The opt-in challenger may interrogate assumptions and ask clarifying questions but **shall not** answer on the author's behalf, write pattern content, resolve findings, or mint `grounded` claims.

**Exit condition:** the author can explain and defend the decomposition the draft represents.

### Phase 2 — Review

**Question: is the candidate any good?** **Goal:** pressure-test it before independent review — not to prove correctness, but to expose weaknesses, ambiguities, omissions, and unresolved assumptions. The phase stays author-led but adopts a reviewer posture.

Run the three passes, recording findings **into the draft's Lineage notes** (the canonical home — a standalone review file alongside the pattern is a documented process error), per-finding `F-id — short name — class → fix`.

- **Pass 1 — GRID** (the methodology's nine-checkpoint completeness framework) + the mechanical lint the core can run without judgment: section presence and order, undefined acronyms, dangling cross-references, Tier-1 Summary cleanliness if present. (Rule ownership: [`tools/linter/lint.py`](../linter/lint.py) is the corpus's mechanical checker and continuous-integration gate; the guide reimplements the draft-local subset because out-of-tree drafts never reach that gate — the shared dangling-reference rule is the linter's, knowingly mirrored.)
- **Pass 2 — EOS** extraction questions, re-run against what was written.
- **Pass 3 — Linus.** The three postures are **forced per-section prompts**, not an open invitation to find nothing — *"what would the cheapest-compliant implementer do with this `approve()` signature?"* And where configured, the **AI challenger** conducts a live fresh-reader interrogation here: a *fresh context* — a new conversation given only the pass question sets and the draft, never the authoring session's transcript — reads the draft cold and pushes back, its challenges recorded in Lineage as open questions.
**The exit gate is decoupled from self-graded severity.** Blocking a draft's progress on a finding the *user* labeled "foundational" creates a fatigue-hour incentive to downgrade — teaching the opposite of the discipline. Instead: any finding may be explicitly **carried out as open, deferred to the Final Critique**, recorded as such in Lineage. The Final Critique consumes carries in **two steps** — the full fresh-reader pass first, with the carried items withheld so fresh-reader discipline holds; the carried items opened and adjudicated only after that pass closes. The critique brief encodes the same order for outsiders. Honesty about a finding never costs the user their exit; the unresolved-and-*unacknowledged* draft is the only one held back. No finding may silently disappear: every one is resolved or explicitly carried.

**Emits:** the updated draft, the findings record, open questions, updated Lineage notes. **Exit condition:** every finding is resolved or explicitly carried.

### Phase 3 — Formalise

**Question: does this candidate require formal verification work?** **Goal:** capture the formalization decision honestly and prepare the downstream work. The tool does not verify — it identifies where verification is justified and prepares the work items, and **shall not** claim verification has occurred.

- **The formal-layer vote**, asked in **plain-language probes** the user can actually answer — *Can two of these actions happen at the same time? Does the order of steps ever change what's allowed? Is there a moment where a half-finished action would break a rule? Does a clock, window, or deadline change what an action is allowed to do?* — from which the yes/no is derived and shown back for confirmation. No outsider can parse "load-bearing temporal claims" cold. (The probes deliberately encode the practiced bar, not just the vote's written definition: the 2026-06-03 bar reconsideration grounds window-only patterns with no action-vs-action race English-only, so the clock probe feeds the rationale while a race found by the first probe is what flips the vote.)

The tool then records the vote and recommends a status per §Status ceiling — never higher than `partially resolved`, and never `draft`, which by the pinned grammar means the foundation round has not run (false the moment Review completes). (That the corpus taxonomy leaves the two tokens' boundary unpinned is routed upstream — [`open-questions.md`](../../open-questions.md) §Status-line grammar.)

**Emits:** the formal-vote rationale; the formal-queue entry (vote-yes only — draft path, shape, named load-bearing invariants the model must cover, suggested tool by the property-class rule); the suggested verification scope. **Exit condition:** the candidate's formalization posture is explicitly recorded.

### Phase 4 — Submit

**Question: is the candidate ready to enter the commons?** **Goal:** package the candidate and its artifacts for independent review. **Submission is not admission** — grounding remains a library function performed by independent review, adjudication, and verification outside this tool; the tool's responsibility ends at preparing the candidate.

The phase emits the queue entries (review always; formal if vote-yes) and packages the bundle, forked by run type. **In-tree** (`--out` into the repo): queue entries written to the tracked `tools/guide/queue/{review,formal}.md`, plus the catalog follow-ups the workflow owes ([`contributing.md`](../../contributing.md) §Workflow steps 5–6). **Own-directory** (default): the whole bundle plus the two honest exits — the **human-runnable review brief** (the challenger run once more in a fresh context, bundling the draft and the constituent specs it names) and the **submission candidate** for the commons (entering the contribution lifecycle at Draft with Round 1 evidenced; the queue entries travel as admission work orders). The closing report renders sections done, findings raised/resolved/carried, the vote and its rationale, and exactly what Lane B does next — making `partially resolved` legible as *"you finished your half."*

**Emits:** the submission-candidate bundle, the review-queue entry, the human-runnable review brief, the formal-queue entry (when applicable), and the closing report. **Exit condition:** the candidate is packaged and ready for independent review.

## Navigation model — a linear super-wizard with one-way rewind

The four phases compose into one **super-wizard**: linear by default, and each phase — and each on-demand sub-wizard — repeats the same Question / Goal / Emits / Exit shape, so the user learns one rhythm and reuses it at every depth.

**The flow is one-way, inheriting the Elm/React discipline.** State moves *forward* through the arc; no step reaches back and mutates a prior step in place. Forward motion is **gated by the exit conditions** — a phase opens only once the prior phase's artifacts exist (you cannot Review a draft that does not exist, vote on a spec that is not drafted, or Submit an unreviewed candidate — that last gate *is* the status ceiling). This is the spine, and it is the discipline: "skip ahead and submit" is the move the tool exists to refuse.

**Roadblocks rewind; they do not teleport.** When a step raises a roadblock that a *prior* decision owns — Review finds the decomposition itself is wrong, or the structural-relation sub-flow finds the chosen cardinality cannot hold — the tool **flags the problem at the step that owns it** (the *problem spike*) and **steps back through the one-way arc one step at a time** until it lands on the flag. Not an arbitrary jump to anywhere; a controlled unwind to the exact origin. The user fixes it *there*, and the change **re-flows forward**: every downstream artifact the edit invalidates is re-derived and re-validated rather than silently kept stale — the same one-way guarantee Elm/React give a view, and the same *make drift structurally impossible* move the rest of the design already uses (the candidate list draining to empty; challenger output routed only into Lineage; the constituent-change cascade downgrading compositions on a breaking change). A fixed upstream decision cannot leave a stale downstream artifact behind it.

**Sub-wizards appear when needed, with exactly the same flow.** A step that carries its own decision spawns a sub-wizard that is the super-wizard in miniature — same Question / Goal / Emits / Exit, same linear-with-rewind-to-flag motion. Two already exist: the **Phase-1 candidate-list loop** (elicit → triage → emit, where re-triage is a rewind) and the **structural-relation sub-flow** (declare cardinality/modality → auto-insert invariants → queue the buggy twin). They are not special cases; they are the fractal showing through. The caution is restraint — spawn a sub-wizard only where a decision earns one: Phase 4 (Submit) is mechanical packaging, a checklist, not a looped wizard.

**v1 versus the deferred state machine.** v1 implements the linear spine, exit-gated forward motion, **rewind-to-flag**, resume, and the two existing sub-wizards — all of which ride the *hard-coded* arc and need no computed navigation. What stays deferred (the [`open-questions.md`](../../open-questions.md) §`state → phase → action` mapping, a non-goal for v1) is *deriving* where-am-I / what's-next and spawning sub-wizards from arbitrary artifact state rather than the fixed arc. Rewind walks a known arc backward to a recorded flag; the deferred work computes the arc itself.

## Status ceiling

The tool never mints `grounded`. The highest status a run may recommend is **`partially resolved`**.

| Condition | Recommended status |
|---|---|
| One or more findings remain unacknowledged (neither resolved nor explicitly carried) | `unresolved` |
| Every finding resolved or explicitly carried | `partially resolved` |

The recommendation is also never `draft`, which by the pinned grammar means the foundation round has not run — false the moment Phase 2 (Review) completes. Grounding is established only through the library's independent review, adjudication, and verification, never by this tool (the argument is in *The bar the tool must never cross*; the unpinned `unresolved`/`partially resolved` boundary is routed to [`open-questions.md`](../../open-questions.md) §Status-line grammar).

## Submission candidate

The tool's primary product is a **submission candidate**: the draft specification, the decomposition map, the Lineage notes, the findings record, the review brief, and the formal work items (vote-yes only). It is designed to enter the library's existing lifecycle at **Draft with the author-led review round already evidenced** ([`contributing.md`](../../contributing.md) §How to contribute); the queue entries travel with it as work orders the council and harness drain on admission.

The tool therefore provides **authoring assistance, review preparation, formal-work preparation, and submission-candidate generation**. It does **not** provide **independent review, adjudication, formal verification, or grounding** — those remain library functions performed outside the tool.

---

## Progressive disclosure — an output property, not a tool mode

There is no verbosity mode and no audience mode. What makes a spec readable to a newcomer *and* fast for a fluent reader is **progressive disclosure**, and it lives in the **output**: the library's three reading tiers — Tier 1 (plain-language Summary), Tier 2 (main text), Tier 3 (formal models) — held consistent with each other (the bridge principle). The same artifact serves both readers; there is nothing to toggle. The tool's job is to produce specs that carry the tiers: Summary plain, main text defining each term inline at first use, formal layer queued. (The interview defines terms inline as ordinary good prompting — always on, no switch.) The only real setting is **`--out`**: where output lands (the user's own directory by default, or in-tree), independent of everything else.

## Orientation, contract, reward — the UX chrome

A multi-hour, ~25-step arc with no instrument panel abandons its user. v1 specifies:

- **An opening contract.** Before Phase 1: what this run produces across its sittings (a complete reviewable draft + a queued independent review — and, if the commons is the goal, a submission-ready candidate bundle), what it explicitly does *not* (a `grounded` pattern — grounding is a library function), and the rough time budget with the session plan's expected sitting count. The honest ceiling is spoken at minute zero, not sprung at the end.
- **A progress panel.** At every transition: phase, section *n*-of-*m*, and time estimates — the methodology's published per-pass figures for the Phase 2 review passes; the tool's own estimates for Phase 1 authoring (and the Phase 3–4 formalise/submit steps), which the methodology does not time, calibrated against the pre-code prototype test (see *the user-success bar*). Hard-codable because v1's arc is hard-coded.
- **A closing report.** At completion: sections done, findings raised and resolved (and carried), the vote and its rationale, and exactly what Lane B does next and when — forked by run type. In-tree: the drain cadence, plus the catalog follow-ups the workflow owes that the tool does not perform ([`contributing.md`](../../contributing.md) §Workflow steps 5–6: forthcoming-links, the roadmap status row, index regeneration). Own-directory: the two exits — run the critique brief, and/or submit the candidate bundle (a rendered submission checklist points at the channel; the tool never files anything — see *Non-goals*). `partially resolved` is made legible as *"you finished your half"* — which is the true claim, and the difference between an accomplishment and an anticlimax.

## Artifacts — schemas pinned

- **Decomposition map** — `<domain>.decomposition.md`. Per candidate: name; one-line statement; disposition (`reuse <x>` / `extend <x>` / `new` / `reject — <reason>`); for promoted candidates, classification (`atom`/`composition`) with the triage answers that decided it; constituents (compositions); extraction rationale.
- **Candidate list** — the live, mutable working set behind Phase 1, persisted with the map so a resumed run reloads it; empty at Phase 1 exit (the exit invariant).
- **Spec scaffold** — `<name>.md`. Canonical section order; answers filled; `not-yet-drafted` on thin sections; a seeded `## Lineage notes`.
- **Review log** — **no separate file**; folded into the scaffold's `## Lineage notes`.
- **Review-queue entry** — draft path, shape, date, "independent Final Critique owed." For own-directory runs, rendered as the **human-runnable critique brief** (above), bundling the draft *and the constituent specs it names* — a composition cannot be fresh-read for capability provenance without them.
- **Formal-queue entry** (vote-yes only) — draft path; shape; vote rationale; named load-bearing invariants the model must cover; suggested tool by the property-class rule the roadmap's 2026-06-03 formal-triage table encodes (structural/relational → Alloy; behavioural/interleaving → TLA+ — restated here as a standing rule so new entries do not depend on a dated backlog table); date; status `model pending`. For own-directory runs it is not separately runnable — it travels in the submission bundle as the work order the council and harness pick up on admission.
- **Session plan** — emitted at pattern choice: the constituent-first ordering and rough sitting count for the chosen pattern's dependency set.

**Locations.** An in-tree run (`--out` into the repo) writes queue entries to `tools/guide/queue/{review,formal}.md` (council/harness reads them; see *The queues* for the re-homing). An own-directory run (default cwd) writes the whole bundle to the user's directory. **Mid-run quit** is safe: artifacts are written incrementally and valid-as-partial; the status recommendation is withheld until Phase 3 completes; a later run resumes from what is on disk.

## The queues — lifecycle, not just emission

A queue with no owner and no drain cadence rots the way the methodology warns its own rescan dates can ("it silently stops running… quiet fiction") — the live precedent being the 2026-06-10 C12/C3 `formal coverage of Invariant 4 pending` correction. So: **home & owner** — in-tree `tools/guide/queue/*.md` (re-homed 2026-06-11: the original `internal/queue/` plan collided with `internal/`'s engine-only rule, and queues are work orders for *public* patterns — they need tracking and history, which `internal/`'s untracked, machine-local exclusion deliberately forgoes; `tools/` is already site-excluded, so the queue is tracked-but-unpublished), drained on the scheduled rescan's weekly batch cadence (one calendar surface, not a second rhythm): the council drains the review queue; the council drains the formal queue by *authoring* the model, with the harness only *verifying* it; for outsiders, the critique brief and the submission bundle are the drains. **Consumer interface** — the entry's fields are exactly a drain run's work order, which is why the schema is fixed here. **Staleness** — an entry older than one drain cadence is flagged by the next drain run as a finding, not left silent; each entry is dated so staleness is computable.

## Form and fit

- **Deterministic core:** a CLI in [`tools/guide/`](.), Node ESM (ECMAScript modules), **zero npm dependencies** (built-ins only), offline. It does not inherit a convention from neighbors — `tools/harness/` carries a `tla-checker` dependency and `tools/recipe/` is Python; the no-deps choice stands on its own (a front-door tool should run with nothing to install beyond Node itself — the one named runtime requirement, minimum version pinned at implementation). **Acquisition:** an outsider gets the tool by cloning the repo and running it from the clone; the clone *is* the catalog retrieval reads, so catalog freshness is clone freshness. `$EDITOR` unset falls back to inline multi-line capture — the prompt degrades, the run never blocks.
- **Challenger:** opt-in, via built-in `fetch` to a configured AI endpoint — endpoint URL, key, and model named in a config file or environment variables (the exact config contract is pinned at implementation; it is the named home, not an ambient default); the user's own key for own-directory runs, the repo's local untracked config for in-tree runs. Still zero *package* dependencies; a configured endpoint is runtime config, not an installed package. No endpoint → the core runs unchanged.
- **Question sets** live in a data module the CLI imports, **citing the canonical docs** (`pressure-testing.md`, `spec-format.md`, `contributing.md`, `roadmap.md`) as SSOT (single source of truth), hand-curated with mandatory source citations and a drift check (a test that fails if a cited anchor stops resolving). (`CLAUDE.md` is deliberately absent: it is a one-line shim to `AGENTS.md`, which carries no canonical content — a citation into it would resolve as a file while pointing at nothing.) An automatic generator is desirable but undesigned, so unclaimed.

## v1 scope, non-goals, and the user-success bar

**In scope (decision B — outsiders day one):** the full Lane A arc with the Phase-1 elicitation interview, candidate retrieval, per-question worked examples, the mutable candidate-list loop, `$EDITOR` prose, resume, the UX chrome, the two-exit outsider Lane B (critique brief + submission bundle), the opt-in AI challenger, and the mechanical lint.

**Non-goals (deferred, not forgotten):**
- **No answer-giving AI (branch b)** beyond catalog retrieval — no AI-proposed decomposition, drafting, classification, or finding-closure. The challenger interrogates; it never answers.
- **No *computed* cross-run navigation.** v1 implements the linear spine, exit-gated forward motion, one-way **rewind-to-flag**, and resume on the *hard-coded* arc (see *Navigation model*). What stays deferred is *deriving* "where am I / what's next" and spawning sub-wizards from arbitrary artifact state (vs the hard-coded arc) — the `open-questions.md` §state→phase→action mapping, still unbuilt.
- **No multi-pattern authoring in one run.** Decompose surfaces many; author walks one; the session plan sequences the rest across runs.
- **No submission automation.** The closing report renders the candidate bundle and a checklist pointing at [`contributing.md`](../../contributing.md) §How to contribute; the tool never opens issues or pull requests on the user's behalf.

**User-success acceptance bar (the UX's Proof node).** The tool fails if its users fail. Falsifiable bar: *an outsider with domain knowledge and no library vocabulary completes the **decomposition** step of Phase 1 (1a–1c) — producing a decomposition map they can defend — in under an hour, unaided.* The bar is verified **before code**: a timed paper-prototype walkthrough of that decomposition script (Phase 1, 1a–1c) with three to five real outsiders, run against this document — the cheapest discharge of the closing line's own commitment. A failed run is evidence, not embarrassment: it is the one thing that legitimately reopens decision (2). Builder-facing bar (unchanged): an implementer can build the tool from this doc without inventing a load-bearing decision.

## How this connects to what exists

- The **`state → phase → action` mapping** in [`open-questions.md`](../../open-questions.md) is the substrate this tool first projects; v1 hard-codes a near-linear arc (looped within Phase 1, with one-way rewind-to-flag across phases — see *Navigation model*), and resolving that question is what lets a later version derive next-steps from artifact state.
- The **contribution lifecycle** in [`contributing.md`](../../contributing.md) (Proposal → Draft → Pressure-tested → Grounded) is the ladder the tool walks a user up — stopping, by design, at the Pressure-tested rung. An outsider's candidate enters the same ladder by submission; the bundle is a Draft-with-evidence, not a new rung.
- The **two-lane split** is the methodology's formal-layer vote (`pressure-testing.md` §Formal models) plus the model backlog (a `roadmap.md` construct) made an explicit authoring workflow; the **challenger** is its AI-conducted fresh-reader Final Critique pulled forward, live, in non-binding form.

## Design review

This design was pressure-tested before any code — the dogfood the thesis demands. Three pressure-test passes plus two later directives (a vocabulary alignment and the v5 four-phase restructure), all folded:

- **Fable Super-Torvalds (correctness) — 2026-06-11 → v2.** Eight foundational findings folded: the tool minting forbidden `grounded` from one author-led round (→ the bar + two-lane ceiling at `partially resolved`); the undefined Lane B failure path; the owner-less, outsider-undrainable queue; decompose never reading the catalog; the undecided findings loop; contributor findings colliding with Lineage-not-sibling hygiene; the incoherent multi-pattern workflow; missing artifact schemas. Plus the lint-vs-judge boundary, the over-broad moat claim, a false "matches harness/recipe conventions" citation, a non-existent question generator, and a miscited backlog source.
- **Fable UX Super-Torvalds (experience) — 2026-06-11 → v3.** Verdict: the v2 wizard served contributors, not the outsiders it listed first — losing the median outsider in an *undesigned* Phase 1 and a one-sitting marathon. Two decisions taken: **the live AI challenger (deterministic core + opt-in challenger; answer-giver rejected except retrieval)** — decisive because the methodology already mandates an AI fresh-reader for grounding, so a non-challenging wizard contradicted its own method; and **full outsider support in v1 (decision B)**. Findings folded: the undesigned first mile (→ elicitation interview); the catalog wall (→ candidate retrieval); definition-is-not-discrimination (→ per-question yes/no examples); no back button (→ the mutable candidate-list loop, renamed by the 2026-06-11 vocabulary directive); the one-sitting fantasy (→ resume to v1); prose in a line prompt (→ `$EDITOR`); self-graded severity as exit gate (→ decoupled, carry-as-open); the vote with no floor (→ plain-language probes); no instrument panel / opening contract / closing report (→ UX chrome); the vapor outsider Lane B (→ human-runnable review brief); the bait-and-switch one-of-many (→ session plan); and no user-success bar (→ the Proof node above).
- **Fable fresh-reader adversarial (corpus-verified) — 2026-06-11 → v4.** Strict fresh-reader pass (the pass question sets and this document, nothing else), every checkable citation opened against the corpus; a consolidate seat (GPT) and an outside seat (Grok) contributed the disposition table and three findings. Verdict: the v3 architecture survives — every foundational hit landed where v3's new ambitions touch existing machinery; the seams got the decisions, the interiors didn't. 26 findings — **4 foundational:** retrieval read only atoms while the extraction gate and this document's own Audit Trail example required compositions (→ both catalogs searched; retrieval triggers the gate's *consideration*, the gates decide); the outsider Lane B could not deliver the grounding it promised and a vote-yes outsider's formal entry had no drain (→ **decision 3**: authoring plus submission candidate — two honest exits, queue entries travel as admission work orders); the status recommendation had no mapping and `draft` contradicted its own token definition (→ set pinned to `{unresolved, partially resolved}` with the resolved-or-carried rule; the corpus taxonomy gap routed to `open-questions.md`); the relation templates cited canonical phrasing that existed nowhere and named the static orphan form the Relations line forbids (→ canonical home created in `spec-format.md` §Cross-cutting authoring conventions, conditional at-quiescence form). **20 refining folded:** the queue re-home propagated to §Artifacts; the SSOT list corrected (shim out, `contributing.md` in); the placement test re-quoted and the fourth EOS question restored; lint ownership named (`lint.py` owns the rule, the guide knowingly mirrors the draft-local subset); the vote probes gained the clock probe and the practiced-bar defense; the Final Critique split into fresh read then carry adjudication; the queue drain pinned to the rescan cadence with the drain run as flagger; time-estimate provenance corrected; sitting language aligned with resume; the cascade conditioned on breaking changes; acquisition, endpoint config, and `$EDITOR` fallback pinned; GRID/EOS/SSOT/ESM glossed; the critique brief made to bundle constituent specs; the moat wording ceded to the manifesto; the triage-table citation lifted to a stated rule; never-answers made structural (channel constraint); mid-run challenger failure made degrade-not-block; the pre-code prototype test attached to the user-success bar. **2 rhetorical rewritten:** the challenger's contradiction overclaim (the method's own Round 1 is author-led; the challenger is additive, not a contradiction-resolver); the author/verify drain muddle.
- **Vocabulary directive folded — separation of concepts — 2026-06-11.** The corpus's unit of separation is the **concept**; the guide's pre-triage items are **candidate concepts** — a stage, not a kind, consumed by triage. The legacy working noun is banned corpus-wide (lint rule J names it; the title-case proper noun naming the ancestor principle remains permitted). This document's ~30 uses were all Phase-1-stage uses — the term was already behaving as if the stage definition existed, so the rename is recognition, not renovation; prior review entries' references were renamed with it. The elicitation-friendliness relocates rather than dies: it was always in the probes, never the noun — the probes never used it, and the tool's output labels answers as candidates, so the user never produces the word. Triage gained the fourth disposition (**reject**, recorded in the decomposition map) and Phase 1 its exit invariant (the candidate list drains to empty).
- **Four-phase restructure — v5 — 2026-06-12.** The three-phase arc (Decompose / Author / one author-led round) was reorganized into **four explicit phases — Authoring, Review, Formalise, Submit** — each answering one question, emitting named artifacts, and resumable independently. **Authoring** merges the former Decompose and Author phases (understand the domain and write the draft in one author-led arc, 1a–1d); **Review**, **Formalise**, and **Submit** split the former combined round so pressure-testing, the formal-layer decision, and packaging are distinct responsibilities — the motivation being phase-by-phase implementation and automation decisions rather than one monolith, and a clearer outsider journey. No load-bearing machinery was dropped: the decompose loop and exit invariant, the structural-relation sub-flow, the three passes with forced postures, the carry-as-open exit gate, the two-step Final Critique, and the plain-language vote probes all carry into their phases. The status-recommendation mapping was lifted into a standalone **Status ceiling** section and the product into a standalone **Submission candidate** section. Vocabulary held to the 2026-06-11 directive — pre-triage items stay **candidate concepts**, not the banned working noun. Phase-number cross-references (UX progress panel, user-success bar) were re-pointed: the review passes are Phase 2, the decomposition bar is Phase 1 (1a–1c). A **Navigation model** was then pinned: the four phases compose into one linear super-wizard with Elm/React-style one-way flow — forward motion exit-gated, roadblocks rewinding one step at a time to the flagged *problem spike* (not arbitrary jumps) and re-flowing the fix forward so no stale downstream artifact survives, and sub-wizards spawning on demand with the identical Question / Goal / Emits / Exit shape. Rewind-to-flag and the two existing sub-wizards (the candidate-list loop, the structural-relation sub-flow) are v1 on the hard-coded arc; *computed* navigation stays the deferred state→phase→action work.

Next before code: the pre-code prototype test of the Phase 1 decomposition bar, then one cheaper fresh read of this v5 — three passes in, the findings are converging on seams rather than structure, and the prototype test is the instrument that says whether the structure meets its users.
