## Step 3 — bound saturation

- **Correct model:** 274 states at `ExpiresAt = 2`, `MaxClock = 3`, `MaxC = 3`. Unlike the pre-refactor model (which was purely slot-parametric in `MaxC`), this model adds an **injected clock dimension** (`now \in 0..MaxClock`, advanced by `Tick`). The raw state count is therefore **linear in `MaxClock`** — each additional clock tick multiplies the reachable `(status, successor)` configurations by one more `now` value — but the model's *behavior* **saturates once `now >= ExpiresAt`**: at that point every stored-`Active` slot reads `Expired` (`Lapsed` is true for all of them), `EffActiveCount(now)` is 0 regardless of how many stored-`Active` slots exist, and no further `now` increment changes which transitions are enabled. `MaxClock = 3` with `ExpiresAt = 2` exercises both regimes — clock strictly before the deadline (`now \in {0,1}`, where effective-Active is non-trivial and the uniqueness/TOCTOU races live) and clock at/after the deadline (`now \in {2,3}`, where the derivation saturates and lapsed-coexistence appears) — so raising `MaxClock` past `ExpiresAt + 1` adds only behaviorally-equivalent post-deadline clock values, not new behavior.
- **Slot dimension:** `MaxC = 3` exercises a two-hop rotation chain (k1→Rotated, k2→Rotated, k3→Active) — sufficient for every chain-link path — and admits two stored-`Active` slots coexisting (the lapsed-plus-fresh case the 67-state trap relies on). The bound is deliberate: it is the minimal scope that exercises both the multi-hop rotation chain and the stored-Active-coexistence nuance under a clock that crosses the deadline.
