# Prior-art / reading note — Augment's brownfield spec-driven development guide

_Working staging, not canonical. A reading brief on an adjacent vendor guide, with the method takeaways to adopt and the positioning contrasts to keep. Lands into the Evergreen Modernization framing, measurement.md, and the prior-art/positioning note as the adoptions are worked._

**Source:** *Spec-Driven Development for Brownfield Enterprise Codebases* (Molisha Shah, Augment Code, published 2026-03-19, updated 2026-06-18) — https://www.augmentcode.com/guides/spec-driven-development-brownfield-codebases

**Context for you:** Augment's answer to the brownfield problem: comprehensive upfront specification of a 100k+-file legacy system is impractical, so write **change-level specs** — narrow deltas scoped to the modification — after their Context Engine builds a dependency map of the existing code. Adjacent to Grace Commons but *relative* where we are *absolute*: their specs describe deltas against undocumented behavior and chase the code (their own "drift rate" metric governs how fast the spec falls behind); our code chases the spec and drift is measured as conformance. Their discovery layer (semantic dependency mapping at 400k-file scale) is real and worth pairing with; their specification and verification layers are the gap this library fills. Adopt the following:

1. **The four-element change-level spec as the modernization delta container.** Their change spec defines: current behavior, target behavior, **invariants (what must not change in adjacent systems)**, scope boundary. The shape is right and the third element is an empty slot shaped exactly like our atoms — today they fill it with prose ("don't break the audit trail"); filled from this library it becomes *named pattern invariants* ("Audit Trail Invariants 1–8 hold") with the pattern's Generation acceptance queries run as the regression gate. Deltas anchored to grounded absolutes, measured instead of asserted. Adopt as the per-change artifact for Evergreen Modernization engagements; their migration-spec pattern (target state + independently-deployable steps + facade) slots our compositions in as the *target state* the strangler fig grows toward.
2. **Specced-vs-unspecced defect density.** Their sharpest proposed metric: defect density in pattern-anchored areas of a codebase versus unanchored areas. Adopt into [`measurement.md`](../measurement.md) as a level-2 metric once modernization engagements produce the data — it is the brownfield form of the leverage claim, and no one (them included — they say so) has published rigorous before/after numbers. First credible dataset wins the citation.
3. **Never attempt comprehensive system specification on brownfield entry.** Their critique of full-system specs is correct and must never land on this library, so state the entry move explicitly wherever modernization method gets codified: we do not specify the *system*, we recognize *patterns* — the concept-recovery routing test against a bounded atom set (nine-system saturation evidence, [`discoveries.md`](../discoveries.md) 2026-06-13). Their "tribal knowledge lost" failure mode is answered by the fossil taxonomy ([`the-spec-layer.md`](../the-spec-layer.md) §Essential vs. Accidental) — intent reconstruction with accidental complexity classified and routed to the right decision-maker — not by archaeology.

**Positioning contrasts (for [`prior-art-and-positioning.md`](./prior-art-and-positioning.md), not process changes):**

- **The drift-direction tell.** Their governing metric is *drift rate* — divergence of spec from actual behavior, managed by the discipline "update the spec alongside every change." That is spec-as-documentation with better hygiene: the code holds authority. Conformance inverts it. Same word, opposite direction of truth — a one-sentence differentiator for the earning-SSOT argument.
- **The verification floor.** The guide's worked example of a "machine-checkable contract" is `redocly lint openapi.yaml` — validating that the *schema file is well-formed*, not that any implementation honors it. The conformance validator's records-alone checks are the layer above that floor; the contrast is citable evidence that "machine-checkable" in the 2026 SDD wave still mostly means lint.

**Narrative bonus (not a process change):** their own workflow requires "at least one engineer who understands the existing architecture well enough to review and correct the dependency maps" — the tribal-knowledge bottleneck restated as a staffing requirement. The atom taxonomy is the scalable substitute: pattern recognition transfers across engagements; per-system archaeology does not. Usable in the modernization pitch alongside the Salesforce two-years-to-four-months dependency-first case the guide itself cites.
